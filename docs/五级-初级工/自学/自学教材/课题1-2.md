## 一、数据库是什么：表、字段、记录、主键

在学"怎么查"之前，先搞清楚自己到底在查什么。本课题用的数据库 `practice.db` 里有三张表：`users`（用户）、`products`（商品）、`orders`（订单）。

| 概念 | 含义 | 本课题例子 |
|---|---|---|
| 表（table） | 存放同一类事物信息的集合，像一张Excel表 | `users` 表存所有用户信息 |
| 字段（column） | 表里的一列，描述事物的某一个属性 | `users` 表有 `user_id`、`user_name`、`city`、`register_date` 四个字段 |
| 记录（row） | 表里的一行，代表一个具体的"个体" | 一条记录就是一个具体用户的信息 |
| 主键（primary key） | 能**唯一标识**一条记录、不允许重复的字段 | `users.user_id`、`orders.order_id`、`products.product_id` |

**为什么一定要有主键？** 如果没有一个"身份证号"一样的字段，两条记录就算所有其他信息都长得一模一样，你也没办法准确判断"这是同一个人"还是"碰巧两条记录长得一样的两个人"。主键就是用来解决这个问题的——保证表里每一条记录都有独一无二的编号。**一旦你在某张表里发现主键重复了，基本可以直接断定这批数据存在严重的质量问题**，这个信号比任何单独一个字段的异常都更该引起你的警觉。

**三张表是怎么联系在一起的？** 再看一眼 `orders` 表，它有一个 `user_id` 字段，这个字段里存的编号，理论上应该能在 `users` 表里找到对应的那一条用户记录；同理，`orders.product_id` 也应该能在 `products` 表里找到对应商品。**两张表正是靠这种"字段对字段"的方式关联起来的**——这句话先记住，第四、五节讲 `JOIN` 的时候会用到它。

**动手检查一下**：对照上表，自己在三张表里找出各自的主键，并说出"`orders.user_id` 应该能在哪张表里找到对应记录"。这不是走过场——后面排查"孤儿记录"用的正是这个对应关系。

## 二、基础SQL语法：从"挑数据"到"排序限量"

SQL查询最常用的骨架就这一句：

```sql
SELECT 字段 FROM 表名 WHERE 条件 ORDER BY 字段 LIMIT 数量;
```

- **SELECT 字段**——你想要哪些字段，想要全部就写 `*`。
- **FROM 表名**——从哪张表里找。
- **WHERE 条件**——筛选条件，不写就是不筛选、要全部记录。
- **ORDER BY 字段**——按哪个字段排序，默认从小到大，加 `DESC` 就是从大到小。
- **LIMIT 数量**——只要前几条，常用来"先看几条结果，别一下子查全表"。

> ⚠️ **零基础最容易踩的坑**：`WHERE` 条件里，**文字要用英文单引号包起来，数字不用**。
>
> 查城市是"北京"的用户要写 `WHERE city='北京'`，引号不能丢；查价格大于5000的商品要写 `WHERE price>5000`，绝不能写成 `WHERE price>'5000'`。记混了，查询不一定报错，但结果可能悄悄不对——**这正是SQL新手阶段最隐蔽的一类错误：没有任何报错提示，只是结果不对**。

### 回到开头那个判断

现在可以正式回答开篇的问题了：**小李的做法有没有问题？**

先看他的查询语句：`WHERE city='beijing'`。引号倒是加对了，但**把中文"北京"错写成了拼音"beijing"**，而数据库里存的是中文"北京"，拼音永远匹配不上，查出来自然是0条。

所以问题不在于"查出来是0条"这件事本身，而在于**看到0条这个结果，小李完全没有停下来想一想"一个大城市的用户数是0，正常吗"**。0条和"查出一个异常大的数字"一样，都是需要你多问一句"为什么"的信号，不是看到一个数字就能直接收工导出的。把这句话记牢，它会在第四节以另一种形式（997 vs 1000）再出现一次。

### 动手验证

打开 Jupyter，连接数据库，跑下面这段代码：

```python
import sqlite3, pandas as pd
conn = sqlite3.connect("../数据集/practice.db")

q1 = "SELECT * FROM users WHERE city='北京'"
print("北京用户数：", len(pd.read_sql(q1, conn)))

q2 = "SELECT * FROM products WHERE price>5000"

q3 = "SELECT user_id, user_name, register_date FROM users ORDER BY register_date DESC LIMIT 5"
print(pd.read_sql(q3, conn))
```

**实测结果（已验证，你跑出来的结果应该与此完全一致）**：

```

价格超过5000元的商品数： 24
```

用正确的中文"北京"一查，马上就是30条——而不是小李查出来的那个具有迷惑性的0。**跑完这三个任务，自己先猜一下结果大概是什么量级，再运行验证**，这个习惯从现在就开始养成，后面每一次查询都照此执行。

**自查一下常见的两类错误**：①字符串条件忘加引号，或者不小心用了中文引号""而不是英文引号''；②字段名或表名拼写错误（比如把 `product_id` 拼成 `products_id`）导致报错。如果你跑代码时结果和上面对不上，先从这两处查起。

## 三、GROUP BY 与 COUNT：按组统计

前面查的都是"挑出符合条件的记录"。但实际工作中更常见的需求是"按类别数一数各有多少"——比如"各城市分别有多少用户"。这就要用到 `GROUP BY`：

```sql
SELECT 分组字段, COUNT(*) FROM 表名 GROUP BY 分组字段;
```

**原理**：`GROUP BY city` 做的事情是，把所有记录按 `city` 字段的取值分成一堆堆——所有"北京"分一堆，所有"上海"分一堆……`COUNT(*)` 再数每一堆里有多少条记录。

```python
q = "SELECT city, COUNT(*) as cnt FROM users GROUP BY city ORDER BY cnt DESC"
print(pd.read_sql(q, conn))
```

**实测结果（已验证）**：

```
城市    cnt
成都    39
广州    36
深圳    34
杭州    33
北京    30
上海    28
```

**互相印证**：上一节任务查出的"北京用户数=30"，正好对得上这张表里北京那一行的30。**这正是聚合查询的一个额外好处——它能让你用一条查询同时核对多个筛选条件算出来的结果，是检查自己有没有写错查询的好工具。**

`GROUP BY` 不是只能配 `COUNT`，它是一个"分组之后统一加工"的通用工具，配合 `AVG()` 就能按组算平均值，用法完全一样：

```python
q = "SELECT category, ROUND(AVG(price),1) as avg_price, COUNT(*) as cnt FROM products GROUP BY category ORDER BY avg_price DESC"
print(pd.read_sql(q, conn))
```

**实测结果（已验证）**：

```
category    avg_price  cnt
手机        6221.2     9
耳机        5499.0     8
笔记本电脑   4856.1     14
智能手表     4665.7     12
平板        3856.1     7
```

`COUNT(*)` 数条数，`AVG()` 算平均值，跟在 `GROUP BY` 后面的用法一模一样——这说明 `GROUP BY` 是一个"分组之后统一加工"的通用工具，不是只能配 `COUNT` 一种统计量。

**再动手练一次**：自己写一条查询，统计 `orders` 表里各个 `status` 状态分别有多少条订单。你应该会得到 `completed 790、cancelled 125、pending 85`，三个数字加起来正好是1000，等于订单总数——先记住这个"加起来应该等于总数"的核对动作，它是第四节要讲的核心习惯的第一次预演。

## 四、一个真实案例：JOIN 之后，为什么"丢了"3条记录

现在进入本课题分量最重的一节。`orders` 表总共有 **1000条** 订单记录。如果要统计"各城市的订单量"，需要把 `orders` 和 `users` 两张表拼接起来——因为订单本身不含城市信息，城市信息在用户表里，两张表要靠 `user_id` 这个共同字段关联。这种把两张表"拼"到一起看的操作叫 `JOIN`。

```python
q = """SELECT u.city, COUNT(*) as cnt FROM orders o
        JOIN users u ON o.user_id = u.user_id
        GROUP BY u.city ORDER BY cnt DESC"""
print(pd.read_sql(q, conn))
```

**实测结果（已验证）**：

```
深圳 193   成都 188   广州 173   北京 170   杭州 146   上海 127
```

**动手算一下**：把这六个城市的数字加起来：193+188+173+170+146+127 = **997**。

现在停下来问自己：`orders` 表总数是1000条，按城市统计出来的订单量加起来却只有997条，**少的这3条去哪了**？

### 只发现数字对不上，不等于分析完了

很多人到这一步会卡住：看到997≠1000，意识到"好像有点不对"，但不知道下一步该怎么查，于是就这么把997的结果交了上去。**这是最危险的做法——发现了异常信号却没有处理，和根本没发现一样危险，甚至更糟，因为你已经有了线索却没有去追。**

完整的排查思路分两步：第一步，搞清楚 `JOIN` 本身的工作机制；第二步，用正确的方法把"丢失的3条"揪出来。

### JOIN 的两种类型，处理"两表对不上"时结果完全不同

`JOIN` 最常用的有两种：

| | INNER JOIN | LEFT JOIN |
|---|---|---|
| 结果范围 | 只保留两表都能对上的记录 | 左表全部保留，右表对不上则填 `NULL` |
| 对不上的记录 | **被静默排除**，不会有任何提示 | **被保留**，右表字段显示为空 |
| 能否用来找"丢失"的记录 | 不能（问题记录已经被排除了，你根本看不到它） | **能**（配合 `WHERE 右表字段 IS NULL`） |

```sql
SELECT ... FROM A JOIN B ON A.字段=B.字段;           -- 等价于 INNER JOIN
SELECT ... FROM A LEFT JOIN B ON A.字段=B.字段;      -- LEFT JOIN，对不上也保留
```

上面那条按城市统计的查询用的是普通 `JOIN`，也就是默认的 `INNER JOIN`——它只保留两张表都能对上的记录，**对不上的那些会被静默排除，不会有任何报错提示，程序正常跑完，看起来一切正常，但数据已经悄悄少了**。这就是997比1000少3条的真正原因：丢的不是数据本身，是在 `JOIN` 这一步被"筛"掉了。

> 🔑 **判别口诀**：要"两边都有的"数据 → 用 `INNER JOIN`；要"左边一个不漏，顺便揪出查无此人的" → 用 `LEFT JOIN`。

### 用 LEFT JOIN 把"丢失"的记录揪出来

既然 `LEFT JOIN` 会把对不上的记录也保留下来、只是右边填 `NULL`，那只要再加一个条件——**筛选出右表字段是 `NULL` 的那些记录**——就能精准找出"左表有、右表却找不到对应记录"的异常数据。这类记录有个专门的名字，叫**孤儿记录**（这里具体是"孤儿订单"）。

```python
q = """SELECT o.order_id, o.user_id FROM orders o
        LEFT JOIN users u ON o.user_id = u.user_id
        WHERE u.user_id IS NULL"""
print(pd.read_sql(q, conn))
```

**实测结果（已验证）**：

```
order_id  user_id
998       9001
999       9002
1000      9003
```

`users` 表里一共只有200个用户（`user_id` 从1到200），但订单998、999、1000的 `user_id` 分别是9001、9002、9003——**这些编号在 `users` 表里根本不存在**。

**想象一下后果**：如果业务需求是"统计各城市的订单量"，你直接把这1000条订单全部导出、拿去跟用户表拼接，这3条订单会发生什么？它们的 `user_id` 在 `users` 表里根本找不到对应记录，没有城市信息，没法被算进"某个城市的订单量"里——用 `INNER JOIN` 的话，它们会被悄悄排除，程序正常跑完，不会有任何提示，这才是最危险的地方：**没有任何错误信息，但数据已经少了**。想象你导出的报告显示"本月共997条有效订单"，而实际系统里明明有1000条，如果你没做这次排查，你根本不会知道"少的3条"是正常业务情况，还是数据本身有问题。

> 🔑 **判别口诀（SQL对照板书）**：`LEFT JOIN + WHERE 右表字段 IS NULL` → 专门用来找"查无此人"的孤儿记录。

### 没查出问题，也要写进报告

用同样的方法再查一下 `orders.product_id` 是否都能在 `products` 表里找到对应商品：

```python
q = """SELECT o.order_id FROM orders o
        LEFT JOIN products p ON o.product_id = p.product_id
        WHERE p.product_id IS NULL"""
print(pd.read_sql(q, conn))
```

**实测结果（已验证）**：**空结果，没有一条孤儿记录**——商品这边的关联是干净的。

这说明：排查的意义不是"非要挑出毛病"，而是**系统地把该查的关联字段都查一遍**。用户这边查出3条孤儿订单，商品这边没查出问题，**两者都要写进交付说明里**——不能因为"顺手查了一下没发现问题"就连这一步检查本身都略过不提。"没问题"也是一条需要确认和记录的结论，不是默认状态、可以不写的状态。

### 这一节最该带走的一课

**代码能跑出结果，不代表结果是对的。** `COUNT` 核对总数、`LEFT JOIN` 核查关联完整性，这两个动作花不了多少时间，但它们是唯一能帮你在导出之前发现问题的机会——数据一旦发出去，别人很难再帮你发现这批数据"悄悄缺了几条"。回头看看开篇小李查出"0条"的那个例子，和这里"997≠1000"的例子，本质上是同一类问题的两种表现：**一个是查询条件写错导致结果异常地少，一个是JOIN关联方式导致结果悄悄变少**——共同点都是"代码正常跑完、没有报错，但结果是错的"。

## 五、业务需求怎么翻译成SQL查询

实际工作中，业务方不会直接给你SQL，他们只会说一句中文需求，比如：**"帮我查一下北京地区最近一个月的订单量。"** 这句话要翻译成SQL，你需要先把它拆成几个要素：

```
① 要查哪张表？要不要关联别的表？       —— 订单在orders，但"北京地区"是users表里的字段，要JOIN
② 筛选条件对应哪个字段？具体筛选值是什么？ —— city='北京'
③ "最近一个月"怎么界定？              —— 需要一个基准日期，再往前推时间范围
④ 最终要的是明细还是统计数量？         —— "订单量"是数量，要用COUNT
```

**第3步最容易被轻视**。"最近一个月"或者"近30天"，看起来很明确，其实藏着一个问题：**是自然月，还是从今天往前滚动30天？算不算今天？** 这种边界不说清楚，你和业务方对出来的数字可能完全不一样。拿不准就要主动去问清楚，而不是自己猜一个定义就开始写查询——这条规则在考试和实际工作中同样适用。

### 一次完整的演示

就用数据集本身做一次演示。这批订单数据的最新日期是2026-03-31，这里把"近30天"定义为2026-03-01至2026-03-31这个区间（共31天，按自然日近似处理）。现在要查"北京地区近30天的订单量"：

```python
q = """SELECT COUNT(*) as cnt FROM orders o
        JOIN users u ON o.user_id = u.user_id
        WHERE u.city = '北京' AND o.order_date >= '2026-03-01'"""
print(pd.read_sql(q, conn))
```

**实测结果（已验证）**：`cnt： 59`

**顺带想一下，把前面的知识点串起来**：这条查询用的是普通 `JOIN`（也就是 `INNER JOIN`），第四节说过它会悄悄排除孤儿订单。这里有没有影响？回忆一下——998/999/1000号孤儿订单的下单日期都在1月，本来就不在"近30天"这个筛选范围内，所以这次结果没有受到影响。**但这只是巧合，不代表以后每次用 INNER JOIN 统计时孤儿记录都恰好落在筛选范围之外**——这正是为什么"核对总数"要成为一个固定的习惯动作，而不是只在"感觉可能有问题"的时候才做。

**自己动手练一次**：仿照上面四个翻译步骤，拆解"统计上海地区completed状态的订单数量"这个需求——涉及哪些字段、哪些条件，然后独立编写并运行查询，验证自己的拆解是否正确。

## 六、变式思考：把"核对总数"变成一个随手就做的动作

最后巩固一次第四节的核心习惯。请你自己写一条SQL，用 `JOIN` 把 `orders` 和 `users` 关联起来，按城市统计订单量：

```python
q = """SELECT u.city, COUNT(*) as cnt FROM orders o
        JOIN users u ON o.user_id = u.user_id
        GROUP BY u.city ORDER BY cnt DESC"""
print(pd.read_sql(q, conn))
```

这其实就是第四节已经跑过的那条查询，六个城市加起来是997，而 `orders` 表总数是1000条。**少的这3条正是998/999/1000号孤儿订单**——它们的 `user_id` 在 `users` 表里找不到对应记录，普通 `JOIN`（即 `INNER JOIN`）在关联的时候把它们排除掉了，不会有任何报错提示。

把这件事提炼成一条可以在任何新查询上复用的习惯：

> **只要查询里用到了 JOIN，导出前就不能只核对"这张表本身对不对"，还要核对"JOIN之后的总数，和原表总数能不能对得上"。** 差了几条，往往就是关联字段存在孤儿记录。核对的方法很简单——**用 COUNT 分别算一下 JOIN 前和 JOIN 后的总数，两个数字一对比就知道了**。

这不是一个只在本课题数据集上才成立的巧合，而是任何涉及多表关联的场景都该养成的固定检查步骤。

| 考点 | 考试怎么考 | 易错点 |
|---|---|---|
| **导出前核对数量** | 实操核心 | **写完查询直接导出，不核对数量** |
| 数据库基本概念 | 单选/判断 | 混淆"字段"和"记录"，不清楚主键的唯一标识作用 |
| WHERE条件的引号规则 | 实操 | 字符串条件忘加引号，或数字条件误加引号 |
| GROUP BY + COUNT | 实操 | 分组字段选错，或忘记COUNT的结果应与其他查询互相印证 |
| JOIN查找孤儿记录 | 实操 | 不知道用 `LEFT JOIN` + `WHERE 右表字段 IS NULL` 的组合方式；误以为INNER JOIN也能发现孤儿记录 |
| 业务需求翻译为SQL | 简答/实操 | 忽略"近30天"这类时间范围的边界定义，自己想当然地猜一个定义 |

## 自测练习

以下5题与课堂讲义的随堂练习完全一致，答案直接写出（自学材料不设折叠，建议先自己写出答案，再对照核对）。

**练习 1**：某订单表中有部分订单的product_id在商品表中找不到对应记录，该用什么SQL方式排查？

**答案**：使用LEFT JOIN以订单表为主表关联商品表，再用WHERE子句筛选商品表对应字段为NULL的记录，即可找出所有product_id无效的"孤儿"订单。

**练习 2**：`SELECT city, COUNT(*) FROM users GROUP BY city` 这条SQL语句的作用是什么？

**答案**：按城市分组，统计每个城市的用户数量。GROUP BY把数据按city字段的取值分组，COUNT(*)统计每组内的记录条数。

**练习 3**：导出查询结果前，为什么要先用COUNT核对数量？

**答案**：因为写错查询条件（比如WHERE条件写漏、JOIN关联字段用错）很容易导致导出的数据比预期少或者多，而这种错误从导出的文件本身不容易直接看出来。先用COUNT核对数量是否符合预期，能及时发现查询逻辑上的问题，避免把错误的数据交付出去。

**练习 4**：主键的作用是什么？

**答案**：主键用于唯一标识表中的每一条记录，确保不会出现完全相同标识的两条记录。主键重复或冲突通常意味着数据存在严重的质量问题。

**练习 5**：业务需求"查询北京地区近30天的订单"，翻译成SQL查询时要确定哪些要素？

**答案**：需要确定：筛选条件对应的字段名（地区字段、下单日期字段）、具体的筛选值（"北京"）、时间范围的计算方式（近30天如何界定，是否需要用当前日期减去30天）。把业务语言准确翻译成字段名和筛选条件，是写对SQL查询的关键一步。

## 小结

| 要点 | 一句话 |
|---|---|
| 数据库基本概念 | 表/字段/记录/主键，主键唯一标识一条记录 |
| 基础SQL骨架 | `SELECT 字段 FROM 表 WHERE 条件 ORDER BY 字段 LIMIT 数量` |
| 聚合统计 | `GROUP BY 分组字段, COUNT(*)`——分组之后统一加工，也可配`AVG()`等 |
| JOIN核心区别 | INNER JOIN静默排除对不上的记录；LEFT JOIN全部保留、对不上填NULL |
| 找孤儿记录 | `LEFT JOIN + WHERE 右表字段 IS NULL` |
| 核心习惯 | 代码能跑出结果 ≠ 结果是对的——导出前，先COUNT；用了JOIN，还要核对JOIN前后总数是否一致 |

回顾一下这节课从头到尾都在验证同一件事：小李查"beijing"查出0条，没核对就直接发了；直接 `JOIN` 统计城市订单量，997比1000少了3条，不核对就发现不了。**代码能跑出结果，不代表结果是对的。导出前用COUNT核对数量、用JOIN核查关联完整性，这个习惯现在养成，以后做任何数据工作都用得上。**
