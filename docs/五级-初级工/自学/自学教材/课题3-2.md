## 写在前面

前面几个课题，你学的都是"怎么把一件事做对"——怎么采集数据、怎么清洗、怎么标注、怎么运维系统。这一课题要学的是另一件同样重要、但很容易被忽视的事：**怎么把你做过的事，写成一条别人看得懂、能据此采取行动的记录。**

这件事听起来简单，甚至有点"不像技术活"，但它恰恰是最容易被零基础学习者做砸的一环——不是因为不会写字,而是因为生活中说话的习惯和工作记录的要求是两回事。读完本篇，你会清楚知道两者的区别在哪里，以及怎么跨过这道坎。

---

## 学习目标

**知识目标**
1. 能说明运行记录的作用：问题可追溯、异常可复现、绩效可核查。
2. 能说出运行记录应覆盖的三项要素：功能使用情况、运行是否正常、异常现象描述。

**技能目标**
1. 能够记录智能系统功能应用情况。
2. 能够记录智能系统应用数据情况。
3. 能填写规范的运行/维护记录表。

**素养目标**
1. 异常描述要写现象，不写结论。

## 一、运行记录为什么存在

在往下读之前，先想一个问题，自己心里给个答案：

> **如果半年后，某条数据被发现有问题，你靠什么去查清楚当时到底发生了什么？**

答案就是——靠你当时留下的运行记录。如果当时什么都没记，半年后这件事基本就是"死无对证"，谁都说不清楚。这就是运行记录存在的全部意义，具体拆开看，它有三个作用：

- **问题可追溯**——记录写得清楚，半年后出问题照样能查到当时的具体操作和现象，不必凭记忆。
- **异常可复现**——好的记录能让排查的人按你写的步骤重新"演"一遍问题，而不是凭猜测排查。
- **绩效可核查**——记录也是统计每个人工作量、工作质量的客观依据。

对应地，一条规范的运行记录应该覆盖**三项要素**：

```
功能使用情况    运行是否正常    异常现象描述
```

也就是说：你用了什么功能、做了什么操作；这次运行是否正常；如果不正常，具体现象是什么。

**自测一下**：如果你今天的记录只写"我今天标注了数据"，这条记录够不够格？——不够，因为它漏掉了具体任务、具体数量、是否遇到异常这些信息，半年后看到这句话，谁都查不出当时发生了什么。合格的写法应该类似："今天用标注工具标注了XX任务50条文本，中途有一次保存失败，刷新页面后恢复正常。"——这才是三要素都覆盖到的记录雏形。你可以把这个例子当作本课题"合格记录"的参照标准。

## 二、核心原则：写现象，不写结论

这是本课题唯一、也是最重要的一条原则，也是五级考试里这一知识点的高频考点和易错点。

### 先做一次判断

在往下看之前，自己先回答这个问题：

> **如果你是负责排查问题的同事，收到"系统坏了"这四个字，你能做什么？**

记下你的答案，继续往下读，看看是否和下面的分析一致。

### 为什么"系统坏了"这种表述不合格

答案是：几乎什么都做不了。"系统坏了"这四个字没有告诉你：
- 是哪个功能坏了（登录？上传？提交？）
- 具体是什么现象（报错？卡住？没反应？）
- 什么时候发生的、能不能重现

**这就是"结论式表述"的致命问题：它把判断的工作替你做完了，却没有留下让你验证这个判断、或者重新排查的任何线索。** 换句话说，结论是作者自己"消化"过的二手产物，现象才是原始素材——排查问题需要的是原始素材，不是别人替你下的判断。

反过来，"描述现象"就是把这些原始的、具体的线索如实记下来，这样无论是你自己半年后回看，还是同事接手排查，都能据此定位问题、甚至重现问题。

### 正反对比示例

下面两组对比，建议先自己判断哪个合格、为什么，再往下看解析。

| 写法 | 判断 | 为什么 |
|---|---|---|
| "系统坏了" | ✗ 结论 | 不知道具体是什么问题、哪个功能、什么时候，无法排查 |
| "点击提交后页面提示500错误，重试3次均失败" | ✓ 现象 | 具体的操作、具体的错误码、具体的复现次数，看一眼就知道从哪里查起 |
| "数据不对" | ✗ 结论 | 不知道哪里不对、差多少，排查范围无从谈起 |
| "导出文件行数为980，预期应为1000，缺少20行" | ✓ 现象 | 具体数字对比，立刻能判断问题规模、能定位排查方向 |

### 一句话判别口诀

看完上面的例子，你可以提炼出一条随时能用的检验标准：

> **你写的这句话，能不能让一个完全没在场的人，看完就知道该从哪里查起？**
> 能——这是现象，合格；不能——这还是结论，要继续改写。

### 动手练一次改写

光看例子不够，试着自己把下面三句笼统表述改写成具体的现象描述（想好了再往下翻看练习部分的参考答案）：

1. "标注工具用不了"
2. "导出的数据有问题"
3. "网络连不上"

改写的关键始终是同一件事：补上**具体时间、具体操作、具体现象、是否可复现**这几项信息，而不是停留在一个笼统的判断词上。

## 三、两类记录对象：功能应用情况 vs 应用数据情况

"写现象不写结论"是总原则，但实际记录时，你会遇到两类不同性质的记录对象，容易混为一谈。弄清楚这两类的区别，才能让记录既分类清楚又不遗漏。

### 3.1 功能应用情况记录——记录"操作过程、功能好不好用"

**场景**：你今天上午用标注工具标注时，点击提交后页面卡住，刷新后恢复，卡顿约3分钟。请把这件事写成一条规范的运行记录。

规范记录应该包含的要素（也是记录模板）：

```
功能使用情况：……（什么时间、用了什么功能、做了什么操作）
运行是否正常：……
异常现象描述：……（如无异常，可直接写"无异常"）
```

套用上面的场景，一条合格的记录应该类似：

> "今日上午使用标注工具进行标注操作，点击'提交'按钮后页面无响应，持续约3分钟，刷新页面后恢复正常，未再次出现。"

写完之后，自己用这条检验标准过一遍：**如果这条记录半年后被别人看到，他能不能单凭这几句话判断问题出在提交环节还是网络环节？** 如果能，说明你写出了足够具体的时间点、复现方式，而不是用"刚才""今天"这种笼统时间，也不是直接写"卡顿"两个字代替对现象的描述。

### 3.2 应用数据情况记录——记录"数据本身的数量/状态"

这是另一类记录对象：它关心的不是"功能顺不顺手"，而是数据本身的量化状态对不对。

**场景**：你今天导出了一批标注任务的统计文件，系统显示导出文件行数为980行，但该批次预期应为1000行，缺少20行。请把这件事写成一条规范记录。

这里有一个关键判断："缺少20行"，应该写成"数据不对"，还是写成"980 对 1000，缺20行"？

答案很明确：一定是后者。"数据不对"这三个字不能告诉同事缺了多少、该从哪个范围开始查；而"980对1000，缺20行"这种**具体数字对比**，看一眼就知道问题有多大、该往哪个方向排查。一条合格的记录应该类似：

> "导出XX批次标注任务统计文件，实际导出980行，预期应为1000行，缺少20行，导出操作于XX月XX日XX时XX分执行。"

### 3.3 两类记录的共同点与区别

| | 功能应用情况记录 | 应用数据情况记录 |
|---|---|---|
| 记录对象 | 操作过程、功能是否好用 | 数据本身的数量/状态 |
| 本课例子 | 提交卡顿约3分钟 | 导出980行，预期1000行，缺20行 |
| 共同原则 | 都要写现象，不写结论 | 都要写现象，不写结论 |

记住这一点：两类记录**形式不同，但都要服从同一个总原则**——写现象，不写结论。实际工作中，不要把两类记录混在一句话里写不清楚（比如把"提交卡顿"和"行数差异"糅在一起），而应该分开、分别写清楚各自的具体现象。

## 四、常见不合格记录自查

下面是三类在实际工作中很容易出现的不合格记录，你可以把它们当作"错题本"，对照检查自己以后写记录时会不会踩同样的坑。

| 典型错误写法 | 问题诊断 |
|---|---|
| "今天标注遇到点问题，处理了" | 全篇都是结论，没有任何现象、时间、数字，排查者完全无从下手 |
| "导出数据少了" | 属于应用数据情况记录，但缺少具体数字对比（少了多少、预期是多少） |
| "提交卡顿，行数也对不上" | 把功能使用情况和应用数据情况混在一句话里说不清楚，应该分开各自写清楚 |

自查的时候，可以依次问自己三个问题：
1. 这条记录里有没有具体时间点？
2. 有没有具体现象（而不是一个笼统判断词）？
3. 如果涉及两类记录对象，是不是分开写清楚了，而不是混在一起？

三个问题都回答"是"，这条记录才算合格。

## 五、本课题与全课程的关系

学到这里，你已经学完了五级/初级工全部60个学时的内容。回头看这60个学时，无论是采集数据、处理数据，还是标注、审核、运维，贯穿始终的一条主线是：

> **按规范把事情做准、做细；遇到规范没覆盖的情况，记录上报，而不是自己凭感觉处理。**

本课题"写现象不写结论"，正是这条主线在最后一个环节上的体现——把你做的事、遇到的情况，如实、具体地记录下来，才能让别人（或未来的你）据此判断和处理，而不是凭一句笼统的结论蒙混过去。

这也是你们接下来四级要学的"审核与优化"、三级要学的"设计与诊断"的共同起点——没有扎实的"做"和"记录"的基础，审核和设计都无从谈起。

## 随堂练习（自测）

建议先自己完整作答，再看参考答案对照。

**练习 1**：把"标注工具用不了"这句话改写成一条规范的异常记录。

**答案**：示例："打开标注工具后点击'开始标注'按钮无响应，页面停留在加载界面超过2分钟，刷新页面后问题依旧，尝试时间为XX月XX日XX时XX分。"——关键是写出具体现象、复现方式和时间，而不是用"用不了"一句话概括。

**练习 2**：运行记录的三个核心要素是什么？

**答案**：功能使用情况、运行是否正常、异常现象描述。三者共同构成完整的运行记录，既要记录正常使用的情况，也要在出现异常时具体描述现象。

**练习 3**：为什么说运行记录有助于"问题可追溯、异常可复现"？

**答案**：规范的运行记录会写明具体的操作时间、现象和复现步骤，后续排查问题时可以依据这些记录定位问题发生的具体环节和条件，甚至按记录的步骤重新复现问题，而不需要凭记忆或猜测去排查，大大提高排查效率。

**练习 4**：把"数据导出有问题"改写成规范的异常记录，应该包含哪些具体信息？

**答案**：应包含具体的数字对比（如导出文件实际行数与预期行数的差异）、发生的具体操作步骤、尝试的时间。例如："导出XX任务数据，实际导出980行，预期应为1000行，缺少20行，导出操作于XX月XX日XX时XX分执行。"

**练习 5**："写现象不写结论"这个原则，除了运行记录，还能用在哪些场景？

**答案**：这个原则同样适用于向同事反馈问题、向上级汇报工作异常、甚至在标注质检中描述发现的问题等场景——任何需要让别人据此采取行动或做出判断的书面/口头表达，都应该优先给出具体可验证的现象描述，而不是笼统的结论性判断。
