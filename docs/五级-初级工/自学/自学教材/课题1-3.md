## 一、业务数据整理归类到底在解决什么问题

先搞清楚这个课题的定位：前面课题1-1、1-2讲的是怎么把数据"采集"进来（设备、数据库、SQL），数据到手之后，并不能直接拿去做统计分析——因为同一个业务含义，往往会被不同人、不同系统、不同时间录入成好几种不同的书写形式。如果不先把这些"写法不统一"的问题处理掉就直接汇总，算出来的数字会是错的，而且是那种**不报错、看起来运行得好好的、但结果已经严重失真**的错误。

这正是"整理归类"工作存在的意义：把同一个真实世界的事物，不管它被写成了几种形式，先统一成一种标准写法，再送去做后续统计。

业务数据里最常见的写法不统一，可以归成五类，我们先把这五类过一遍，再用代码验证它们是不是真的存在于这份销售数据里。

### 五类常见格式问题

| 问题类型 | 定义 | 业务后果 |
|---|---|---|
| 日期格式不统一 | 同一个字段里，日期用了不同的书写格式（如`2026-03-05`、`2026/3/5`、`03-05-2026`、`20260305`） | 程序无法把它们当成同一种"日期类型"统一排序、比较和计算，按日期筛选时会漏掉写法不同的记录 |
| 全半角混用 | 同样的字符用了全角和半角两种编码（如数字"1"和"１"） | 对程序而言这是两个完全不同的字符，字符串比较和数值转换都会失败 |
| 首尾空格 | 字段值前后多出看不见的空格（如"华东"和" 华东 "） | 肉眼完全看不出差异，但程序判断两者是不同的字符串，分组统计时会被当成不同类别 |
| 单位不一致 | 同一个数值字段，有的记录带单位后缀或千分位符号，有的没有（如"27986"和"27986元"、"143,984"） | 带文字或符号的数值无法直接参与数学运算，会被当成文本处理，汇总求和时报错或被跳过 |
| 大小写/同音异形混乱 | 同一含义的词使用了不同的字形写法（如"手机"/"手機"） | 程序按字符逐个比对，这是两个不同的字符串，会被分别统计，同一类商品的数据被人为拆散 |

这五类问题有一个共同特点，先记住这句话，后面会反复用到：

> **格式问题的共同特点：对人眼来说"差不多"，对程序来说"完全不同"。**

为什么会是这样？这是本节最容易被忽视、但必须想清楚的一点。人看"手机"和"手機"，会自动用"意思"去理解——两个字长得像、意思一样，大脑直接判定"这是同一个东西"，甚至根本不会注意到字形有差异。但计算机不理解"意思"，它只做一件事：**逐个字符比对编码是否完全相同**。"机"和"機"是两个不同的字符（繁简字形不同，对应不同的字符编码），哪怕含义相同，对程序来说就是两个不同的字符串，分组统计时会被分到两个不同的类别里，分别计数。首尾空格同理——"华东"和" 华东 "在显示出来的样子上几乎分辨不出差异，但多出来的空格字符会让整个字符串"不相等"，程序照样把它们当成两个不同的地区分别统计。

想一想：这五类问题里，哪一类最容易被漏掉？答案是——**越是"看起来像文字小瑕疵"的问题，越容易被当成无关紧要而忽视**，首尾空格和同音异形尤其如此，因为它们根本不会让人觉得"这条数据有错"，顶多觉得"这个字打得有点怪"，然后就翻过去了。这正是本课题要纠正的直觉误区。

## 二、用代码把"看起来没问题"的数据打回原形

光讲定义还是抽象的，现在把开头那份销售流水表打开，用代码把每个字段的真实写法情况跑出来，看看它到底"干不干净"。

```python
import pandas as pd
d = pd.read_csv("../数据集/sales_raw.csv")

print("商品类别取值:", d["商品类别"].value_counts().to_dict())
print("销售地区取值样例:", d["销售地区"].unique().tolist())
print("下单日期样例:", d["下单日期"].sample(8, random_state=1).tolist())
print("销售金额样例:", d["销售金额"].sample(8, random_state=1).tolist())
```

**实测结果（已验证，你在自己机器上运行应该得到完全一致的结果）**：

```

销售地区取值样例: ['华北', '华东', '东北', '西南', '  东北 ', '华南', '  华东 ', '  华南 ', ...]
```

现在回到开头的判断题：这份"字段齐全、排版工整"的数据，能不能直接按商品类别做汇总？答案已经很清楚了——**不能**。四个字段（商品类别、销售地区、下单日期、销售金额）全部存在格式问题，而这些问题你光靠眼睛扫一遍，几乎一个都看不出来。

## 三、重点难点：手机94/手機21/手机(空格)20 ——该不该合并、怎么合并

这是本课题最核心的一个知识点，也是最容易出两种相反错误的地方：要么漏合并（该合并的没合并），要么乱合并（不该合并的也合并了）。我们一步步拆开讲。

### 先搞清楚：不合并会有什么后果

"手机"94条，"手機"21条，"手机 "（带空格）20条——这三种写法实际描述的是同一个商品品类。如果不统一这些写法，后面按商品类别做汇总统计，程序会把它们当成**三个不同的类别**分别计数，报表上会显示"手机"卖了94台、"手機"卖了21台、"手机 "卖了20台，三条并列的记录，没有人会意识到这其实是同一个品类被拆开了。

这会带来什么问题？如果你是业务负责人，只看到报表上"手机"这一行写着94，你会怎么判断这个品类的真实销量？——你会严重低估它，因为真实销量其实是94+21+20=135，被人为拆成了三份，报表上最大的那个数字（94）只有真实数字（135）的约70%。**这正是归类整理工作的核心价值所在：看起来"差不多"的写法，背后可能是被严重低估的真实业务数据。**

### 统一写法的代码

```python
d["商品类别"] = d["商品类别"].str.strip()                    # 去除首尾空格
d["商品类别"] = d["商品类别"].replace({"手機": "手机"})       # 统一同义写法
print(d["商品类别"].value_counts())
```

**验证输出（已实测）**：

```
手机        135
耳机        104
笔记本电脑   96
平板         89
智能手表     84
```

合并之后，"手机"真实销量135的面貌才完整显现出来。对照一下合并前后的数字：

| | 手机 | 手機 | 手机（空格） | 合并后 |
|---|---|---|---|---|
| 条数 | 94 | 21 | 20 | 135 |

### 反过来想：是不是什么都能合并？

学会"同义写法要合并"之后，很容易矫枉过正，把本来就不一样的东西也强行合并。数据集里还有"平板"和"笔记本电脑"两个类别——都是电子产品，要不要也合并？

多数人第一反应会说"不要"，但往往说不清楚理由。这里需要一条清晰、可以套用到任何场景的判断标准：

> 🔑 **判别口诀：先问——这两条记录描述的是不是同一个真实世界的事物？**
> 是 → 合并（"手机"和"手機"说的是同一种商品，只是写法不同）；
> 不是 → 保留为不同类别（"平板"和"笔记本电脑"是两种真实不同的商品，写法清清楚楚，不存在"同义词"的问题，不能因为"都是电子产品"这种更上位的相似性就合并）。

记住这条口诀，它不仅适用于商品类别，适用于任何"要不要把两条记录当成同一类"的判断场景：**判断依据永远是"是不是同一个真实事物"，而不是"写法像不像""属不属于同一个大类"。**

## 四、把方法迁移到另外两个字段：销售地区与下单日期

商品类别处理完了，同样的思路要迁移到销售地区和下单日期这两个字段。

```python
# 销售地区：去除首尾空格
d["销售地区"] = d["销售地区"].str.strip()
print("处理后地区取值:", d["销售地区"].unique().tolist())

# 下单日期：统一转换为标准日期类型
d["下单日期"] = pd.to_datetime(d["下单日期"], errors="coerce")
print("处理后日期样例:", d["下单日期"].head(5).tolist())
print("转换失败（变为空值）的条数:", d["下单日期"].isna().sum())
```

运行之后，用`unique()`核对销售地区是否只剩标准的几个地区名（没有带空格的重复项）；核对下单日期转换后是否变成统一的日期类型，而且"转换失败条数"应为0——为0说明前面看到的四种格式，pandas全部识别成功，没有记录被丢失。

**一个容易漏掉的细节**：`pd.to_datetime()` 一定要带上 `errors="coerce"` 这个参数。如果不加这个参数，一旦遇到pandas识别不了的格式，代码会直接报错中断整个程序运行，而不是把这条记录标记成空值跳过——这意味着漏了这个参数，哪怕只有一条记录格式特殊，整个处理流程都会崩掉。加上之后，识别不了的记录会被转换成空值（`NaT`），程序继续往下跑，你再用`isna().sum()`去统计这类"确实无法识别"的记录有多少条即可。

## 五、变式练习：同样的陷阱换了个样子，藏在数字字段里

前面处理的"手机/手機"是文字字段的格式问题。现在看一个数值字段——**销售金额**，在正式揭晓答案之前，建议你先自己动手探查一下这个字段有没有问题、属于五类中的哪一类，这是检验你是否真正学会方法（而不是只记住了"手机"这一个具体案例）的最好方式。

**提示性探查代码（可以先运行这两行，自己判断再往下看）**：

```python
print(d["销售金额"].sample(10, random_state=2).tolist())
print("能直接转换为数字的条数:", pd.to_numeric(d["销售金额"], errors="coerce").notna().sum(), "/", len(d))
```

**实测结果（已验证）**：抽样会看到"27986"、"27986元"、"143,984"（带千分位逗号）、全角数字等多种写法混杂；**能直接转换为数字的只有 436/508 条**，其余 72 条因为带了"元"字、千分位逗号或全角数字，被当成普通文本，无法参与任何求和、求均值等数学运算。

### 想清楚一个问题：这和商品类别的问题是同一回事吗？

答案是——**本质完全一样**。商品类别的问题可以概括为"同一含义，多种文字写法"（手机/手機）；销售金额的问题可以概括为"同一数值，多种文本包装"（27986/27986元）。表面看一个是文字字段一个是数字字段，但根本原因完全相同：**写法不统一，程序没法把它们识别成同一类东西。**

对人眼来说"27986"和"27986元"显然说的是同一个数；但程序看到字符串里混进了汉字"元"，就不再把它当数字处理，而是当成一串普通文本。这里有一个比报错更危险的后果：**如果直接对这一列求和，带单位或逗号的记录会被悄悄跳过，求和结果偏小，而且程序不会报错提醒你**——你拿到一个看起来完全正常的数字，却不知道它已经是错的。这正是格式问题比语法错误更隐蔽、更需要主动排查的原因。

### 统一清洗代码

```python
def clean_amount(s):
    if pd.isna(s):
        return None
    s = str(s)
    s = s.translate(str.maketrans("０１２３４５６７８９", "0123456789"))  # 全角转半角
    s = s.replace(",", "").replace("元", "").strip()                      # 去千分位、去单位
    try:
        return float(s)
    except ValueError:
        return None

d["销售金额"] = d["销售金额"].apply(clean_amount)
print("清洗后能转换为数字的条数:", d["销售金额"].notna().sum(), "/", len(d))
```

**验证输出（已实测）**：

```
清洗后能转换为数字的条数: 495 / 508
```

### 区分清楚："格式问题"和"真的缺失"是两回事

清洗前436条能直接用，清洗后495条——多找回了59条本来就是正常数值、只是写法不规范的数据。但还剩13条仍然是空值（508-495=13），这13条**不是格式问题**，是**真正缺失的数据**，这类问题会在后续课题里专门处理（涉及缺失值填补、剔除等策略）。

> 📌 **一句话区分**：本课题的"整理归类"只负责把"能救回来"的格式问题统一好——即数据其实存在、只是写法不规范；它不负责补全真正没有的数据——即数据本身就是空的。把"格式不规范"和"数据真缺失"混为一谈，是零基础学员很容易踩的另一个坑：看到一条记录处理完还是空的，就以为是自己清洗代码写错了，其实那13条本来就没有值，清洗代码没有问题。

## 六、换一个工具再做一遍：Excel 操作对照

前面全部是用Python做的。如果你的实际工作环境里没有现成的Python环境，或者需要和不熟悉代码的同事协作，同样的整理归类任务也可以在Excel里完成，操作思路完全一致：

- 用"查找和替换"功能统一商品类别的写法——把"手機"替换成"手机"；注意"手机 "（带空格）这种情况用普通查找替换可能找不到，需要额外处理。
- 用 `=TRIM()` 函数去除销售地区等字段的首尾空格，生成一个辅助列，再核对结果。

动手做完之后，记得核对一下Python处理结果和Excel处理结果是否一致——比如"手机"合计应该是135条，两边对得上，才说明两种工具确实做的是同一件事，只是实现方式不同。

**一个容易忽略的坑**：Excel"查找替换"功能默认情况下不区分全角/半角、不一定能识别出首尾空格这类差异，直接肉眼核对很难发现替换有没有彻底生效，建议配合`=TRIM()`辅助列做二次核对，不要只看"替换成功"的提示就认为万事大吉。

## 七、一个你以后在工作中会反复遇到的场景：别人做了一半的"归类"

实际工作中，整理归类任务经常不是你一个人从头到尾做完，而是接手别人已经处理过一部分的数据，或者你自己处理完要交给别人检查。这里有两种最典型的"只做了一半"的遗漏，提前知道能帮你在这两个方向都养成检查习惯：

| 典型遗漏 | 会造成什么后果 |
|---|---|
| 只统一了商品类别，销售地区仍带空格 | 分组统计销售地区时，"华东"和" 华东 "会被当成两个不同地区，分别统计 |
| 销售金额没有清洗，直接对该列求和 | 带"元"字和逗号的记录会被当成文本跳过，求和结果偏小，而且**不会报错**，是四类遗漏里最隐蔽、最容易被忽略的一种 |

拿到一份"号称已经整理归类完"的数据，别只看处理的那个字段有没有处理好，而要把**全部**相关字段都重新用`value_counts()`/`unique()`/`notna().sum()`跑一遍，才能确认是不是真的"全部字段都处理完了"，而不是"只处理了最显眼的那一个"。

## 本课题知识地图回顾

整理一下这篇教材讲过的内容，串成一条线：

1. 业务数据整理归类要解决的问题：同一真实事物被写成多种不同形式，不统一就直接汇总，结果会严重失真、但不会报错。
2. 五类常见格式问题：日期格式不统一、全半角混用、首尾空格、单位不一致、大小写/同音异形混乱——共同特点是"人眼差不多、程序完全不同"。
3. 发现问题的方法：不能靠肉眼，要用`value_counts()`、`unique()`、`sample()`等代码逐字段跑出真实取值情况。
4. 统一写法的核心工具：`str.strip()`去空格、`replace()`统一同义写法、`pd.to_datetime(errors="coerce")`统一日期、自定义清洗函数处理数值单位问题。
5. 判断该不该合并的通用标准：**是不是同一个真实世界的事物**，而不是写法像不像、属不属于同一大类。
6. 格式问题 ≠ 数据真缺失：前者能救回来，后者需要其他方式处理，不要混为一谈。
7. 同一套思路可以在Python和Excel两种工具间迁移，核心是"发现问题→统一处理→验证结果"这个流程，不是记住某个具体函数。
8. 检查自己或别人的处理结果时，要把所有相关字段都重新验证一遍，而不是只看最显眼的那一个字段。

## 考点清单

| 考点 | 考试怎么考 | 易错点 |
|---|---|---|
| **同义不同写法识别** | 实操核心 | **只看表面"没有明显错误"，忽视细微的写法差异**（首尾空格、同音异形字） |
| 日期格式统一 | 实操 | 不统一格式直接做日期计算，导致排序/比较出错；忘记加`errors="coerce"`导致程序中断 |
| 合并判别标准 | 理论+实操 | 把"写法像/同属一个大类"当成合并依据，而不是"是否同一真实事物"（矫枉过正误合并） |
| 单位不一致处理 | 实操 | 直接对未清洗字段求和，结果偏小且不报错，比报错更危险 |
| 格式问题 vs 数据缺失 | 理论 | 把清洗后仍为空的记录误判为"清洗代码写错了" |

## 随堂练习（自测）

**练习 1**：某字段存在"北京""北京市""BEIJING"三种写法表示同一地区，该怎么处理？

**答案**：应先统一映射为同一个标准写法（如统一为"北京"），再进行后续的分组统计分析，否则同一地区的数据会被拆分成三个不同类别，导致统计结果失真。

**练习 2**：`str.strip()` 的作用是什么？为什么首尾空格问题容易被忽视？

**答案**：`str.strip()`用于去除字符串首尾的空格。首尾空格容易被忽视是因为肉眼从表格或打印输出里很难直接看出某个字符串末尾多了一个空格，但对程序来说"手机"和"手机 "是两个不同的字符串，会导致分组统计时被当成不同类别。

**练习 3**：下单日期字段同时存在`2026-03-05`、`2026/3/5`、`20260305`三种格式，该怎么统一处理？

**答案**：使用`pd.to_datetime()`函数，pandas能够自动识别多种常见的日期格式字符串并统一转换为标准的日期类型，转换后的日期可以直接进行排序、比较和日期计算，不会因为原始格式不同而出错。建议带上`errors="coerce"`参数，避免遇到无法识别的格式时程序直接报错中断。

**练习 4**：为什么"同一含义不同写法"的问题，仅凭肉眼检查很容易被漏掉？

**答案**：因为肉眼浏览数据时，"手机"和"手機"字形接近、含义相同，容易被当作"同一类"直接略过；而首尾空格这类问题在普通查看方式下几乎不可见。这类问题通常需要通过代码统计各取值的出现次数（如`value_counts()`）才能被系统性地发现。

**练习 5**：整理归类工作完成后，应该怎么验证处理结果是否正确？

**答案**：可以重新运行`value_counts()`等统计方法，检查同一含义的数据是否已经合并为统一的取值，取值种类数是否符合预期（比如原本8种门店编码写法应归并为4种）；也可以抽样检查几条处理前后的数据，确认转换逻辑没有引入新的错误。
