## 第一节：动手采集之前，有三件事必须先想清楚

### 先看一个真实案例

某位学员用手机采集了42张商品图片，用于后续的图像标注任务。他自己检查过：数量够了，也挨个点开看了一眼，觉得"挺清楚的，应该没问题"，就打包提交了。结果质检环节把这批数据打了回来，要求重拍其中几张、重新命名归档。

**先别往下看，花三十秒猜一猜：这批图片问题出在哪？大概有几张不合格？**

把猜测写下来——问题类型 ______，大概 ______ 张。记住这个数字，我们稍后用代码验证。

### 动手之前，老师先问你三个问题

在揭晓答案之前，老师要先带你回到更前面一步：**采集前有三件事，不想清楚就动手，后面全白干。是哪三件？**

1. **数据用途**——采集来做什么？
2. **授权范围**——是否有合法采集授权？
3. **采集口径**——字段定义、时间范围、抽样规则是否明确？

老师逐一追问"为什么必须排在动手之前，不能采集完再补"：

**先说用途。** 同样是拍商品图，用于电商详情页展示，和用于训练图像识别模型，对清晰度、背景干净程度的要求完全不一样。不先问清楚用途就开拍，拍回来才发现规格不对，往往要全部重拍或报废——返工成本远高于提前花一分钟确认。

**再说授权范围。** 如果拍门店场景拍到了顾客，没有明确授权就采集，轻则这批数据不能用，重则直接构成违规——这正是 01 篇讲的"标注员是数据安全链条上的一环"在采集环节的具体落地：**采集环节同样要先确认"能不能采"，不能等采完了再想**。

**最后说采集口径。** 比如任务是"采集100张商品图"，这个100张是每个品类都要覆盖，还是随便拍满就行？是只拍正面还是要多角度？口径不明确，采回来的样本结构很可能完全不满足后续需要——到那时再补拍，往往已经错过最佳条件（促销活动结束、商品下架）。

一句话记住：**想清楚"干什么用"，确认"能不能采"，定清楚"怎么算合格"——这三件事做在采集动作之前。**

### 揭晓答案：42张图片到底出了什么问题

现在用代码查一下（已验证，你跑出来的结果应该完全一致）：

```python
from PIL import Image
from pathlib import Path
import re

files = sorted(Path("../数据集/images").glob("*.jpg"))
sizes = {}
irregular_names = []
for p in files:
    img = Image.open(p)
    sizes.setdefault(img.size, []).append(p.name)
    if not re.match(r"^[a-z]+_\d{3}", p.name):
        irregular_names.append(p.name)

print("分辨率分布:", {k: len(v) for k, v in sizes.items()})
print("命名不规范文件:", irregular_names)
```

实测结果：分辨率分布 `{(640,480): 37, (320,240): 4, (1280,960): 1}`，命名不规范文件 `['IMG_3.jpg', '商品图片16.jpg', 'new photo 29.jpg']`。代码查出了5张分辨率不一致、3张命名不规范。

但老师会追问：**这份清单完整吗？** 还没完——这42张图里实际还有**4张严重模糊、3张过曝、2组完全重复**的图片，代码刚才一个都没查出来。

### 为什么代码查不出模糊和过曝

这不是代码写得不够好，而是两类问题性质不同：

- 分辨率、文件名、是否完全重复——这些是"能被精确计算"的东西，尺寸是两个数字，文件名是一串字符，重复可以逐字节比对，代码能稳定查出来。
- 模糊、过曝——"看起来模糊""看起来发白"是主观视觉判断，没有一行简单代码能给出和人眼完全一致的结论。

**代码能可靠查出客观可计算的问题，但主观视觉质量问题，现阶段最可靠的办法仍然是人当场看一眼。** 这就是为什么"采集质量当场自检"不是"跑完代码就能替代"的步骤，而是必须有人眼参与的独立检查环节。

完整答案揭晓：这42张图片有**5张分辨率不一致、4张模糊、3张过曝、3张命名不规范，外加2组完全重复**。回头看你一开始的猜测——多数人往往只注意到"分辨率不一样"这种一眼能看出的问题，而漏掉命名、重复这类需要专门检查才能发现的问题。

### 当场自检清单与三类问题的区分

- [ ] 分辨率是否符合要求
- [ ] 是否清晰（无模糊、无过曝）
- [ ] 命名是否规范
- [ ] 有无重复采集

| | 分辨率不一致 | 模糊 | 过曝 |
|---|---|---|---|
| 现象 | 同批图像尺寸不同 | 细节看不清 | 画面接近全白 |
| 常见成因 | 设备/模式切换未统一 | 低分辨率放大、对焦失败 | 光线过强或曝光不当 |
| 能否代码检测 | 能 | 较难，建议人工目测 | 较难，建议人工目测 |
| 修复方式 | 统一规格重拍 | 当场重拍 | 调整光线后重拍 |

判别口诀：先问"尺寸对不对"（代码能查）→ 再问"看得清不清、亮不亮"（人眼当场查）。

### 为什么"当场自检"比"事后处理"省那么多成本

想象一下：如果这4张模糊、3张过曝的图片是你拍的，当场拍完立刻回看一眼发现模糊，**当场重拍**——成本几乎为零，光线、角度、商品摆放都还在。但如果拍完没检查直接打包上传，几天后质检才告诉你不合格——这时候你可能已经离开拍摄现场，光线变了、商品甚至已经下架，**根本没法重新拍出一模一样的内容**。

**核心习惯**：采集质量问题最大的代价不是"要重做"，而是很多时候"根本没法重做"。这正是开头那位学员踩的坑——他"看了一眼"，但看的是"内容对不对"，而不是对照系统的自检清单逐项检查。

### 换一种数据类型，这条原则还成立吗

不是所有采集任务都是拍照片。换成录制客服通话音频、导出系统日志，"当场自检"查什么？

| 采集类型 | 对应质量问题 | 识别方式 |
|---|---|---|
| 图像 | 模糊、过曝、分辨率不一致 | 人工目测 + 代码查规格 |
| 音频 | 底噪过大、截断 | 当场回放试听 |
| 日志 | 字段缺失 | 当场抽样核对字段是否齐全 |

表现形式完全不同，但背后是同一个原则：不管采集什么类型的数据，"当场自检、当场重采"这个工作习惯是通用的——**变的只是检查清单的具体内容，不变的是"不等上传之后才发现问题"这条原则。**

## 第二节：数据不在表格里，而在数据库里，该怎么采

### 从"点开看一眼"切换到"写查询"

设备采集面对的是图片、音频这类文件；数据库采集面对的是存在系统里的结构化数据，要用 SQL 查询把你需要的那部分"捞"出来：

```sql
SELECT 字段 FROM 表名 WHERE 条件 ORDER BY 字段 LIMIT 数量;
SELECT 字段, COUNT(*) FROM 表名 GROUP BY 字段;
```

### 一个关于"导出前核对"的真实案例

某练习库 `practice.db` 有 users（用户）、products（商品）、orders（订单）三张表。老师带你跑三条查询：

```python
import sqlite3, pandas as pd
conn = sqlite3.connect("../数据集/practice.db")

q2 = "SELECT status, COUNT(*) FROM orders GROUP BY status"
print(pd.read_sql(q2, conn))

q3 = """SELECT o.order_id FROM orders o
        LEFT JOIN users u ON o.user_id = u.user_id
        WHERE u.user_id IS NULL"""
print(pd.read_sql(q3, conn))
```

实测：订单共1000条，completed 790、cancelled 125、pending 85。用 `LEFT JOIN` 核查发现：**订单998、999、1000** 对应的 `user_id` 在users表里根本不存在——这是"孤儿订单"，属于脏数据。

老师追问：**如果业务需求是"统计各城市真实有效用户的订单量"，直接导出全部1000条订单会发生什么？**

这3条孤儿订单会混入统计，导致城市归属无法匹配或统计口径出错。**核心习惯**：导出前先用 `COUNT` 核对数量是否符合预期，再用 `JOIN` 核查关联字段的完整性，这是避免"少导一半数据还没发现"或"多算了无效数据"的关键习惯。

### 怎么系统地找出所有"孤儿记录"

`LEFT JOIN` + `WHERE 右表字段 IS NULL` 是查找"左表有、右表无对应记录"的标准写法——左表（orders）全部保留，关联不上右表（users）的那些行，右表字段就会是空（NULL），用 `WHERE ... IS NULL` 把它们筛出来，在业务数据采集中非常实用，可以推广到任何"检查两张表关联完整性"的场景（比如订单表的 `product_id` 是否都能在商品表里找到）。
