## 一、数据库是什么：表、字段、记录、主键

在学"怎么查"之前，先搞清楚到底在查什么。本课题用的数据库 `practice.db` 里有三张表：`users`（用户）、`products`（商品）、`orders`（订单）。

| 概念 | 含义 | 本课题例子 |
|---|---|---|
| 表（table） | 存放同一类事物信息的集合，像一张Excel表 | `users` 表存所有用户信息 |
| 字段（column） | 表里的一列，描述事物的某一个属性 | `users` 表有 `user_id`、`user_name`、`city`、`register_date` 四个字段 |
| 记录（row） | 表里的一行，代表一个具体的"个体" | 一条记录就是一个具体用户的信息 |
| 主键（primary key） | 能**唯一标识**一条记录、不允许重复的字段 | `users.user_id`、`orders.order_id`、`products.product_id` |

**为什么一定要有主键？**

如果没有一个"身份证号"一样的字段，两条记录就算所有其他信息都长得一模一样，你也没办法准确判断"这是同一个人"还是"碰巧两条记录一样的人"。主键就是用来解决这个问题的——保证表里每一条记录都有独一无二的编号。**一旦发现主键重复，基本可以断定这批数据存在严重的质量问题**，这个信号比任何单独一个字段的异常都更该引起警觉。

**三张表是怎么联系在一起的？**

再看一眼 `orders` 表，它有一个 `user_id` 字段，这个字段里存的编号，理论上应该能在 `users` 表里找到对应的那一条用户记录；同理，`orders.product_id` 也应该能在 `products` 表里找到对应商品。**两张表正是靠这种"字段对字段"的方式关联起来的**——这句话先记住，第五节讲 `JOIN` 的时候会用到它。

## 二、基础SQL语法：从"挑数据"到"排序限量"

SQL查询最常用的骨架就这一句：

```sql
SELECT 字段 FROM 表名 WHERE 条件 ORDER BY 字段 LIMIT 数量;
```

- **SELECT 字段**——你想要哪些字段，想要全部就写 `*`。
- **FROM 表名**——从哪张表里找。
- **WHERE 条件**——筛选条件，不写就是不筛选、要全部记录。
- **ORDER BY 字段**——按哪个字段排序，默认从小到大，加 `DESC` 就是从大到小。
- **LIMIT 数量**——只要前几条，常用来"先看几条结果，别一下子查全表"。

> ⚠️ **零基础最容易踩的坑**：`WHERE` 条件里，**文字要用英文单引号包起来，数字不用**。
>
> 查城市是"北京"的用户要写 `WHERE city='北京'`，引号不能丢；查价格大于5000的商品要写 `WHERE price>5000`，绝不能写成 `WHERE price>'5000'`。记混了，查询不一定报错，但结果可能悄悄不对。
>
> 这也是开头小李踩的坑的另一半：他引号倒是加对了，**但把中文"北京"错写成了拼音"beijing"**，数据库里存的是中文，拼音永远匹配不上，查出来自然是0条。

### 回到开头那个判断

**小李的做法有没有问题？**

问题不在于"查出来是0条"这件事本身，而在于**看到0条这个结果，他完全没有停下来想一想"一个大城市的用户数是0，正常吗"**。0条和"全表记录数"一样，都是需要你多问一句"为什么"的信号，不是看到一个数字就能直接收工导出的。

### 动手验证

```python
import sqlite3, pandas as pd
conn = sqlite3.connect("../数据集/practice.db")

q1 = "SELECT * FROM users WHERE city='北京'"
print("北京用户数：", len(pd.read_sql(q1, conn)))

q2 = "SELECT * FROM products WHERE price>5000"
print("价格超过5000元的商品数：", len(pd.read_sql(q2, conn)))

q3 = "SELECT user_id, user_name, register_date FROM users ORDER BY register_date DESC LIMIT 5"
print(pd.read_sql(q3, conn))
```

**实测结果（已验证，你的结果应与此完全一致）**：

```
北京用户数： 30
价格超过5000元的商品数： 24
```

## 三、GROUP BY 与 COUNT：按组统计

前面查的都是"挑出符合条件的记录"。但实际工作中更常见的需求是"按类别数一数各有多少"——比如"各城市分别有多少用户"。这就要用到 `GROUP BY`：

```sql
SELECT 分组字段, COUNT(*) FROM 表名 GROUP BY 分组字段;
```

**原理**：`GROUP BY city` 做的事情是把所有记录按 `city` 字段的取值分成一堆堆——所有"北京"分一堆，所有"上海"分一堆……`COUNT(*)` 再数每一堆里有多少条记录。

```python
q = "SELECT city, COUNT(*) as cnt FROM users GROUP BY city ORDER BY cnt DESC"
print(pd.read_sql(q, conn))
```

**实测结果（已验证）**：

```
城市    cnt
成都    39
广州    36
深圳    34
杭州    33
北京    30
上海    28
```

**互相印证**：第二节查出的"北京用户数=30"，正好对得上这张表里北京那一行的30。**这正是聚合查询的一个额外好处——它能让你用一条查询同时核对多个筛选条件算出来的结果，是检查自己有没有写错查询的好工具。**

`GROUP BY` 不是只能配 `COUNT`，它是一个"分组之后统一加工"的通用工具，配合 `AVG()` 就能按组算平均值：

```python
q = "SELECT category, ROUND(AVG(price),1) as avg_price, COUNT(*) as cnt FROM products GROUP BY category ORDER BY avg_price DESC"
print(pd.read_sql(q, conn))
```

**实测结果（已验证）**：

```
category    avg_price  cnt
手机        6221.2     9
耳机        5499.0     8
笔记本电脑   4856.1     14
智能手表     4665.7     12
平板        3856.1     7
```

## 四、一个关于"导出前核对"的真实案例

`orders` 表里，总共有 **1000条** 订单记录。如果要统计"各城市的订单量"，需要把 `orders` 和 `users` 两张表拼接起来（订单本身不含城市信息，城市信息在用户表里）：

```python
q = """SELECT u.city, COUNT(*) as cnt FROM orders o
        JOIN users u ON o.user_id = u.user_id
        GROUP BY u.city ORDER BY cnt DESC"""
print(pd.read_sql(q, conn))
```

**实测结果（已验证）**：

```
深圳 193   成都 188   广州 173   北京 170   杭州 146   上海 127
```

把六个城市的数字加起来：193+188+173+170+146+127 = **997**。

> ⚠️ **订单表总数是1000条，按城市统计出来的订单量加起来却只有997条，少的这3条去哪了？**

### 为什么？——必须说出机制

这是本课题最该记住的一课，而很多人只看到"数字对不上"，却停在这一步，不往下追问。

**❌ 只发现"997≠1000"却不去查原因**——这等于发现了异常信号却没有处理，和没发现一样危险。

**✅ 完整的排查思路是两步**：

第一步，用 `LEFT JOIN` + `WHERE 右表字段 IS NULL` 找出具体是哪些记录出了问题（方法见下一节）；

第二步，查出原因：

```python
q = """SELECT o.order_id, o.user_id FROM orders o
        LEFT JOIN users u ON o.user_id = u.user_id
        WHERE u.user_id IS NULL"""
print(pd.read_sql(q, conn))
```

**实测结果（已验证）**：

```
order_id  user_id
998       9001
999       9002
1000      9003
```

`users` 表里一共只有200个用户（`user_id` 从1到200），但订单998、999、1000的 `user_id` 分别是9001、9002、9003——**这些编号在 `users` 表里根本不存在**。这种"左表有记录、右表找不到对应记录"的数据，叫**孤儿记录**（这里具体是"孤儿订单"）。

**机制**：前面用的 `JOIN`（默认即 `INNER JOIN`）只保留两张表都能对上的记录，对不上的那些**会被静默排除，不会有任何报错提示**——程序正常跑完，看起来一切正常，但数据已经悄悄少了3条。这就是为什么"按城市统计的订单量加起来是997，不是1000"。

**结论**：如果你没有核对JOIN前后的总数，直接把997条的统计结果当成"全部订单的城市分布"交付出去，统计口径本身就是错的，而你完全不会意识到问题存在。

## 五、JOIN 与孤儿记录排查方法

`JOIN` 最常用的有两种，处理"两表对不上"的记录时，结果完全不同：

| | INNER JOIN | LEFT JOIN |
|---|---|---|
| 结果范围 | 只保留两表都能对上的记录 | 左表全部保留，右表对不上则填 `NULL` |
| 对不上的记录 | **被静默排除**，不会提示 | **被保留**，右表字段显示为空 |
| 能否用来找孤儿记录 | 不能（问题记录已经被排除了） | **能**（配合 `WHERE 右表字段 IS NULL`） |

```sql
SELECT ... FROM A JOIN B ON A.字段=B.字段;           -- 等价于 INNER JOIN
SELECT ... FROM A LEFT JOIN B ON A.字段=B.字段;      -- LEFT JOIN，对不上也保留
```

> 🔑 **判别口诀**：要"两边都有的"数据 → 用 `INNER JOIN`；要"左边一个不漏，顺便揪出查无此人的" → 用 `LEFT JOIN`。

**找孤儿记录的标准写法**：`LEFT JOIN` 既然会把对不上的记录也保留、只是右边填 `NULL`，那只要再加一个条件——**筛选出右表字段是 `NULL` 的那些记录**——就能精准找出异常数据：

```sql
LEFT JOIN + WHERE 右表字段 IS NULL  →  专门用来找"查无此人"的孤儿记录
```

### 没查出问题，也要写进报告

用同样的方法查一下 `orders.product_id` 是否都能在 `products` 表里找到对应商品：

```python
q = """SELECT o.order_id FROM orders o
        LEFT JOIN products p ON o.product_id = p.product_id
        WHERE p.product_id IS NULL"""
print(pd.read_sql(q, conn))
```

**实测结果（已验证）**：**空结果，没有一条孤儿记录**——商品这边的关联是干净的。

这说明：排查的意义不是"非要挑出毛病"，而是把该查的关联字段都系统地查一遍。**用户这边查出3条孤儿订单，商品这边没查出问题，两者都要写进交付说明里**，不能因为"顺手查了一下没发现问题"就连这一步检查本身都略过不提——"没问题"也是一条需要确认和记录的结论，不是默认状态。

## 六、业务需求怎么翻译成SQL查询

实际工作中，业务方不会直接给你SQL，他们只会说一句中文需求，比如："帮我查一下北京地区最近一个月的订单量。"这句话要翻译成SQL，需要先拆成几个要素：

```
① 要查哪张表？要不要关联别的表？      —— 订单在orders，但"北京地区"是users表里的字段，要JOIN
② 筛选条件对应哪个字段？具体筛选值是什么？ —— city='北京'
③ "最近一个月"怎么界定？              —— 需要一个基准日期，再往前推时间范围
④ 最终要的是明细还是统计数量？         —— "订单量"是数量，要用COUNT
```

> 💡 第③步最容易被轻视。"最近一个月"或"近30天"看起来很明确，其实藏着一个问题：**是自然月，还是从某一天往前滚动30天？算不算当天？** 这种边界说不清楚，你和业务方对出来的数字可能完全不一样。拿不准时要主动问清楚，而不是自己猜一个定义就开始写查询。

### 一次完整的演示

数据集里订单的最新日期是2026-03-31，这里把"近30天"定义为2026-03-01至2026-03-31这个区间（共31天，按自然日近似处理）。查询"北京地区近30天的订单量"：

```python
q = """SELECT COUNT(*) as cnt FROM orders o
        JOIN users u ON o.user_id = u.user_id
        WHERE u.city = '北京' AND o.order_date >= '2026-03-01'"""
print(pd.read_sql(q, conn))
```

**实测结果（已验证）**：`cnt： 59`

**顺带想一下**：这条查询用的是普通 `JOIN`（即 `INNER JOIN`），前面说过它会悄悄排除孤儿订单，这里有没有影响？——998/999/1000号孤儿订单的下单日期都在1月，本来就不在"近30天"这个范围内，所以这次结果没受影响。**但这只是巧合，不代表下次用INNER JOIN统计时孤儿记录依然恰好落在筛选范围之外**。这正是为什么"核对总数"要成为固定动作，而不是只在"感觉可能有问题"的时候才做。

## 随堂练习

**练习 1**：某订单表中有部分订单的product_id在商品表中找不到对应记录，该用什么SQL方式排查？

<details><summary>答案</summary>使用LEFT JOIN以订单表为主表关联商品表，再用WHERE子句筛选商品表对应字段为NULL的记录，即可找出所有product_id无效的"孤儿"订单。</details>

**练习 2**：`SELECT city, COUNT(*) FROM users GROUP BY city` 这条SQL语句的作用是什么？

<details><summary>答案</summary>按城市分组，统计每个城市的用户数量。GROUP BY把数据按city字段的取值分组，COUNT(*)统计每组内的记录条数。</details>

**练习 3**：导出查询结果前，为什么要先用COUNT核对数量？

<details><summary>答案</summary>因为写错查询条件（比如WHERE条件写漏、JOIN关联字段用错）很容易导致导出的数据比预期少或者多，而这种错误从导出的文件本身不容易直接看出来。先用COUNT核对数量是否符合预期，能及时发现查询逻辑上的问题，避免把错误的数据交付出去。</details>

**练习 4**：主键的作用是什么？

<details><summary>答案</summary>主键用于唯一标识表中的每一条记录，确保不会出现完全相同标识的两条记录。主键重复或冲突通常意味着数据存在严重的质量问题。</details>

**练习 5**：业务需求"查询北京地区近30天的订单"，翻译成SQL查询时要确定哪些要素？

<details><summary>答案</summary>需要确定：筛选条件对应的字段名（地区字段、下单日期字段）、具体的筛选值（"北京"）、时间范围的计算方式（近30天如何界定，是否需要用当前日期减去30天）。把业务语言准确翻译成字段名和筛选条件，是写对SQL查询的关键一步。</details>
