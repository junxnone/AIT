# 教案 · 课题 3-1：智能系统基础操作

| 项目 | 内容 |
|---|---|
| 所属等级 | 五级 / 初级工 |
| 对应国标 | 职业功能3 智能系统运维 · 3.1 智能系统基础操作 |
| 学时 | **4 学时**（理论 2 + 实操 2，共 240 min） |
| 授课类型 | 理论与实操一体化 |
| 教学场地 | 计算机机房 |
| 教学系统 | 教学用标注/审核实训系统（或模拟操作环境），需能演示"测试环境/生产环境"标识 |

---

## 一、教学目标

### 知识目标
1. 能说明智能系统的基本组成与常见界面功能分区。

### 技能目标
1. **能够进行智能系统开启**：登录、权限确认、环境与服务状态检查。
2. **能够简单使用智能系统**：数据导入导出、任务创建与领取、提交与保存、结果查看。
3. 能识别常见操作异常并按流程上报。

### 素养目标
1. **操作前确认当前处于哪个环境**（测试/生产），避免误操作真实数据。

---

## 二、教学重点与难点

**重点**：操作前确认环境（测试vs生产）的习惯养成。

**难点**：零基础学员对"测试环境"和"生产环境"的区别缺乏概念，容易在不确认环境的情况下直接操作，一旦误操作生产环境数据后果严重。

---

## 三、学情分析与前置知识

**前置知识**：课题2-5（标注后数据分类与统计）。

**学情判断**：本课题进入模块三"智能系统运维"，是学员从"处理数据"转向"操作系统"的第一课。此前的课题学员已经熟悉了数据本身——怎么清洗、怎么标注、怎么分类统计，但对"系统"这个载体——登录、权限、不同环境——基本没有概念。尤其"测试环境"和"生产环境"的区别，对零基础学员而言是全新概念，抽象讲规则容易左耳进右耳出，必须结合具体的误操作后果场景，才能让学员真正建立起"操作前先看一眼"的警觉，而不是仅仅记住一条规则。

---

## 四、教学方法与手段

| 方法 | 说明 |
|---|---|
| **风险警示法**（核心） | 用具体的误操作后果场景建立安全意识，而非单纯讲规则——先让学员代入判断，再用机制解释推翻或印证直觉 |
| **异常场景演练法** | 模拟真实的操作异常（登录失败、上传失败、任务无法提交），训练应急上报流程，不满足于"知道要上报"，要练到"知道该怎么报、报什么" |

### 环节一：导入——一次误操作引发的判断（0–10′）

**教师讲述（不给结论）**：

> "小李是刚入职一周的标注员。这天他打开系统，想清理一批自己前几天建来练手的测试数据。页面上列着一堆任务，看着都眼熟，他心想'这些都是我这几天自己建的测试任务'，于是勾选全部，点击了'删除'。几秒后，带班的同事路过，看了一眼屏幕脸色就变了——**这个页面其实是生产环境，里面是当天刚提交、还没来得及审核的真实任务。**"

**提问话术**：

> "如果是你，在点击'删除'之前，本来应该先做哪一步？花三十秒写下你的判断，先别说出来。"

**预期学员反应与教师应对**：

| 学员反应 | 教师应对 |
|---|---|
| "应该先确认这是测试环境还是生产环境" | 肯定但不展开："这个方向是对的，具体为什么关键、怎么做到，我们稍后详细讲。" |
| "应该再检查一遍勾选的内容对不对" | 部分肯定："仔细核对是好习惯，但光核对'选没选错任务'还不够——还有一个更前置的问题，我们等会儿揭晓。" |
| 答不上来 / 没想到 | 不急于纠正："没关系，记住这个故事，三十分钟后我们回来详细拆解。" |

**设计意图**：不立即给出答案，让学员先公开表达自己的判断，为"环境确认习惯"难点突破环节积累代入感和认知落差。

---

### 环节二：新授——系统组成与界面功能分区（10–35′）

**讲授脚本**：

> "接下来三节课我们都会围绕'操作系统'展开。先打好基础：一个典型的智能标注/审核类系统，界面上通常分这几块。"

**投影逐项演示**：

- **登录入口**：账号/工号登录
- **环境标识区**：页面角落标明"测试环境"或"生产环境"（重点提示："记住这个位置，这节课后半段的核心内容就围绕它展开"）
- **任务列表区**：展示待领取/已领取/已完成任务
- **工作区（操作台）**：具体标注/审核/处理界面
- **提交/保存按钮区**
- **个人中心/消息通知区**：显示任务状态变化、系统公告

**学员活动**：在自己机器上逐一找到对应区域，口头说出每个分区的名字和作用（提问2-3人）。

**设计意图**：不直接灌输定义，让学员边看边找边说，建立空间感和操作熟悉度，同时为环境标识区埋下后续伏笔。

---

### 环节三：新授——系统开启流程三步骤及其意义（35–55′）

**讲授脚本**：

> "系统开启的正确流程是：**登录 → 权限确认 → 环境与服务状态检查**。这三步听起来像走个过场，但各自在确认不同的事——"
>
> "**登录**，确认'你是谁'，身份核实，系统才知道该给你分配什么任务、记录在谁名下。
>
> **权限确认**，确认'你能做什么'，不同岗位能看到、能操作的功能范围不一样。跳过这一步，你可能在系统里摸索半天，尝试一个自己本就没权限做的操作，不仅做不成，还可能把流程卡在一个错误的状态上。
>
> **环境与服务状态检查**，确认'现在能不能正常操作'——网络是否正常、服务是否就绪、当前打开的是哪个环境。跳过这一步最直接的后果是：在服务异常的情况下硬着头皮操作，轻则提交失败、任务卡住，重则数据没有完整同步就被当成'已完成'。"

**正反对比（板书）**：

| | 跳过检查直接操作 | 先完整走完三步骤 |
|---|---|---|
| 权限相关风险 | 可能尝试越权操作，被拒绝甚至引发误操作 | 清楚自己能做什么，少走弯路 |
| 环境/服务相关风险 | 可能在异常状态下提交，数据丢失或任务卡住 | 确认服务正常后再操作，减少返工 |

**板书核心句**：

> **三步骤加起来不过十几秒，省掉任何一步，后面要花的排查和返工时间往往是几十倍。**

**学员活动**：在自己机器上实际走一遍这三步骤，口头说出每一步在确认什么（提问2-3人）。

### 环节五：强调——环境确认习惯（难点突破核心，65–95′）

**回扣导入**：

> "现在回到小李的故事。谁愿意说一下，他漏掉的那一步是什么？"

（引导学员答出"看环境标识"，呼应环节一的判断）

**教师提问**：

> "如果你现在要删除一批测试数据，但不确定当前打开的是测试环境还是生产环境，你会怎么做？"

**预期学员反应与教师应对**：

| 学员反应 | 教师应对 |
|---|---|
| "先删了看看，不对再恢复" | 严肃纠正："**生产环境的数据往往无法简单恢复。** 这批数据可能已经和其他同事的工作、后续的审核或统计流程相互关联，一旦误删，不只是'能不能恢复'的技术问题，恢复期间这批数据相关的工作全部停摆，已经造成的下游影响也不会自动撤销。你说的'不对再恢复'这个想法本身就很危险。" |
| "反正删错了联系管理员恢复就行" | 追问："你怎么知道一定能完全恢复？恢复不是瞬间完成的，这段时间里，依赖这批数据的其他工作怎么办？谁来承担这段空窗期的影响？" |
| "先确认环境标识再操作" | 肯定："对，这才是正确的习惯。" |

**机制讲解——为什么两者后果完全不一样**：

> "很多系统在界面上都会有一个小标识告诉你现在是'测试环境'还是'生产环境'。**每次打开系统做任何操作前，先看一眼这个标识。**
>
> **测试环境**：数据是人为模拟、专门用来练习和验证功能的，清空重建不影响任何真实业务——这就是为什么课堂上教你可以大胆练习。
>
> **生产环境**：数据是真实业务和真实用户产生的，而且往往已经和其他环节相互关联。误删、误改之后，不是简单点个'恢复'就能解决的。"

**正反对比表（学员填写）**：

| | 测试环境误操作 | 生产环境误操作 |
|---|---|---|
| 数据性质 | 人为模拟，可重建 | 真实业务 / 用户数据 |
| 恢复难度 | 容易，重置重来即可 | 困难，可能无法完全恢复 |
| 影响范围 | 仅限自己的练习 | 可能牵连同事、下游流程、真实用户 |
| 需要承担的后果 | 几乎没有 | 需要上报、排查，可能要承担责任 |

**板书判别口诀**：

> **操作前先问自己一句：这批数据，删了/改了之后，能不能简单地"重来一次"？**
> **能 → 大概率是测试环境，大胆练；不能 → 当它是生产环境，先确认标识再动手。**

**教师总结话术（回扣主线）**：

> "现在回答开头小李的问题。他本该做的，就是点删除之前，花三秒钟看一眼页面角落的环境标识。这个习惯养成了，能避免你职业生涯里最可能踩的一个大坑；没养成，代价往往不是一句'下次注意'就能翻篇的。"

### 环节六：新授——基础使用操作四环节（95–120′）

**讲授脚本**：

> "开启系统之后，日常最常用的是四个环节：数据导入导出、任务创建与领取、提交与保存、结果查看。每一个都有它存在的意义，也都有最容易踩的坑。"

**逐项讲解**：

- **数据导入导出**——系统和外部数据之间的桥梁。导入前不核对文件格式、字段是否匹配模板，轻则直接报错（还算幸运），重则系统"接受"了这份数据但字段错位，表面看不出异常，等后面任务展示或统计时才暴露问题。
- **任务创建与领取**——"领取"的意义是把一份工作正式认领到你名下。常见错误：看到任务直接开始做，忘了点"领取"，结果系统里这份工作一直显示"未领取"，统计不到工作量，还可能被别的同事同时处理造成冲突。
- **提交与保存**——最容易混淆的一对动作（板书判别口诀）：
  > **保存是"存起来给自己看"，提交是"交出去给别人看"。点了保存 ≠ 点了提交。**
  > 保存只是把内容留在本地/草稿状态，还能随时修改；提交才代表工作成果正式交付、进入下一个环节（如审核）。
- **结果查看**——提交之后别就不管了，及时查看结果状态（待审核/已通过/被打回），被打回的说明通常会写原因，越早看越不会拖慢整批任务进度。

**学员活动**：记录四环节及各自的判别口诀，针对"保存与提交的区别"互相提问确认。

---

### 环节七：实操一——基础操作综合练习（120–200′）

**任务书（投影+讲义附）**：

> "请在教学系统（或模拟环境）中，按顺序完成以下操作并记录操作日志：
> ① 操作前，先确认当前环境标识；
> ② 导入一份样例数据；
> ③ 创建并领取一个标注任务；
> ④ 完成标注动作后先点保存，查看任务状态；
> ⑤ 点击提交，再次查看任务状态有什么不同；
> ⑥ 在个人中心/结果查看区确认提交结果。"

**巡回指导要点**：

- 检查学员是否在动手前先确认了环境标识（把难点习惯落到实操里巩固，而不只是口头说说）
- 检查是否混淆"保存"与"提交"——这是本环节最常见的操作性错误
- 检查任务是否完整走完"领取"这一步，而不是直接开始操作

**对完成快的学员追问**：

> "如果提交后发现任务被系统打回，你接下来会怎么做？"（引导思考，铺垫环节八的异常处理）

**学员活动**：独立完成六步骤操作，填写操作日志（时间点、每步操作结果）。

---

### 环节八：实操二——异常场景演练（200–230′）

**教师活动**：设置三个场景（登录失败、上传失败、任务无法提交），逐一演示/模拟，组织学员跟练应急上报流程。

**预期学员反应与教师应对**：

| 学员反应 | 教师应对 |
|---|---|
| "多试几次总能成功" | 追问："如果试了5次、10次还不行呢？反复操作本身会不会有风险——比如重复提交导致数据重复？正确做法是先确认环境/网络，仍不行就按流程上报，而不是无限重试。" |
| "先放着，去做别的任务" | 纠正："异常不处理，意味着这部分工作没有真正完成，别人也不知道卡在了哪里。该上报的要第一时间上报，不是放着不管。" |
| "确认是网络问题，合理等待重试，并记录" | 肯定："这是比较合理的做法——先排除简单原因、给出合理的重试次数，仍不行就上报，并且把这次异常记录下来。" |

**教师总结（对接实操真题逻辑）**：

> "这正是实操考核里的真实考法：先确认环境/服务状态是否正常，重试2-3次仍失败就按流程上报，而不是自己反复硬扛。即便后来自己恢复了，这次异常也要如实记录——下一课题'运行记录'会专门训练这个能力。"

**学员活动**：对三个场景分别练习一次完整的"确认→重试→上报"话术与操作。

---

### 环节九：小结与作业（230–240′）

**知识回顾**（请学员口述，教师补全）：

1. 系统开启的三步骤分别在确认什么？
2. 为什么生产环境误操作的后果和测试环境完全不一样？
3. 保存和提交有什么区别？遇到异常该怎么处理？

**回扣主线**：

> "这节课只有一句话最该带走：**操作前，先看一眼——这是测试环境，还是生产环境？** 这一眼，决定了你接下来的每一个动作要不要加小心。下一课题讲'运行记录'，你会发现今天练的异常上报，正是写好运行记录的前半段。"

## 七、板书设计

**主板书区**

```
智能系统基础操作：

开启：登录 → 权限确认 → 环境/服务状态检查
使用：数据导入导出 → 任务创建领取 → 提交保存 → 结果查看

┌──────────────── 铁律 ────────────────┐
│ 操作前先问：这是测试环境，还是生产环境？ │
└────────────────────────────────────────┘
```

**副板书区（测试环境 vs 生产环境 对比）**

```
            测试环境            生产环境
数据性质    人为模拟/可重建       真实业务/用户数据
恢复难度    容易，重置重来        困难，可能无法恢复
影响范围    仅自己                牵连同事/下游/真实用户

判别口诀：删了/改了，能不能简单"重来一次"？
          能 → 测试环境（大胆练）
          不能 → 当生产环境（先确认标识再动手）

保存 vs 提交：保存=存给自己看  提交=交给别人看  保存≠提交
```
