## 一、教学目标

### （一）知识目标

1. 能说明数据库、表、字段、记录、主键的基本概念，并能说出主键"**唯一标识一条记录**"这一作用。
2. 能说明 `GROUP BY` + `COUNT` 聚合统计的基本原理——按某字段分组，再统计每组各有多少条记录。
3. 能说明 `JOIN` 的作用，并能解释 **INNER JOIN 与 LEFT JOIN 在处理"两表对不上的记录"时，结果为什么不一样**。

### （二）技能目标

1. **能编写基础SQL完成数据查询与导出**：`SELECT`/`WHERE`/`ORDER BY`/`LIMIT`/`GROUP BY`/`COUNT`/基础 `JOIN`。
2. 能将业务需求翻译成查询条件（字段、筛选值、时间范围等要素要拆解完整）。
3. **能将查询结果导出，并验证导出行数与预期一致**。
4. **能用 `LEFT JOIN` + `WHERE 右表字段 IS NULL` 的方法排查"孤儿记录"**（两表关联字段对不上的异常数据）。

### （三）素养目标

1. 建立"**代码能跑出结果 ≠ 结果是对的**"的职业习惯——把"导出前核对数量"当成和写查询语句本身一样基本的动作，而不是可做可不做的额外步骤。

---

## 二、教学重点与难点

### 重点

**导出前用 `COUNT` 核对数量的习惯**——不管查询写得多熟练，结果导出前先确认"这个数字对不对"。

### 难点

| 难点 | 学员典型错误预判 | 突破方式 |
|---|---|---|
| 零基础学员容易写完查询就直接导出，不做数量核对 | 把"代码能跑出一个结果"等同于"这个结果是对的"——查询条件写错（如字符串拼错、`JOIN` 用错类型导致部分记录被悄悄排除）也不会主动起疑，直接把文件导出发走 | 用数据集里**真实存在**的"孤儿订单"现象（998/999/1000号订单的 `user_id` 在 `users` 表中根本找不到对应记录），让学员亲手跑一遍 `JOIN` 查询，亲眼看到"查出来的数量和预期（1000条）对不上"，再追问"如果你没核对，这批带错误的数据会被原样交付出去"，建立"导出前必须核对"的条件反射，而不是停留在"老师说要核对"这句口号上 |

## 三、学情分析与前置知识

**前置知识**：课题1-1（设备与工具的原始业务数据采集）。

**学情判断**：

- 本课题是学员在本职业等级**第一次接触数据库和SQL这个全新工具**，与课题1-1积累的"用设备采集"经验关联较小，几乎是从零开始。
- SQL语法本身难度不高，但零基础学员最大的障碍往往不是"记不住关键字"，而是**第一眼看到一整行英文字母不知道从哪开始读、怎么拆**。因此教学中每引入一个语法点，必须立刻配一次可以照抄照跑的小练习，把"看得懂"转化成"自己能写"，否则很容易在后半程积累畏难情绪。
- 本课题实操占比高达3学时，内容密度大（从基本概念到 `SELECT` 到聚合统计再到 `JOIN`），必须控制好每个新语法点之后的练习时长，防止前松后紧、`JOIN` 这类较难内容被压缩。

## 四、教学方法与手段

1. **演示+跟练法**（核心）：每个SQL语法点先投影演示，学员立刻跟着敲一遍，当场验证结果。
2. **真实数据验证法**：用数据集中真实存在的"孤儿订单"现象，让学员体会"导出前核对"的必要性，而不是空讲道理。
3. **认知冲突法**：用 `INNER JOIN` 后总数"凭空少了3条"这一反直觉现象，制造追问机制的契机。
4. **任务驱动法**：以"独立写出一条完整的业务翻译查询并核对数量"作为本课题的终产物。

### 环节一：导入（0–10′）

**教师活动** —— 投影展示（不给结论）：

> "组长让实习生小李导出'北京地区的所有注册用户清单'。小李打开数据库工具，写了一条SQL：
>
> `SELECT * FROM users WHERE city='beijing'`
>
> 点击运行，结果显示——**0条记录**。小李心想'大概北京确实没什么用户'，直接把这个空文件发给了组长。"

**提问话术**：

> "请大家判断：小李这么做，有没有问题？举手表决——认为没问题、可以直接发的请举手。"

（预期：部分学员会犹豫，部分会觉得"查出来是0条就是0条，有什么问题"）

> "好，先记住你的判断。学完这节课你会发现，这个'0'字里面，藏着SQL入门阶段最常见、也最容易被忽视的一类错误。"

**设计意图**：不直接否定，让"代码能跑出结果=结果就是对的"这个常见直觉先被公开表达，后面用语法细节推翻它，冲击力更强。

### 环节二：数据库基本概念（10–25′）

**讲授脚本**：

> "在学怎么查之前，先搞清楚我们到底在查什么。打开 `practice.db`，里面有三张表：`users`（用户）、`products`（商品）、`orders`（订单）。"

**逐项讲解**（投影 + 板书）：

| 概念 | 含义 | 本课题例子 |
|---|---|---|
| 表（table） | 存放同一类事物信息的集合，像一张Excel表 | `users` 表存所有用户信息 |
| 字段（column） | 表里的一列，描述事物的某一个属性 | `users` 表有 `user_id`、`user_name`、`city`、`register_date` 四个字段 |
| 记录（row） | 表里的一行，代表一个具体的"个体" | 一条记录就是一个具体用户的信息 |
| 主键（primary key） | 能**唯一标识**一条记录、不允许重复的字段 | `users.user_id`、`orders.order_id`、`products.product_id` |

**讲授脚本（主键的作用）**：

> "为什么要有主键？因为如果没有一个'身份证号'一样的字段，两条记录就算所有其他信息完全相同，你也没办法准确说'这是同一个人'还是'这是两个长得一样的人'。主键就是用来解决这个问题的——**保证表里的每一条记录都有一个独一无二的编号**。如果你发现主键重复了，基本可以断定这批数据有严重的质量问题。"

**铺垫JOIN的伏笔**：

> "再看一眼 `orders` 表，它有一个 `user_id` 字段——这个字段存的编号，理论上应该能在 `users` 表里找到对应的那条用户记录。**两张表就是靠这种'字段对字段'的方式关联起来的**。这句话先记住，后面讲 `JOIN` 的时候会用到。"

**学员活动**：对照投影，在自己的讲义上找出三张表各自的字段和主键，并说出"`orders.user_id` 应该能在哪张表里找到对应记录"。

### 环节三：基础SQL语法（25–45′）

**讲授脚本**：

> "有了表、字段、记录这几个概念，现在正式学怎么'问数据库要数据'。SQL查询最常用的骨架就这一句："

**板书核心句**：

```
SELECT 字段 FROM 表名 WHERE 条件 ORDER BY 字段 LIMIT 数量;
```

**逐项讲解**：

> "**SELECT 字段**——你想要哪些字段，想要全部就写 `*`。
> **FROM 表名**——从哪张表里找。
> **WHERE 条件**——筛选条件，不写就是不筛选、要全部记录。
> **ORDER BY 字段**——按哪个字段排序，默认从小到大，加 `DESC` 就是从大到小。
> **LIMIT 数量**——只要前几条，常用来'先看几条结果，别一下子查全表'。"

**语法易错点（零基础高频踩坑）**：

> "这里有一条零基础最容易踩的坑：**WHERE条件里，文字要用英文单引号包起来，数字不用**。
>
> 比如要查城市是'北京'的用户，要写 `WHERE city='北京'`，引号不能丢；但要查价格大于5000的商品，要写 `WHERE price>5000`，这里绝对不能写成 `WHERE price>'5000'`。记混了，查询不一定报错，但结果可能悄悄不对——这也是开头小李踩的坑的另一半：他引号倒是加对了，**但把中文'北京'错写成了拼音'beijing'，数据库里存的是中文，拼音永远匹配不上，查出来自然是0条**。"

**回扣导入**：

> "现在回答第一节的问题：小李的做法有没有问题？**问题不在于'查出来是0条'本身，而在于看到0条这个结果，他完全没有停下来想一想'一个城市用户数为0，正常吗'**。0条和全表的记录数一样，都是需要你多问一句'为什么'的信号，不是看到数字就能直接收工导出的。"

**学员活动**：抄写骨架语句并记录引号规则，口头举一个"这里要不要加引号"的例子（如按注册日期筛选、按用户名筛选）。

### 环节五：新授——GROUP BY 与 COUNT 聚合统计（75–95′）

**讲授脚本**：

> "前面查的都是'挑出符合条件的记录'。但实际工作中更常见的需求是'按类别数一数各有多少'——比如'各城市分别有多少用户'。这就要用到 `GROUP BY`。"

**板书核心句**：

```
SELECT 分组字段, COUNT(*) FROM 表名 GROUP BY 分组字段;
```

**讲授脚本（原理）**：

> "`GROUP BY city` 做的事情是：把所有记录按 `city` 字段的取值分成一堆堆——所有'北京'分一堆，所有'上海'分一堆……`COUNT(*)` 再数每一堆里有多少条记录。"

**举例演示**：

```python
q = "SELECT city, COUNT(*) as cnt FROM users GROUP BY city ORDER BY cnt DESC"
print(pd.read_sql(q, conn))
```

**预期结果（已验证）**：

```
城市    cnt
成都    39
广州    36
深圳    34
杭州    33
北京    30
上海    28
```

**提问话术**：

> "刚才任务1查出'北京用户数=30'，和这张表里北京那一行对得上吗？"

（引导学员核对 30 = 30，建立"两种不同写法算出的数字应该互相印证"的意识）

> "这正是聚合查询的一个额外好处：它能让你**用一条查询同时核对多个筛选条件的结果**，是检查自己有没有写错查询的好工具。"

**学员活动**：记录 `GROUP BY` + `COUNT` 的骨架语句，并用上面的结果反向核对任务1的30这个数字。

### 环节七：新授——JOIN 与"孤儿记录"排查方法（125–145′）

**讲授脚本**：

> "环节二留了一个伏笔：`orders.user_id` 应该能在 `users` 表里找到对应记录。如果我想查'每个订单对应哪个城市的用户'，光查 `orders` 表是看不到城市信息的——城市信息在 `users` 表里。这时候就要把两张表'拼'到一起看，这就是 `JOIN`。"

**两种JOIN的区别（板书对比）**：

> "`JOIN` 最常用的有两种，处理'两表对不上'的记录时，结果完全不同：
>
> **INNER JOIN**：只保留两张表都能对上的记录，对不上的那些，**直接被悄悄丢弃**，你不会看到任何提示。
>
> **LEFT JOIN**：以左边的表为准，全部保留；右边表如果没有对应记录，就用 `NULL`（空）填上，**而不是丢弃这条记录**。"

**板书语法**：

```
SELECT ... FROM A JOIN B ON A.字段=B.字段;              -- 等价于 INNER JOIN
SELECT ... FROM A LEFT JOIN B ON A.字段=B.字段;         -- LEFT JOIN
```

**排查"孤儿记录"的方法**：

> "既然 `LEFT JOIN` 会把对不上的记录也保留下来、只是右边填 `NULL`，那我只要加一个条件——**筛选出右表字段是 `NULL` 的那些记录**——就能精准找出'左表有、右表却找不到对应记录'的异常数据，这类记录我们叫它**孤儿记录**。"

**板书核心句**：

```
LEFT JOIN + WHERE 右表字段 IS NULL  →  专门用来找"查无此人"的孤儿记录
```

**学员活动**：记录两种JOIN的区别，口头复述"如果我想找出 `orders` 表里 `product_id` 在 `products` 表中不存在的记录，应该怎么写"。

### 环节八：实操三——孤儿记录排查（难点突破，145–180′）

**教师指令**：

> "现在用真实数据验证一下。我们查一下 `orders` 表里，有没有订单的 `user_id`，在 `users` 表里根本找不到对应用户。"

**投影代码（学员照抄运行）**：

```python
q = """SELECT o.order_id, o.user_id FROM orders o
        LEFT JOIN users u ON o.user_id = u.user_id
        WHERE u.user_id IS NULL"""
print(pd.read_sql(q, conn))
```

**预期结果（已验证）**：

```
order_id  user_id
998       9001
999       9002
1000      9003
```

**关键提问（难点突破核心）**：

> "订单998、999、1000，它们的 `user_id` 是9001、9002、9003，但 `users` 表里一共只有200个用户（`user_id` 从1到200）。如果业务需求是'统计各城市的订单量'，你直接把这1000条订单全部导出、拿去跟用户表拼接，这3条订单会发生什么？"

**预期学员反应与教师应对**：

| 学员反应 | 教师应对 |
|---|---|
| "没事吧，导出来直接用就行" | 追问："这3条订单的 `user_id` 在 `users` 表里根本找不到对应记录，没有城市信息，你打算怎么把它们算进'某个城市的订单量'？" |
| "会报错吧" | 纠正："不会报错。如果你用 `INNER JOIN`，这3条记录会被**悄悄排除**，程序正常跑完，不会有任何提示——这才是最危险的地方：**没有任何错误信息，但数据已经少了**。" |
| 意识到会出问题但说不清楚后果 | 引导："想象你导出的报告显示'本月共997条有效订单'，而实际系统里明明有1000条。如果你没做这次排查，你根本不会知道'少的3条'是正常业务情况，还是数据本身有问题。" |

**追加提问（迁移巩固——"没查到问题也要写进报告"）**：

> "再用同样的方法查一下 `orders.product_id` 在 `products` 表里是不是都能找到对应商品，结果会是什么？"

（学员运行类似查询，结果为**空，没有一条孤儿记录**）

> "这说明什么？不是每次排查都会查出问题。**商品这边是干净的，用户这边有3条孤儿订单**——检测的意义不是'非要挑出毛病'，而是系统地把该查的关联字段都查一遍，有问题的记下来、处理掉，没问题的也要确认清楚、写进交付说明里，不能因为'顺手查了一下没发现问题'就连这一步检查本身都不提。"

**教师总结话术**：

> "这就是本课题最该带走的一课：**代码能跑出结果，不代表结果是对的**。`COUNT` 核对总数、`LEFT JOIN` 核查关联完整性，这两个动作花不了多少时间，但它们是唯一能帮你在导出之前发现问题的机会——数据一旦发出去，别人很难再帮你发现这批数据'悄悄缺了几条'。"

### 环节九：新授+实操——业务需求翻译成查询条件（180–205′）

**讲授脚本**：

> "实际工作中，业务方不会直接给你SQL，他们只会说一句中文需求，比如：**'帮我查一下北京地区最近一个月的订单量'**。这句话要翻译成SQL，你需要先把它拆成几个要素。"

**翻译步骤（板书）**：

```
① 要查哪张表 / 要不要关联别的表？   —— 订单在orders，但"北京地区"是users表里的字段，要JOIN
② 筛选条件对应哪个字段？具体筛选值是什么？ —— city='北京'
③ "最近一个月"怎么界定？                 —— 需要一个基准日期，再往前推时间范围
④ 最终要的是明细还是统计数量？            —— "订单量"是数量，要用COUNT
```

**教师强调（易踩坑点）**：

> "第3步最容易被轻视。'最近一个月'或者'近30天'，看起来很明确，其实藏着一个问题：**是自然月，还是从今天往前滚动30天？算不算今天？** 这种边界不说清楚，你和业务方对出来的数字可能完全不一样。考试和实际工作中，拿不准就要主动去问清楚，而不是自己猜一个。"

**完整演示案例**：

> "就用数据集本身做一次演示。这批订单数据的最新日期是2026-03-31，我们把'近30天'定义为2026-03-01至2026-03-31这个区间（共31天，按自然日近似处理）。现在要查'北京地区近30天的订单量'。"

```python
q = """SELECT COUNT(*) as cnt FROM orders o
        JOIN users u ON o.user_id = u.user_id
        WHERE u.city = '北京' AND o.order_date >= '2026-03-01'"""
print(pd.read_sql(q, conn))
```

**预期结果（已验证）**：`cnt： 59`

**顺带追问（串联前面的知识点）**：

> "这条查询用的是普通 `JOIN`（也就是 `INNER JOIN`），前面讲过它会悄悄排除孤儿订单。这里有没有影响？"

（引导学员回忆：998/999/1000号孤儿订单的下单日期都在1月，本来就不在"近30天"这个筛选范围内，所以这次结果没有受到影响——但**这是巧合，不代表以后每次都没有影响**，这正是为什么"核对总数"要成为习惯动作，而不是只在"看起来可能有问题"的时候才做。）

**学员活动**：仿照上面四个翻译步骤，口头拆解"统计上海地区completed状态的订单数量"这一需求涉及哪些字段和条件，再独立编写并运行。

### 环节十：变式练习——INNER JOIN 为什么"丢了"数据（205–225′）

**教师指令**：

> "最后一个练习。请大家写一条SQL，用 `JOIN` 把 `orders` 和 `users` 关联起来，按城市统计订单量，然后把六个城市的订单数加起来。"

```python
q = """SELECT u.city, COUNT(*) as cnt FROM orders o
        JOIN users u ON o.user_id = u.user_id
        GROUP BY u.city ORDER BY cnt DESC"""
print(pd.read_sql(q, conn))
```

**预期结果（已验证）**：

```
深圳 193   成都 188   广州 173   北京 170   杭州 146   上海 127
```

**关键提问**：

> "把这六个数字加起来，等于多少？再对照一下，`orders` 表总共有多少条记录？"

**预期学员反应与教师应对**：

| 学员反应 | 教师应对 |
|---|---|
| 算出997，没察觉异常 | 追问："`orders` 表总数是1000条，你按城市分组统计出来的加起来却是997，少的这3条去哪了？" |
| 立刻联想到孤儿订单 | 肯定："完全正确。这3条正是998/999/1000号孤儿订单——它们的 `user_id` 在 `users` 表里找不到对应记录，普通 `JOIN`（即 `INNER JOIN`）在关联的时候就把它们排除掉了，不会有任何报错提示。" |
| 算错了数字 | 引导：先用计算器核实6个数字的加和，确认997这个数字本身没算错，再回到问题本身 |

**教师总结话术**：

> "这是本课题最后，也是最重要的一个提醒：**只要查询里用到了JOIN，导出前就不能只核对'这张表本身对不对'，还要核对'JOIN之后的总数，和原表总数能不能对得上'**。差了几条，往往就是关联字段存在孤儿记录。核对的方法很简单——**用COUNT分别算一下JOIN前和JOIN后的总数，两个数字一对比就知道了**。"

## 七、板书设计

**主板书区**

```
数据库三要素：表(table) / 字段(column) / 记录(row)      主键 = 唯一标识一条记录

SELECT 字段 FROM 表 WHERE 条件 ORDER BY 字段 LIMIT 数量;
SELECT 分组字段, COUNT(*) FROM 表 GROUP BY 分组字段;

┌──────────────────── 实测反差 ────────────────────┐
│ orders 表总数：1000 条                            │
│ 按城市 JOIN 统计后合计：997 条   ← 少了 3 条！      │
│   → LEFT JOIN + WHERE 右表字段 IS NULL 一查：      │
│     订单 998 / 999 / 1000 的 user_id 在 users 表中 │
│     根本不存在 ──"孤儿订单"                        │
└────────────────────────────────────────────────────┘
```

**副板书区（INNER JOIN vs LEFT JOIN）**

```
              INNER JOIN              LEFT JOIN
结果范围      两表都能对上的记录       左表全部保留，右表对不上填NULL
能否找孤儿    不能（被静默排除）       能（配合 WHERE 右表字段 IS NULL）

判别口诀：
  要"两边都有的" → 用 INNER JOIN
  要"左边一个不漏，顺便揪出查无此人的" → 用 LEFT JOIN
```

**角落常驻**

```
⚠ 代码能跑出结果 ≠ 结果是对的——导出前，先COUNT
```
