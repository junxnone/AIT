## 一、教学目标

### （一）知识目标
1. 能说明运行记录的作用：问题可追溯、异常可复现、绩效可核查。
2. 能说出运行记录应覆盖的三项要素：功能使用情况、运行是否正常、异常现象描述。

### （二）技能目标
1. **能够记录智能系统功能应用情况**。
2. **能够记录智能系统应用数据情况**。
3. 能填写规范的运行/维护记录表。

### （三）素养目标
1. **异常描述要写现象不写结论**。

---

## 二、教学重点与难点

### 重点
异常描述"写现象不写结论"的区别。

### 难点

| 难点 | 学员典型错误预判 | 突破方式 |
|---|---|---|
| 异常描述"写现象不写结论" | 零基础学员习惯用"系统坏了""不正常""数据不对"这类笼统结论描述问题，说不出具体观察到的现象，导致记录无法用于问题排查 | 用"收到'系统坏了'四个字，你能做什么"这一提问制造认知冲突，让学员自己意识到结论式表述几乎没有信息量；再用正反对比示例 + 改写练习让学员动手内化标准，最后在两类实操记录（功能应用情况、应用数据情况）中分别巩固迁移 |

---

## 三、学情分析与前置知识

**前置知识**：课题3-1（智能系统基础操作）。

**学情判断**：本课题是五级/初级工60学时课程的最后一课，学员已掌握系统基础操作，本课题聚焦"记录"这一容易被轻视但实际很重要的技能。零基础学员普遍习惯用口语化的笼统结论描述问题（"坏了""不对"），这是生活中常见的表达习惯，但在工作记录场景下并不合格——这不是态度问题，而是没有意识到"记录是写给别人（或未来的自己）看的"，需要专门训练把表达具体化、数字化的书面习惯。

---

## 四、教学方法与手段

1. **对比辨析法**（核心）：用"现象 vs 结论"的直接对比，让合格标准一目了然。
2. **改写练习法**：让学员把笼统表述改写为具体现象描述，在动手改写中内化标准。
3. **任务驱动法**：以"填写两类规范记录表"作为本课题的落地任务，直接对接实操题五-6。

### 环节一：新授——运行记录的作用与要素（0–20′）

**讲授脚本**：

> "大家平时在系统里做标注、审核这些操作，有没有想过：如果半年后某条数据出了问题，我们怎么才能查到当时到底发生了什么？"
>
> （停顿，等待反应）
>
> "这就是运行记录存在的意义。它有三个作用：**问题可追溯、异常可复现、绩效可核查**。
> 问题可追溯——记录写得清楚，半年后出问题照样能查到当时的具体操作和现象；
> 异常可复现——好的记录能让排查的人按你写的步骤重新'演'一遍问题，而不是凭猜测排查；
> 绩效可核查——记录也是统计每个人工作量、工作质量的依据。"

**板书核心句**：运行记录三要素——功能使用情况 / 运行是否正常 / 异常现象描述

**学员活动**：记录三要素，并各自口头举一个自己最近操作中可以记录的例子（提问2-3人）

**预期学员反应与教师应对**：

| 学员举例 | 教师应对 |
|---|---|
| 举例只说"我今天标注了数据"（笼统） | 追问："标注了什么任务？几条？用的什么功能？有没有遇到卡顿或报错？"——引导补充成具体可用的记录 |
| 举例具体（如"用标注工具标了50条文本，中途有一次保存失败，刷新后恢复"） | 肯定并板书这个例子，作为"合格记录雏形"的示范 |

**设计意图**：不直接灌输定义，先用"半年后怎么查"这个真实场景制造"为什么需要记录"的代入感，再引出三要素。

---

### 环节二：对比练习——现象 vs 结论（难点突破，20–40′）

**教师先展示一组对比，不直接说明哪个好**：

| 写法 | 学员判断 |
|---|---|
| "系统坏了" | |
| "点击提交后页面提示500错误，重试3次均失败" | |
| "数据不对" | |
| "导出文件行数为980，预期应为1000，缺少20行" | |

**教师提问（难点突破核心）**：

> "如果你是负责排查问题的同事，收到'系统坏了'这四个字，你能做什么？"

**预期学员反应与教师应对**：

| 学员反应 | 教师应对 |
|---|---|
| "能，去看看系统哪里坏了" | 追问："看哪里？是登录功能、上传功能，还是提交功能？什么时候发生的？'系统坏了'这四个字能告诉你这些信息吗？" |
| 意识到信息不够 | 肯定："对，几乎什么都做不了——不知道是哪个功能坏了、什么现象、发生在什么时候。**描述现象才能让别人（或未来的你）据此排查问题。**" |

**教师布置改写练习**：

> "现在给大家几个笼统表述，试着改写成具体现象描述：'标注工具用不了''导出的数据有问题''网络连不上'。"

（巡回指导，检查学员改写是否包含具体现象、时间、复现方式）

**教师总结话术**：

> "记住一个检验标准：**你写的这句话，能不能让一个完全没在场的人，看完就知道该从哪里查起？** 能——是现象；不能——还是结论，要继续改写。"

---

### 环节三：实操一——填写规范记录表：功能应用情况（40–65′）

**任务情境**（投影）：

> "你今天上午用标注工具标注时，点击提交后页面卡住，刷新后恢复，卡顿约3分钟，请把这件事写成一条规范的运行记录。"

**记录模板**（投影+讲义已有要素）：

```
功能使用情况：……（什么时间、用了什么功能、做了什么操作）
运行是否正常：……
异常现象描述：……（如无异常，可直接写"无异常"）
```

**巡回指导要点**：

- 检查是否写出具体时间点（而非"刚才""今天"笼统带过）
- 检查是否用结论代替现象（如直接写"卡顿"，而不写"点击提交后页面无响应，约3分钟后恢复"）
- 检查是否交代了复现方式（刷新后是否恢复、是否重试过）

**对完成快的学员追问**：

> "如果这条记录半年后被别人看到，他能不能单凭这几句话判断问题出在提交环节还是网络环节？"

---

### 环节四：实操二（变式练习）——记录应用数据情况（65–90′，难点迁移巩固）

**教师指令**：

> "刚才记录的是'功能用得顺不顺'。现在换一类——'应用数据情况'，记录的是数据本身的状态，不是功能好不好用。"

**任务情境**（投影，沿用讲义已有案例数字）：

> "你今天导出了一批标注任务的统计文件，系统显示导出文件行数为980行，但该批次预期应为1000行，缺少20行。请把这件事写成一条规范记录。"

**关键提问（难点迁移巩固）**：

> "这里的'缺少20行'，是该写成'数据不对'，还是写成'980 对 1000，缺20行'？为什么？"

**预期学员反应与教师应对**：

| 学员反应 | 教师应对 |
|---|---|
| "写'数据不对'就行，意思到了" | 追问："'不对'这两个字，能告诉同事缺了多少吗？能告诉他该从哪个范围开始查吗？"——引导意识到结论式表述丢失了可排查的信息 |
| 写出"980 对 1000，缺20行" | 肯定："对，这才是应用数据情况记录该有的颗粒度——具体数字、具体对比，看一眼就知道问题有多大。" |

**巡回指导要点**：检查是否写出具体数字对比（而非"少了一些"这类模糊表述），是否清楚区分"这是应用数据情况记录"而不是"功能使用情况记录"。

**设计意图**：通过与环节三对照，让学员体会"功能应用情况"记录的是操作过程，"应用数据情况"记录的是数据本身的量化状态，二者形式不同，但都要服从"写现象不写结论"这一个总原则。

---

### 环节五：分组互评与典型错误纠错（90–107′）

**教师活动**：投影展示2-3份教师预先准备的"典型不合格记录"（如：只写"系统有问题"、缺少具体时间、把两类记录混在一起写不清楚），组织学员分组诊断问题所在。

**预期诊断点**：

| 典型错误 | 应诊断出的问题 |
|---|---|
| 记录写"今天标注遇到点问题，处理了" | 全篇都是结论，没有任何现象、时间、数字 |
| 记录只写"导出数据少了" | 应用数据情况记录缺少具体数字对比 |
| 记录把"提交卡顿"和"行数差异"混在一句话里说不清楚 | 功能使用情况与应用数据情况应分开、分别写清楚 |

**学员活动**：分组讨论，每组派代表指出至少1处问题并给出修改建议。

---

### 环节六：小结与作业（回扣全五级课程主线，107–120′）

**知识回顾**（请学员口述，教师补全）：

1. 运行记录的三个作用是什么？三要素是什么？
2. "写现象不写结论"具体要怎么做到？
3. 功能应用情况记录和应用数据情况记录，分别记录什么？

**回扣全五级课程主线（板书收口）**：

> "这是整个五级60学时课程的最后一课。回头看这60个学时——无论是采集数据、处理数据，还是标注、审核、运维，贯穿始终的一条主线是：**按规范把事情做准、做细，遇到规范没覆盖的情况，记录上报，而不是自己凭感觉处理。**
>
> 今天这节课的'写现象不写结论'，正是这条主线在最后一个环节上的体现——把你做的事、遇到的情况，如实、具体地记录下来，才能让别人（或未来的你）据此判断和处理，而不是凭一句笼统的结论蒙混过去。
>
> 这也是你们接下来四级要学的'审核与优化'、三级要学的'设计与诊断'的共同起点——没有扎实的'做'和'记录'的基础，审核和设计都无从谈起。"

**作业**：见下方"作业与课后任务"表。

## 七、板书设计

**主板书区**

```
运行记录三要素：
  功能使用情况    运行是否正常    异常现象描述

核心原则：写现象，不写结论
┌───────────────── 正反对比 ─────────────────┐
│ "系统坏了"  ✗  →  "提交后提示500，重试3次均失败" ✓ │
│ "数据不对"  ✗  →  "导出980行，预期1000行，缺20行" ✓ │
└──────────────────────────────────────────────┘
```

**副板书区（两类记录对象辨析）**

```
                功能应用情况记录          应用数据情况记录
记录对象        操作过程、功能是否好用      数据本身的数量/状态
本课例子        提交卡顿约3分钟            导出980行，预期1000行，缺20行

共同原则：都要写现象，不写结论
```

**角落常驻（收官寄语）**

```
⚠ 规范做准做细；遇规范未覆盖，记录上报，不凭感觉处理
```
