## 第一部分：业务数据处理流程设计（课题 1-1）

### 1. 先问你一句：四级和三级做"数据处理"，差别到底在哪？

四级的核心技能是"按规范标注"；三级的核心技能是**设计一整条从原始数据到可用于训练的数据的处理流程**，并且在每一步都设置质量控制点。完整流程只有五个字能记住框架：

```
采集 → 清洗 → 归类 → 标注 → 质检
```

**先别满足于背下这五个词**——我现在问你：如果一份方案只写了"采集→清洗→归类→标注→质检"，中间什么都不展开，这份方案能得分吗？

答案是几乎不得分。实操题评分表里，每个环节的"质量控制点"和"异常处理方式"是单独配分项。五个字只是框架，考核的核心是框架之下你有没有具体的判断。所以下面每一环节，我们都要练"展开成具体方案"这件事。

### 2. 逐环节过一遍，重点看"质量控制点"怎么想

- **采集**：明确数据来源渠道，同时带着上一篇讲的合规红线把关——采集阶段不合规，后面全白干。
- **清洗**：去重复、缺失、异常、噪声，统一格式。质量控制点是**清洗规则的阈值要有业务依据**，不能拍脑袋。比如"订单金额为负"显然异常，但"金额特别大"可能是大客户批量采购，不是脏数据——这个判断需要结合业务场景，不能套用一个通用清洗脚本。
- **归类**：按业务维度分组，为标注做准备。这一步常被低估，但归类体系设计得好不好，直接决定标注效率和一致性——粒度太粗会降低标注准确率，太细会增加成本和复杂度。
- **标注**：按既定规范（三级要自己设计这套规范）打标签。质量控制点在于标注规范是否清晰无歧义——这个话题足够重要，下一篇会整整用一篇幅展开。
- **质检**：抽检/复核标注结果，常见方式是多人标注一致性检验和抽样专家复核。**质检不是走过场**，是整条流程里"发现问题、反过来优化前面环节"的关键反馈点。

### 3. 这条流程最容易被忽视的一点，先让我问你一个场景

质检发现：同一批客服对话数据，三个标注员的标注一致率只有55%。**你的第一反应是什么？**

如果你的第一反应是"重新标一遍"或者"培训标注员认真点"，先停一下。

更合理的第一反应是**倒推排查更前面的环节**——很可能是归类阶段的标签体系存在歧义，或者标注规范本身就没写清楚判定标准。这正是这条流程"可以反向反馈优化"的含义：它不是单向的流水线，质检发现的问题往往要回头修正"归类"甚至"清洗"阶段。

三级实操题经常给你一个"流程跑下来结果不理想"的场景，让你判断问题出在哪一环、该怎么倒推修正——这正是"设计流程"和"执行流程"的本质区别：执行者看到低一致率只会想"重新标"，设计者会想"流程的哪一环出了问题"。

### 4. 用一个真实数据案例练一下"先探查、再设计"

有一份客服会话原始数据（200条记录），如果你先跑一遍探查代码（`d.isna().sum()`、`value_counts()`），会看到真实现状：渠道字段缺失9条；客服工号字段里混进了9条"未知"；满意度评分缺失40条；"问题是否解决"字段里同时存在"是/否/y/Y"四种取值混用。

**现在问你**：面对"客服工号"字段里的9条"未知"记录，下面两种处理思路，哪个更合理？A. 直接删除这9条；B. 单独归类后人工核实补全，若无法补全再决定是否剔除。

答案是 B。直接删除会损失这批会话里的其他有效信息（比如会话内容、满意度评分）；应该先单独归类，尝试通过其他渠道（比如系统日志）核实补全，确实补不了再结合这9条在整体数据中的占比决定是否剔除。

**这道题想告诉你的是**：三级的"设计"能力必须建立在对真实数据的了解之上。如果不先探查数据的真实问题，设计出来的流程就只能是脱离实际的理想化模板，没法真正解决这批数据存在的具体问题。这也是为什么本篇开头说"先探查现状，再下判断"是贯穿的底层动作——它不是一句口号，是具体操作上"先跑代码看数据长什么样，再动笔写方案"。

## 第二部分：业务模块问题识别与优化方案（课题 1-2）

### 1. 先给你立一个原则，再用数据验证它

本节的核心原则只有一句话：**一个现象，可能有不止一个原因。** 我们现在用一个真实的营销漏斗数据案例，让你亲眼看到这句话有多重要。

场景：某自动化营销项目的曝光→点击→加购→下单→支付五环节漏斗数据，按渠道（A/B/C/D）和周次记录。

### 2. 第一步：看总体，你会看到一个"全局瓶颈"

实测结果（分渠道汇总）：

| 渠道 | 点击率 | 加购率 | 下单率 | 支付率 |
|---|---|---|---|---|
| A | 5.1% | 27.0% | 10.8% | 91.1% |
| B | 3.0% | 27.7% | 10.8% | 90.5% |
| C | 6.2% | **3.0%** | 10.6% | 87.0% |
| D | 4.3% | 26.7% | 10.8% | 90.1% |

**先自己看这张表，花10秒：你能发现几个问题？**

第一个发现：所有渠道的"加购→下单"转化率都只有约10.8%，远低于加购率（约27%）和支付率（约90%）。这是一个**全局性瓶颈**——不管哪个渠道，用户到了购物车之后，大部分都没有继续下单。

### 3. 第二步：如果你只报了第一个发现就提交，会漏掉什么？

**现在再看一眼表格里渠道C那一行。** 它的加购率只有3.0%，而其他渠道都在27%左右。

**停一下想清楚**：如果你的优化方案写的是"加购→下单转化率低，建议优化下单流程"，这个方案对渠道C完全不对症——渠道C的真实问题根本不在"加购→下单"，而在更前面的"点击→加购"环节。这是一个**局部异常**，和刚才发现的全局瓶颈是两个完全独立的问题。

这就是"一个现象可能有不止一个原因"在数据里的真实样子：总体平均数字（全局瓶颈）会掩盖某个渠道的局部异常，不下钻到渠道维度，你永远发现不了渠道C的问题。

### 4. 第三步：还有第三个发现，藏在时间维度里

如果你对渠道B按第5周前后拆开看：第5周前曝光均值约5.9万/周，点击率约4.85%；第5周后曝光均值翻倍到约12.8万/周，但点击率腰斩到约2.43%。**投放量增加了，但流量质量下降了**——这是第三个独立问题，体现在时间维度而不是渠道维度。

**你发现了吗？** 三个发现分别来自三个不同的下钻维度：总体（全局瓶颈）、渠道（局部异常）、时间（时序异常）。只做其中一种下钻，你会永远错过另外两种问题。这正是为什么核心方法要反复强调：**先看总体转化率定位"哪个环节整体最差"，再分维度下钻（渠道/时间/人群）——全局瓶颈和局部异常往往同时存在，而且需要完全不同的优化方案。**

### 5. 一份合格的优化方案，必须包含什么

走到这一步，你应该能自己列出来了，我们对一下：问题定位（分清全局瓶颈和局部异常，不要混为一谈）、根因假设、优化方案（针对每个独立问题分别给方案，不能用一个方案覆盖所有问题）、可度量的成功指标（比如"下单率从10.8%提升到15%"，而不是"提升转化率"这种无法验证的表述）、推动实现的路径。

**最后再考你一道**：如果有份方案写"将下单率尽可能提升"，这个表述合格吗？——不合格，"尽可能"不是可度量、可验证的目标，必须写具体数字和观察周期，否则方案落地之后根本无法判断是否真的达到了预期效果。

## 串起来看：这两节课共享的方法论

1-1 讲的是"先探查数据现状，再设计处理流程"；1-2 讲的是"先看总体、再分维度下钻"。两者其实是同一个思维习惯的两种表现形式：**不要直接套用经验或模板下结论，先去看真实数据长什么样，再决定怎么做。** 这个习惯会在后面讲标注质量诊断、模型训练诊断、系统监控时反复出现——你会发现这门课从头到尾都在练同一种肌肉。
