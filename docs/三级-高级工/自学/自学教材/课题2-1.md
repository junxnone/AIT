## 一、为什么清洗不是"调用几个标准函数"

### 1.1 一次角色转变

如果你是从四级、五级的岗位做上来的，你应该已经很熟悉"清洗"这件事——但那时候你做的是**执行**：拿到一份现成的清洗手册，照着手册上写好的规则一条条处理数据。三级要求的是另一件事：**你自己来设计这份手册**。

这个转变听起来只是"从执行到设计"一句话，但它在编码层面会自然地诱发一个误区：把清洗简化成"调用几个标准函数就完事了"。比如看到数据有缺失，就条件反射地写 `dropna()`；看到有重复，就写 `drop_duplicates()`。这两个函数确实都是 pandas 里货真价实的清洗工具，但问题是——**它们只能处理它们认识的那一类问题，而真实数据里的问题种类，远比这两个函数能覆盖的要多得多**。

这不是靠讲道理能说服你的，所以本教材安排了一个"先预判、后验证"的环节（就是你刚才做的那次判断），用真实运行出来的数字让你亲眼看到这个误区有多大的代价。

### 1.2 数据质量问题的五种类型

在动手清洗之前，你需要一套系统的分类方法，否则很容易"想到哪处理到哪"，漏掉一整类问题。数据质量问题通常分为五类：

| 类型 | 典型表现 | 本课题数据集中的例子 |
|---|---|---|
| 重复 | 完全重复行、主键（如 `review_id`）重复 | 完全重复的评价记录 |
| 缺失 | 空值、空字符串 | 空文本评价 |
| 异常 | 超出合理范围的数值、非法取值 | `rating` 字段出现不在 1–5 区间的值 |
| 噪声 | HTML 标签、emoji、个人信息（手机号/邮箱）、超长/超短文本 | 采集残留的 HTML 标签、手机号、刷屏式超长评价 |
| 格式不一致 | 编码混乱、大小写/全半角混用 | 本数据集中暂未出现，但其他业务场景（如多来源拼接的数据）很常见，你在其他项目中遇到时要留心 |

发现问题类型只是第一步。更关键的是接下来这个问题：**发现了问题，具体该怎么处理？**

### 1.3 三种处理方式，选哪种不是凭感觉

很多人以为清洗就是"发现问题就删掉"，这是本课题要纠正的第二个误区。实际上处理方式只有三种，而选哪一种是有明确判别逻辑的：

- **删除**：这条信息本身没有可保留的价值。比如完全重复的行、空文本、非法评分——留着它对模型训练没有任何帮助，纯粹是噪声，删掉不可惜。
- **替换**：信息需要处理，但处理对象之外的内容仍然有价值。最典型的例子是手机号、邮箱这类个人信息——它必须脱敏，但整条评价剩下的情感语义依然有用，所以**用占位符替换，而不是把整条数据删掉**。
- **标记**：规则暂时无法确定该怎么处理，这时候不要自己瞎猜一个处理方式，而是先标记出来，流转给人工复核。

把这三者的判别逻辑浓缩成一句话，就是本课题最重要的一条判别口诀：

> **判别口诀：这条信息删掉后，会不会损失本可以保留的语义？**
> 会 → 优先**替换**；
> 不会 → 可以**删除**；
> 拿不准 → **标记**流转人工，不要自己猜。

请在心里默念一遍这条口诀，后面几节的所有案例都会反复用到它。

## 二、揭晓答案：两行代码到底处理了多少问题

### 2.1 先亲眼看看数据长什么样

在验证开头的判断之前，建议你先实际打开数据，随便抽 20 条看看，自己找找里面藏着哪些问题——这一步如果跳过，后面的数字对你来说只是抽象的统计量，没有"亲手发现问题"带来的真实感。

```python
import pandas as pd
df = pd.read_csv("../数据集/data.csv")
print(df.shape)
print(df["review_text"].sample(15, random_state=1).to_string())
```

随手抽样你会发现：完全重复的记录、空文本、HTML 标签、emoji、超长到像是刷屏的评论、含手机号邮箱的评价、非法评分（0 或 6，而正常评分应该在 1–5 之间）——这些问题在这批数据里都真实存在，不是教材编出来吓唬你的。

### 2.2 用代码逐项核实

现在我们用代码把每一类问题分别点清楚数量，来验证开头那两行代码到底处理了多少：

```python
import pandas as pd

df = pd.read_csv("../数据集/data.csv")

print("完全重复行:", df.duplicated().sum())
print("review_id重复:", df.duplicated(subset=["review_id"]).sum())
print("空文本(空字符串):", (df["review_text"].astype(str).str.len() == 0).sum())
print("真正的NaN缺失:", df["review_text"].isna().sum())
print("超短文本(<3字):", (df["review_text"].astype(str).str.len() < 3).sum())
print("超长文本(>200字):", (df["review_text"].astype(str).str.len() > 200).sum())
print("非法rating:", (~df["rating"].between(1, 5)).sum())
```

**实际运行结果**（已在试题库实操题 2.1.1 参考答案中验证通过，你自己跑出来的结果应当与此一致）：

```
完全重复行: 40
review_id重复: 0
空文本(空字符串): 31
真正的NaN缺失: 0
超短文本(<3字): 57
超长文本(>200字): 19
非法rating: 10
```

把"两行标准代码能处理的"和"实际需要处理的"并排摆在一起对比：

| 问题类型 | `dropna().drop_duplicates()` 处理情况 | 实际问题规模 |
|---|---|---|
| 完全重复 | 处理了 ✅ | 40 条 |
| 空文本 | **没处理** ❌ | 31 条 |
| 超短 / 超长 / 非法评分 | **没处理** ❌ | 合计 86 条 |
| HTML / emoji / 手机号邮箱 | **从未触碰**（这类问题要用"替换"而不是"删除"来解决） | 需要逐类用正则表达式处理 |

### 2.3 为什么 `dropna()` 对空文本完全无效——这才是真正的机制

看输出结果里一个非常反直觉的细节：**"真正的 NaN 缺失"是 0，但"空文本"却有 31 条。**

这是为什么？关键在于 `dropna()` 判断"要不要删"的标准是**单元格里有没有存值**，它只认 pandas 语义上严格定义的缺失值 `NaN`。而这 31 条问题样本的表现形式是**空字符串 `''`**——从 pandas 的角度看，这个单元格里确实"有值"，只是这个值恰好是空的字符串，不是 `NaN`。`dropna()` 认不出这种情况，一条都不会删。

> **这就是"调用标准函数"这件事最容易出错的地方**：函数认的是**技术上的"缺失"**，不是**业务上的"无效"**。这两者听起来很像，实际上是完全不同的两回事——技术上没缺失（单元格有内容），业务上却是无效数据（空字符串对训练没有任何价值）。一旦你习惯了"调用函数=解决问题"的思维方式，这种两者脱节的情况就会被系统性地漏掉。

再加上超短文本 57 条、超长文本 19 条、非法评分 10 条——这三类问题本质上和"重复""缺失"根本不沾边，`drop_duplicates()` 和 `dropna()` 从设计上就管不到它们。把这几类加起来：31 + 57 + 19 + 10 = **117 条问题**，两行标准代码从头到尾没有处理过其中任何一条。

更不用说 HTML 标签、emoji、手机号邮箱——这些问题根本不涉及"删除整行"，而是要在文本内容**内部做替换**。两行代码从来没有触及"替换"这个维度，连尝试都没尝试。

### 2.4 回到开头的判断：你答对了吗？

现在正式回答开头的问题：**这批数据清洗完成了吗？**

**没有。** `drop_duplicates()` 处理了 40 条完全重复的记录，这是两行代码里唯一真正起作用的地方。剩下至少 117 条行级问题，外加若干需要在文本内部做替换的噪声问题，全部都没有被处理。"调用了标准函数"和"清洗完成"这两件事之间，差着一整套需要你自己设计判定依据的规则——这正是三级要求你具备、而四级/五级不要求的能力。

如果你刚才的判断是"他说得对，清洗完成了"，不用沮丧——这正是本课题设计这个开篇判断的目的：用真实数字亲手推翻一次直觉,比单纯读到"要注意xxx"这种提醒要记得牢得多。

## 三、阈值从哪来：业务依据是清洗规则的生命线

上一节已经证明了"调用函数不等于清洗完成"。但接下来一个更深的问题是：当你自己设计清洗规则时，那些具体的数字（比如"多长算超长"）到底该怎么定？这是本课题真正的难点所在——不是代码写不写得出来，而是**每一条规则背后的判断依据，你自己拿不拿得出来**。

### 3.1 案例：两条关于"超长文本"的规则，哪个更合理

设想有两条规则摆在你面前：

- 规则A："删除所有超过 100 字的评价"
- 规则B："删除超过 200 字且内容高度重复的评价"

哪一条更合理？

乍一看规则A更简单直接、执行效率也高，容易让人觉得"更干脆"。但请你设想一下：假如有一条评价是用户认认真真写了 150 字的详细使用体验呢？按规则A，这条认真写的评价会被直接删掉——这就是问题所在：**长评价不一定是垃圾数据，很可能是用户认真写的详细体验，评价长度本身根本不是判断"是不是垃圾内容"的可靠依据。**

规则B多加了"内容高度重复"这个判定条件，这就更贴近真实业务场景——刷屏灌水内容的典型特征恰恰是"又长又重复"，而不是单纯"长"。所以规则B不会误伤那些认真写的长篇评价。

由此可以得到一条核心结论：**清洗规则不是"多删等于多干净"，而是"删对地方"。** 每一条规则写出来之后，你自己要能回答一个问题：**这条规则会不会把有价值的真实数据误删？** 如果回答不上来，说明这条规则还不合格，需要重新设计判定依据，而不是急着拿去执行。

### 3.2 阈值不是经验数字，而是业务规则的量化表达

再看另一个例子：数据里 `rating` 字段的合法取值范围是 1–5，但样本里出现了 0 和 6。这个"1–5"的阈值，也是训练师自己拍脑袋定的吗？

不是。这里要区分两种不同来源的依据：

- 有的依据**来自数据本身暴露出的异常模式**——比如"超长 + 高度重复"合在一起才判定为刷屏灌水，这是你通过观察数据总结出来的规律；
- 有的依据**来自字段既定的业务定义域**——评分系统在设计的时候就规定了只能打 1 到 5 分，0 和 6 根本不是这个系统允许产生的合法值，只能是录入环节或埋点环节出了错。这不是训练师主观设定的标准，而是业务系统本来就有的既定规则。

区分"这是我自己设计出的判定条件"还是"这是系统本来就规定好的取值范围"，能帮你快速判断一个阈值到底站不站得住脚、该不该被质疑。

把本节内容浓缩成一句判别口诀：

> **阈值不是经验数字，是业务规则的量化表达。有的依据来自数据本身的异常模式（如长度+重复度组合），有的依据来自字段的既定业务定义域（如评分 1–5）。**

## 四、完整清洗规则该怎么写

有了前面三节的判断力基础，现在可以动手把一套完整的清洗规则写出来了。

### 4.1 规则示例（节选）

下表展示几条规则该如何表达——注意每一条都不是只写"做什么"，还写了"为什么"：

| 处理对象 | 处理方式 | 判定依据（为什么） |
|---|---|---|
| 完全重复记录 | 整行去重 | 重复样本会让模型在训练时对这条特定表述反复加权，产生"虚假共识"的学习信号，造成过拟合 |
| HTML 标签 | 正则剥离 `<...>` | 标签是采集阶段残留的系统噪声，不是用户真实表达；不剥离，模型可能学到"标签符号与情感的伪相关"，而不是文本本身真实的语义 |
| 个人信息（手机号/邮箱） | 替换为占位符，不整条删除 | 整条删除会连带丢掉该样本中其他有效的情感语义；用占位符替换，既满足脱敏合规要求，又保留了样本的可用性——脱敏保护的是隐私，删除会额外损失数据价值，这是两件不同的事 |
| 超长文本（>200字） | 整条剔除 | 经查为刷屏灌水样本而非真实评价；若保留，还会在"文本长度"这个特征维度上引入和情感本身无关的干扰 |
| 非法 rating（不在1–5） | 剔除 | 字段的业务定义域是 1–5，0 或 6 只能是录入或埋点环节出的错，不是真实评分，留着会让模型学习一个根本不存在的标签取值 |

### 4.2 两种写法的正反对比

> ❌ **只写处理方式，不写判定依据**：
> "删除超长文本" —— 这句话本身没有说错，但在实操评分表里，"判定依据"是**独立配分**的一项。光写处理方式，这部分分数拿不到；而且换一批新数据，你自己都答不上来"多长算超长"，这套规则没法复用。

> ✅ **处理方式 + 判定依据**：
> "删除超过200字且内容高度重复的文本，判定依据：经抽样核实为刷屏类好评模板，并非真实详细体验" —— 这句话既说清楚了做什么，也说清楚了为什么能这么做。换一批数据，你依然能复用这套判断逻辑去重新核实、重新套用。

这组对比背后其实是同一条道理：**写判定依据不是为了多写字凑格式，而是让这条规则在换了数据之后依然能被你自己验证、被别人复核。**

### 4.3 清洗代码实现

把上面的规则落实成代码：

```python
import re
import pandas as pd

df = pd.read_csv("../数据集/data.csv")
n_raw = len(df)

df = df.drop_duplicates()
df["review_text"] = df["review_text"].astype(str)
df["review_text"] = df["review_text"].str.replace(r"<[^>]+>", "", regex=True)
df["review_text"] = df["review_text"].str.replace(r"1[3-9]\d{9}", "[手机号]", regex=True)
df["review_text"] = df["review_text"].str.strip()

length = df["review_text"].str.len()
df = df[(length >= 3) & (length <= 200)]
df = df[df["rating"].between(1, 5)]

df.to_csv("data_cleaned.csv", index=False, encoding="utf-8-sig")
print(f"清洗前 {n_raw} 行 → 清洗后 {len(df)} 行")
```

> 完整的清洗规则与代码（含 emoji 处理、空文本处理等全部 9 条规则，实测清洗前 1040 行 → 清洗后 883 行，保留率 84.9%）见试题库实操题 2.1.1 参考答案。本教材重点带你练清楚"设计思路"，下一课题 2-2 会在这份清洗后的数据基础上，继续制定标注规范。

### 4.4 清洗规范文档应该长什么样

写完代码并不算完成——实操考核要求你交付的是一份**完整的清洗规范文档**，光有代码没有文字说明，评分表里相应的分数是拿不到的。一份合格的清洗规范文档至少要包含四个要素：

```
一、适用范围与清洗目标
二、逐条规则（处理对象 + 处理方式 + 判定依据）
三、例外情形
四、产出字段说明（清洗前后数据量对比）
```

动手写的时候，建议对照着自查一遍：

1. 每条规则是不是都写明了判定依据，而不仅仅是写了处理方式——这是整个清洗规范文档里最核心的评分点。
2. 代码是不是真的输出了清洗前后的数量对比，并且**各类问题各自命中的记录数**分别是多少（不能只甩一个笼统的总数，谁也看不出到底清掉了什么）。
3. 警惕"两行代码思维"复发——如果你写完之后发现自己的规则其实还是只覆盖了"重复"和"缺失"两类，先回头想想第二节里那 117 条问题去哪了。

## 五、进阶能力：复核别人写的清洗规则

本课题除了要求你自己能设计规则，三级标准里还单独要求一项能力：**看别人写的清洗规则，判断它是否可能误删有价值的数据**。这项能力和"自己会写"是两回事——很多人自己写规则时很谨慎，但审查别人的规则时却容易只看格式是否齐整，不去深究判定依据是否站得住脚。

下面几种情况是实际审查中常见的问题，你可以把它们当作一份自检清单，以后无论是复核别人的文档，还是倒回头检查自己的文档，都可以照着这几条过一遍：

| 常见问题 | 该怎么质疑/怎么改 |
|---|---|
| 把"超长文本删除"的依据写成"太长了不合理" | "不合理"是谁定的标准？能不能换成"经查为刷屏重复内容"这种可以被验证、可以被复查的依据？ |
| "个人信息"的处理方式写的是"删除"（整条删） | 回想第一节的判别口诀——信息需要处理，但剩下的内容还有没有价值？整条删除是不是把情感语义也一起丢掉了？按口诀这里该用"替换"而不是"删除" |
| 规则覆盖不全，漏了 emoji 或非法评分这类问题 | 对照自己亲手抽样时看到的真实问题清单，看对方的规则是不是漏掉了某一类真实存在的问题 |

审查的时候，请始终用同一把尺子去衡量——**这条规则会不会误删有价值数据**，而不是只看格式是否整齐、代码能不能跑通。格式整齐、代码能跑，和判定依据是否站得住脚，是完全独立的两件事，评分表里也是分开计分的。

## 考点清单

| 考点 | 考试怎么考 | 易错点 |
|---|---|---|
| 清洗规则的业务依据 | 实操核心评分点，独立配分 | 只给数值阈值、不说明依据，光写处理方式不写"为什么" |
| 处理方式选择（删除/替换/标记） | 实操 | 该标记/替换的情形被直接删除，造成有效样本的语义损失 |
| 规范文档结构 | 实操 | 只写清洗代码、不写可交付的规范文档，缺"适用范围""例外情形"等要素 |
| 阈值依据的两种来源 | 理论+实操 | 混淆"自己设计的判定条件"和"系统既定的业务定义域"，把本该质疑的阈值当成理所当然 |
| 复核他人规则的能力 | 理论+实操 | 审查时只看格式是否齐整，不深究判定依据是否会误删有价值数据 |

## 小结

读完本教材，用下面这张表回顾一遍核心逻辑：

| 要点 | 一句话 |
|---|---|
| 清洗本质 | 设计规则，不是套用模板 |
| 核心原则 | 阈值要有业务依据，不能拍脑袋 |
| 自检方法 | 每条规则问自己：会不会误删有价值数据？ |
| 处理方式判别 | 会损失语义 → 替换；不会 → 删除；拿不准 → 标记 |
| 实测教训 | `dropna()` 认不出空字符串，两行标准代码连四分之一的问题都处理不了 |
| 文档要素 | 适用范围 → 逐条规则(对象+方式+依据) → 例外情形 → 产出字段说明 |
| 进阶能力 | 不仅自己会写规则，还要能审查别人的规则是否误删数据 |

把这句话记在心里，作为整个课题最浓缩的提炼：

> **"清洗完了吗"这句话，答案不取决于你调用了几个函数，而取决于你能不能对每一类问题说清楚"为什么这样处理"。调用标准函数处理的是你认识的问题，而真实数据里，大部分问题是函数认不出来的。**

下一课题（2-2）会在这份清洗后的数据基础上，继续解决下一个问题：怎么设计一份标注规范，并用量化指标证明标注员标得靠谱。

## 随堂练习（自测，可直接核对答案）

**练习 1**：清洗规则"删除所有包含数字的评价文本"是否合理？为什么？

**答案**：不合理。包含数字的评价可能是真实有效信息（如"用了3天就坏了"），该规则会误删大量有价值数据。应该针对具体问题（如手机号、邮箱这类个人信息）做定向处理，而不是用"包含数字"这种过度宽泛的条件一刀切。

**练习 2**：为什么"删除超过100字的评价"和"删除超过200字且内容高度重复的评价"这两条规则，后者更合理？

**答案**：前者是武断的一刀切，会把用户认真写的详细使用体验也误删，因为评价长度本身不是判断垃圾内容的可靠依据。后者加了"高度重复"这个判定条件，贴近真实业务场景（刷屏灌水的典型特征是内容重复），不会误伤真实的长篇评价。

**练习 3**：制定清洗规则时，自我检验的核心问题是什么？

**答案**：这条规则会不会把有价值的真实数据误删？每条规则写出来后都要能回答这个问题，回答不上来说明规则本身需要重新设计判定依据，而不是急于执行。

**练习 4**：清洗规范文档应包含哪些要素？只写清洗代码是否足够？

**答案**：应包含适用范围、逐条规则（对象+处理方式+判定依据）、例外情形、产出字段说明。只写代码不够——实操评分表中，"判定依据"是独立于代码正确性之外的单独配分项，没有文字说明依据，即使代码跑通了也不能拿满分。

**练习 5**：含手机号、邮箱的评价样本，应该整条删除还是用占位符替换？为什么？

**答案**：应该用占位符替换（如替换为"[手机号]"），而不是整条删除。因为整条删除会损失该样本中其他有价值的情感语义信息，而用占位符替换既满足脱敏合规要求，又保留了样本的可用性，是更精细化的处理方式。
