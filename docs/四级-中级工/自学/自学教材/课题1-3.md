## 一、处理方法怎么选：三个问题框架

拿到一份有缺失值、有异常值的数据，不要凭感觉套用"填充"或"删除"模板，而是依次问自己三个问题。

### 第一问：缺多少，这个字段重不重要？（决定删除还是填充）

如果缺失比例很高——比如超过一半——而且这个字段对后续分析非常关键，再怎么估算都不可信，这种情况下不如整体删除这些记录或者明确标记出来，**不要硬填一个数字冒充真实数据**，因为填进去的数字已经失去了参考意义，反而可能误导后续分析。

但如果缺失比例可以接受，比如课题1-1检测出的销售额缺失15%、会员等级缺失18%，这种程度优先考虑填充，把本来可用的样本保留下来，而不是因为一小部分缺失就把整条记录连带其它完好的字段一起扔掉。

### 第二问：分布是什么形状？（决定均值还是中位数）

这是课题1-1已经验证过的结论：对称分布用均值没问题；长尾/偏态分布——比如本课数据里的销售额，被少数大额订单拉得很偏——用均值会被极端值带偏，必须改用中位数。

还记得那个反差吗？**销售额均值3689.6，中位数194.0，相差近19倍**。这组数字会在本课反复出现，因为它既是判断"用均值还是中位数"的依据，也是后面说明"错误处理有多危险"的关键证据。

**为什么均值会被极端值带偏，中位数不会？** 均值是把所有数值加起来除以个数，极少数特别大的数值会把总和显著拉高，从而拉高整体均值；中位数是把数据排序后取中间位置的值，极端值无论多大多小，都只是排在队伍的最前面或最后面，不影响"中间位置"落在哪里。这就是为什么长尾分布下，中位数比均值更能代表"大多数记录的真实水平"。

### 第三问：记录之间有没有顺序关系？（决定能不能用前向填充）

前向填充（`ffill`）的逻辑是：用前一条记录的值顶替当前缺失值。这个假设只有在记录之间**真的存在时间或空间上的连续性**时才成立——比如同一台设备按时间顺序连续采集的传感器读数，中间短暂断了几次，用前一个读数顶上通常合理，因为物理量不会突变，前后读数大概率接近。

但本课的订单数据不是这种情况。**问自己一句：这份订单数据，每一条记录之间是不是互相独立的？** 上一条订单的销售额和下一条订单之间毫无因果关系——张三今天买了200元的东西，不代表李四下一单也会买200元左右。如果按录入顺序，把第5条订单的缺失值填成第4条订单的销售额，这个数字和第5条订单本身没有任何关系，相当于**凭空捏造了一种本不存在的因果关系**，是典型的用错场景。

**三问小结（判别口诀）**：

> **先问比例和重要性决定删不删；再问分布形状决定均值还是中位数；最后问有没有顺序关系决定能不能用前向填充。**

## 二、数量级错误 vs 正常长尾高值：这是本课的核心难点

### 先动手验证

打开 Jupyter，运行下面这段代码，按SKU分组算一下销售额均值，看能不能找到异常：

```python
import pandas as pd
d = pd.read_csv("../数据集/cosmetics_sales.csv")
sku_mean = d.groupby("SKU")["销售额"].mean().sort_values(ascending=False)
print(sku_mean.head(5))
```

**实测输出（已验证）**：

```
SKU003    39700.6
SKU022    28900.9
SKU011    27164.2
...
```

SKU003均值39700.6、SKU022均值28900.9、SKU011均值27164.2，而正常SKU均值通常在800-900左右——**相差约30-45倍**。

### 这不是正常波动，是数量级录入错误

这个量级的偏离（30-45倍），不是正常的销售波动能解释的，更可能是数量级录入错误（比如单价多打了两个零，或者数量单位搞混）。

**判别依据**：偏离正常范围的倍数是否离谱。正常业务波动造成的长尾高值通常是几倍到十几倍的差异（比如大客户批量采购确实会比普通订单高出不少），而30-45倍这种量级的差异，已经远超正常业务能解释的范围。

### 关键问题：发现这几个SKU偏高，能不能直接用中位数"拉平"？

**不合理**。这是**错误数据**，应该先排查确认是否为数量级录入错误（如核实原始价格表，看是不是价格多了一两个零），核实后应**按正确值修正**，而不是用统计手段掩盖。

这里的核心逻辑是：**统计手段（中位数替代）适用于处理正常数据的填充或极端值问题，不适用于已确认的录入错误**。这两者处理的前提完全不同——

- **统计手段掩盖**（如用中位数替代异常值）：处理的前提是数据本身没有错误，只是数值比较极端，这种处理不改变数据的"真实性"假设；
- **核实修正**：针对的是确认存在的录入错误，处理的是"数据本身就是错的"这个事实。

把录入错误当作正常极端值用统计手段处理，相当于用一个编造的数字掩盖了真实的错误，**而没有真正解决问题根源**——掩盖问题和解决问题是两回事。

### 发现错误之后，还要多问一句

发现一处数量级错误后，不要只改掉已发现的这几条就结束，还要问：**是不是还有同类遗漏？** 核实这批错误是否集中出现在某个录入环节或时间段（比如是不是某个门店、某个时间段的录入员统一出了问题），排查有没有其他未被发现的类似记录。只修复已经暴露的个案，而不去追查根因和同类问题，是数据处理中很容易留下的隐患。

### 回到开头的判断题

现在回答本课开头的判断题：小李的那份报告，能通过吗？

答案应该是**不能通过**。小李统一用中位数替换异常值，恰恰是把录入错误当成了正常数据来掩盖，核实过程完全被跳过了。如果你一开始的判断是"能通过"，这正是本课要纠正的典型直觉误区——"处理了就等于处理对了"。下一节会用具体数字告诉你，这种误区的后果有多严重。

## 三、方法用错比不处理更糟：一个具体的后果推演

很多人觉得"好歹做了处理，总比放着不管强"。下面用一个具体案例检验这句话对不对。

还记得第一节提到的那组数字吗：**销售额均值3689.6，中位数194.0**。假设销售额缺失的那120条记录，一律用均值3689.6去填充——而这批记录大多数真实水平在一两百元左右（参照中位数194.0）——会发生什么？

**具体错在哪**：这120笔本来一两百元的普通订单，被"包装"成了近3700元的大单。如果后续按门店统计业绩、算员工提成，这批被污染的数据会让涉及较多这批记录的门店或SKU业绩虚高。

### 对比两种处理方式，哪个危害更大

现在对比两种情况：

| 处理方式 | 后续使用者能否察觉 | 后果 |
|---|---|---|
| 销售额留空（NaN） | 能——任何人统计前都能一眼看到"这里有120条缺失" | 知道这部分结果需要打问号，会谨慎对待，甚至主动排查 |
| 统一填成均值3689.6 | 不能——填进去的数字"看起来很正常" | 混入正常数据后根本无法分辨，业绩、提成等下游计算被悄悄污染 |

**留空的数据，至少是一个"看得见的缺口"**，知道这部分需要谨慎对待；**而错误的处理方法，把一个"看得见的缺口"变成了一个"看不见的污染"**——填进去的数字看起来很正常，混入正常数据后根本无法分辨，比留白更难被发现、更难挽回。

### "方法用错比不处理更糟"的真正含义

这句话不是说"随便处理一下也比什么都不做强"，而是：**错误的处理可能制造出一个比原问题更隐蔽、更难纠正的新问题**。

> **判别口诀**：错误处理的危险，在于它把可见的问题变成了不可见的污染。

## 四、一致性问题的处理：门店编码归一化

除了缺失值和数量级错误，数据还常见另一类问题——同一个真实对象，被不同的写法记录成了"不同的东西"。

**动手验证**：

```python
d["门店编码"] = d["门店编码"].str.upper()
print(d["门店编码"].value_counts())
```

**实测结果**：归一化前，门店编码有8种取值（大小写混用，比如S001和s001被当成两家不同的门店）；归一化后（统一转大写）合并为4种取值，S001-S004分别为192/205/204/199条，分布趋于均衡合理。

**为什么要做这一步**：归一化前，S001和s001是同一家门店，只是录入时大小写不统一，却被当成两家门店分头统计——真实的单店业绩被人为拆分、低估了。归一化后合并为一个S001，才反映出真实的门店体量。

这也是本课"怎么评估优化有没有效果"的一个具体例子：**不是看代码跑没跑通，而是看优化后的数字是不是更接近业务真实情况。**

**判别口诀**：这类问题属于数据质量六维度中的"一致性"问题——同一个含义的数据用了多种不同写法表示，归一化让同一含义的数据合并统计，才能得到真实情况。

## 五、处理效率优化：不只是"对不对"，还有"快不快、省不省"

前面讲的都是"处理方法选得对不对"。本课题还有同样重要的另一面——处理方法**跑得快不快、占用内存多不多**。数据处理方法优化，优化的不只是结果，也包括过程的效率。这是很多初学者容易忽略的维度：只要代码能跑出正确结果，就觉得"做完了"，不会再去想效率问题。

### 方向一：向量化替代循环

**动手验证**：

```python
import timeit
discount_map = {"黄金": 0.9, "白银": 0.95, "普通": 1.0}

def loop_version(df):
    out = []
    for idx, row in df.iterrows():
        rate = discount_map.get(row["会员等级"], 1.0)
        out.append(row["销售额"] * rate)
    return pd.Series(out, index=df.index)

def vector_version(df):
    rate = df["会员等级"].map(discount_map).fillna(1.0)
    return df["销售额"] * rate

t_loop = timeit.timeit(lambda: loop_version(d), number=20)
t_vec = timeit.timeit(lambda: vector_version(d), number=20)
print(f"循环版本单次均值: {t_loop/20*1000:.3f} ms")
print(f"向量化版本单次均值: {t_vec/20*1000:.3f} ms")
```

**实测结果（Python 3.11.17 + pandas 2.3.3 已验证）**：循环版本单次均值约 **10.4 ms**，向量化版本约 **0.2 ms**，**快约52倍**。

**为什么差这么多**：循环版本每处理一行，都要经过一次Python解释器的调度开销；向量化版本把整列数据一次性交给pandas底层（用C实现）批量运算，解释器开销只发生一次，不是发生800次。**数据量越大，这个差距会被成倍放大**——如果数据量从800条涨到80万条，循环版本的耗时会线性增长到约1000倍，而向量化版本的优势会更加明显。

**一个常见陷阱——`apply` 不等于向量化**：有些人会用 `df.apply(lambda row: ...)` 来代替 `for` 循环，以为这样就是"向量化"了，但这是误区。`apply` 内部本质上仍然是在逐行调用你写的函数，速度提升非常有限，是典型的"伪向量化"。真正的向量化，是像上面 `vector_version` 里的 `map` 这样，让pandas的底层运算直接作用在整列数据上，而不是你自己写代码一行行去调用。

### 方向二：分块处理大文件

如果数据文件大到内存放不下——比如上千万条记录——可以用 `pd.read_csv(path, chunksize=10000)` 分块读取，每次只加载一小块进内存处理，再汇总结果。本课800条数据用不上这个技巧，但数据量上一个量级，这是必备手段。

### 方向三：字段类型降存

**动手验证**：

```python
before = d.memory_usage(deep=True).sum()
d2 = d.copy()
d2["门店编码"] = d2["门店编码"].str.upper().astype("category")
d2["会员等级"] = d2["会员等级"].astype("category")
d2["SKU"] = d2["SKU"].astype("category")
d2["销售数量"] = d2["销售数量"].astype("int8")
after = d2.memory_usage(deep=True).sum()
print(f"优化前: {before}字节, 优化后: {after}字节, 降幅: {(1-after/before)*100:.1f}%")
```

**实测结果（已验证）**：优化前 278756 字节，优化后 119226 字节，**降幅约57.2%**。

**原理**：数值范围小的字段（如本课"销售数量"取值范围是 -7~7）用小类型（如 `int8`，范围 -128~127）就够用，不需要默认的 `int64`；文本重复度高的字段（如门店编码、会员等级、SKU，取值种类少但重复出现很多次）用 `category` 类型存储，底层只存一份取值清单加索引，而不是把重复的字符串原文存很多遍。

**但要注意"够用但留余量"**：`int8` 的范围是 -128~127，本课数据销售数量范围是 -7~7，目前够用。但如果以后业务扩大，单笔销售数量可能超过127，这时候还硬用 `int8` 就会发生溢出或报错。**类型降存不能只图当前数据集下最小，要结合业务未来可能的取值范围留出合理余量**，先看取值范围，再选类型，而不是不假思索把所有整数列都降到最小类型。

**判别口诀**：

> **向量化：批量交给底层算，别一行行自己跑。类型降存：数值范围小就用小类型，文本重复多就用category。**

## 六、怎么评估一次处理方法优化是否真正有效

判断一次处理方法优化是否真正有效，**不能只看"代码没报错"**，要有具体的前后对比：

```
处理方法对不对 → 对比优化前后的数据分布统计量 / 下游指标
处理效率高不高 → 对比优化前后的运行耗时 / 内存占用，用具体数字说话
```

### 成本权衡：是不是所有优化都值得做

本课在800条数据上实测：循环10.4ms、向量化0.2ms。这个差距，在实际工作中几乎感觉不出来——那是不是这个优化就没必要做？

答案是**看情况**。如果这批数据以后涨到几十万条，每天要批量跑几十次，几毫秒的差距会被放大成实实在在的等待时间，这时候优化就有意义。但同时也要考虑维护成本——比如为了引入 `category` 类型，还要考虑"后续出现原来没有的新类别值会报错"这类维护成本。在小数据、低频场景下，这个成本可能比收益还大。

**真正值得优化的，是数据量大、运行频率高、已经成为瓶颈的场景，不是逢优化必做。**

> **判别口诀**：数据量小、偶尔跑一次 → 不必为了优化而优化；数据量大、高频运行 → 效率优化的收益会被放大，值得投入。

## 七、三个典型误用案例自测

在继续往下读之前，先用下面三个真实会出现的案例检查一下自己是否真的理解了前面的内容。每个案例都对应前面讲过的一个知识点，尝试自己先诊断出问题，再看解析。

| 案例 | 场景描述 | 应诊断出的问题 |
|---|---|---|
| A | 对销售额这类长尾分布字段的缺失值，直接用均值填充 | 方法用错——长尾分布应改用中位数，均值会被极端值带偏（对应第一节"第二问"） |
| B | 对互相独立的订单记录，用前向填充补缺失的销售额 | 场景不适用——订单之间无顺序关系，前向填充相当于编造因果关系（对应第一节"第三问"） |
| C | 用 `for` 循环 + `if` 判断实现折扣计算，结果完全正确 | 结果对但效率低——不是只有算错了才需要改，效率低下在数据量变大后同样是问题（对应第五节） |

案例C尤其容易被忽略：很多人只在"结果算错了"的时候才会想到要改代码，但"正确但低效"同样是需要被识别和优化的情形。

## 本课题考点清单

| 考点 | 考试怎么考 | 易错点 |
|---|---|---|
| 数量级错误识别 | 实操核心 | **把录入错误和正常长尾分布混为一谈，都用统计手段处理** |
| 处理方法适用边界 | 单选/实操 | 不加区分地套用"填充/删除"模板，忽略缺失比例、分布形状、顺序关系这三个判断依据 |
| 方法用错比不处理更糟 | 单选/判断 | 误以为"做了处理总比不处理强"，忽视错误填充造成的"不可见污染" |
| 一致性问题处理 | 实操 | 不理解归一化解决的是哪类数据质量问题 |
| 向量化 vs 循环 | 实操 | 把 `apply` 误当作向量化，实际仍是逐行调用，速度提升有限 |
| 字段类型降存 | 实操 | 不假思索把所有整数列都降为最小类型，不考虑未来取值范围变化导致溢出 |
| 优化效果评估 | 简答/实操 | 只看"代码跑通"，不做优化前后的量化对比；不考虑维护成本和适用场景（成本权衡） |

## 自测练习（含答案）

**练习 1**：某SKU的销售额均值是其他同类SKU均值的35倍，正确的处理思路是什么？

**答案**：先核实是否为数量级录入错误（如价格多打了零），而非直接用中位数或其他统计手段替代掩盖。确认是错误后应按正确值修正；若核实后确实是真实的高价值SKU（如限量高端产品），则保留原值，不作处理。

**练习 2**：为什么说"统计手段掩盖"和"核实修正"是两种完全不同性质的处理方式？

**答案**：统计手段掩盖（如用中位数替代异常值）处理的前提是数据本身没有错误、只是数值比较极端，这种处理不改变数据的"真实性"假设；而核实修正针对的是确认存在的录入错误，处理的是"数据本身是错的"这个事实。把录入错误当作正常极端值用统计手段处理，相当于用一个编造的数字掩盖了真实的错误，而没有真正解决问题根源。

**练习 3**：区分"正常长尾高值"和"数量级错误"的判别依据是什么？

**答案**：偏离正常范围的倍数是否离谱。正常业务波动造成的长尾高值通常是几倍到十几倍的差异（比如大客户批量采购），而30-45倍这种量级的差异，已经远超正常业务能解释的范围，更可能是价格多打了一两个零这类录入错误。

**练习 4**：门店编码"S001"和"s001"归一化之后，记录数从8种取值合并为4种，这一步解决的是数据质量六维度中的哪个问题？

**答案**：一致性问题——同一个门店用了两种不同的大小写书写方式表示，归一化（统一转大写）让同一含义的数据合并统计，才能得到真实的门店分布情况。

**练习 5**：发现数量级错误后，除了修正当前这条记录，还应该做什么？

**答案**：应该检查是否存在同类遗漏——比如核实这批数量级错误是否集中出现在某个录入环节或某个时间段，排查是否还有其他未被发现的类似错误记录，而不是只修正已经发现的这一条就结束。

**练习 6**：用 `df.apply(lambda row: ...)` 和用 `df["列"].map(...)` 都能完成同样的折扣计算，为什么说前者不是真正的向量化？

**答案**：`apply` 对一个DataFrame逐行应用函数时，内部本质上仍然是在逐行调用你写的函数，每一行都要经过一次Python层面的函数调用开销，速度提升非常有限，是典型的"伪向量化"。而 `map` 这种按值映射的写法，是把整列数据一次性交给pandas底层（C实现）做批量运算，解释器开销只发生一次，而不是发生800次（或更多次），这才是真正的向量化。

**练习 7**：把"销售数量"字段从 `int64` 降为 `int8` 需要注意什么？

**答案**：需要先确认该字段的实际取值范围是否在 `int8` 的表示范围（-128~127）之内。本课数据销售数量范围是 -7~7，目前够用，但如果以后业务扩大、单笔销售数量可能超过127，继续用 `int8` 会发生溢出或报错。类型降存要"先看取值范围，再选类型"，并为未来可能的业务变化留出合理余量，不能只图当前数据集下最小。

**练习 8**：本课在800条数据上实测，循环处理耗时10.4ms、向量化处理耗时0.2ms，这个差距在日常工作中几乎无感知，是不是说明这项优化没有必要做？

**答案**：不一定，要看数据量和运行频率。如果数据量保持在几百条、偶尔跑一次，这种优化确实收益有限，甚至可能因为引入 `category` 等类型而增加维护成本（比如后续出现新类别值会报错）。但如果数据量以后涨到几十万、几百万条，且每天要批量运行多次，几毫秒的差距会被放大成实实在在的耗时差异，这时候优化就有必要。判断是否值得优化，要看"数据量是否够大、运行是否够频繁"，而不是一概而论。

## 小结

| 要点 | 一句话 |
|---|---|
| 处理方法三问 | 比例和重要性决定删不删；分布形状决定均值还是中位数；顺序关系决定能不能用前向填充 |
| 数量级错误 vs 正常长尾 | 偏离倍数是否离谱（30-45倍提示录入错误，应核实修正而非统计掩盖） |
| 方法用错的代价 | 错误处理把"看得见的缺口"变成"看不见的污染"，比不处理更危险 |
| 一致性问题 | 归一化（如统一大小写）让同一含义的数据合并统计，还原业务真实情况 |
| 效率优化三方向 | 向量化替代循环、分块处理大文件、字段类型降存（注意为未来取值范围留余量） |
| 效果评估 | 既要看"处理方法对不对"（数据分布/下游指标），也要看"处理效率高不高"（耗时/内存），并权衡优化的维护成本与收益 |
