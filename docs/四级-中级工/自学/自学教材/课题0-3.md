## 一、先把地基打牢：三大学习范式 + 训练/验证/测试集

在动手写代码之前，有两个概念性的知识点要先打底，它们是后面所有课题（包括数据标注、模型训练质量判断）都会用到的通用语言。

### 1. 判断一个任务属于哪种范式，不要去记任务名字

很多人学这部分的方式是硬背"图像分类是监督学习、推荐系统是强化学习"这种一一对应的例子，但题目只要换一个没见过的场景就容易蒙。更可靠的办法是：不要去记任务名字，去问自己**一句话**——

> **这个任务有没有预先固定的标准答案？**

- 有标准答案 → **监督学习**。比如拿已经标好"猫/狗"的图片去训练分类模型——标签就是预先固定好的标准答案。
- 没有标准答案，但数据本身有结构可以被发现 → **无监督学习**。比如不告诉算法任何分类标准，让它自己把十万条客服对话按相似度分成几群——没有人提前告诉它"应该分成几类、每类叫什么"。
- 没有标准答案，但有一个不断反馈的信号（奖励/惩罚）→ **强化学习**。比如推荐系统根据用户是否点击、是否停留，动态调整下一次的推荐策略——它不知道"正确答案"是哪个商品，但每次推荐后都会收到一个反馈信号，用这个信号去调整自己。

**判别口诀**：有答案 → 监督；没答案但有结构 → 无监督；没答案但有反馈 → 强化。

自己练一下，判断下面三个场景各属于哪种范式（答案见本节末尾）：
1. 自动驾驶车辆根据路况不断试错，调整转向策略；
2. 给10万条客服对话按相似度自动分组，不预先规定要分成几类；
3. 给带标签的商品图片训练一个分类器。

> 答案：1 强化学习（有反馈信号，没有预先标准答案）；2 无监督学习（没有标签，靠数据结构自己聚类）；3 监督学习（标签就是预先固定的标准答案）。

### 2. 训练集 / 验证集 / 测试集：为什么要切成三份

一个模型项目通常要把数据切成训练集、验证集、测试集三份，而不是一份数据反复用：

- **训练集**：用于模型学习参数；
- **验证集**：用于调参和判断该不该提前停止训练（避免过拟合）；
- **测试集**：用于最终评估模型的真实效果。

**关键问题来了：为什么不能把测试集也拿来调整模型？** 设想一下，如果你拿测试集的反馈结果去反过来调整模型参数，会发生什么？——测试集一旦参与了"调整"这个动作，它实质上就变相参与了训练过程。之后你再用它来做"最终评估"，得到的高分只是"模型已经偷偷记住了测试集长什么样"的结果，并不能说明模型在**真正没见过的数据**上表现如何。

留意一下，这和开头那道判断题其实是**同一类陷阱**：**看到的好结果，可能是假象**。数据"看起来规整"不代表能用，模型"测试分数高"也不代表真的学会了。这条主线会在接下来的 pandas 实操里反复出现，记住它。

## 二、写给第一次接触代码的你：怎么"看懂"一行代码

如果你已经有 Python 基础，这一节可以快速扫过；如果你是第一次正经接触代码，请不要跳过——接下来整课会出现大量代码，但这里不要求你先"背语法"，只要求你先做到**看懂一行代码在干什么**。

代码不是数学公式，而是**一句一句的"操作指令"**，可以直接念成中文。看下面三行：

```python
import pandas as pd              # 第1行：把pandas这个工具箱借过来，取个简称叫pd
df = pd.read_csv("data.csv")     # 第2行：用pd工具箱里的read_csv功能，把一个csv文件读进来，存进df这个名字
print(df.head())                 # 第3行：看一下df的前几行长什么样
```

念出来就是："把 data.csv 这个文件读进来，叫它 df"、"看看 df 前几行"。你暂时不需要会手写这几行代码，先练一个小动作：给你任意一行代码，你能不能用大白话说出它在做什么？

一个小技巧：遇到不认识的函数名，先别慌，看它的英文动词部分——`read_csv` 的 `read` 就是"读"，`to_csv` 的 `to` 就是"写到"，`drop_duplicates` 的 `drop` 就是"丢弃"。英文函数名大多是"动词+对象"的结构，先抓住动词，猜个大概方向，再去查具体用法，比死记硬背每个函数名要轻松得多。

再给自己一个小测验：如果把上面第2行的 `read_csv` 换成 `read_excel`，你猜这行代码会变成读什么格式的文件？——答案是 Excel 文件，这就是"举一反三"：函数名里的线索往往比你想象的更直白。

> 💡 **给零基础读者的定心丸**：下面所有代码都配了"已验证"的真实运行结果，你不需要凭空想象代码会输出什么。遇到报错或结果对不上，大概率是环境配置或路径写法的问题，不是你"学不会代码"——这一点在下一节读数据时会具体讲到。

## 四、numpy：pandas 的底层引擎

课题名字里还有一个"numpy"，容易被忽略，但值得单独说清楚。

你可能会问：一直在用 pandas，为什么还要学 numpy？**因为 pandas 的 Series，本质上就是一个带了索引标签的 numpy 数组。** 每次你对一整列做批量运算（比如把销售额整列打折），背后真正在计算的就是 numpy。

```python
import numpy as np

arr = np.array([1, 2, 3, 4, 5])
print(arr * 2)                     # 向量化运算：整个数组同时乘2，不需要写for循环
print(arr.mean(), arr.sum())       # 常用统计函数

# 对比：pandas整列运算背后就是numpy在工作
print((df["销售额"] * 1.1).head())  # 整列打九折后再涨价10%，不需要逐行写循环
```

**为什么要用"整列一起算"（向量化），而不是写 `for` 循环逐条处理？** 机制是这样的：如果用循环逐条处理成千上万甚至几十万条记录，Python 解释器要一行一行地重复做类型判断和函数调用，开销会随数据量线性甚至更快地增长；而向量化运算是把整批数据一次性交给底层更高效的实现去批量处理，省掉了逐条调度的开销。**数据量越大，这个差距越明显**——这也是 pandas 能处理几十万、上百万行数据依然能跑得动的根本原因。

建议你自己动手跑一下：对 `df["销售数量"]` 做一次向量化运算，比如 `df["销售数量"] * 10`（模拟"件数换算成某单位"），观察输出是整列同时变化，而不是一条条变化。

**判别口诀**：遇到"要不要写 for 循环处理一整列数据"的场景，先问自己——这个操作能不能表达成"对整列做同一种运算"？能 → 用 pandas/numpy 的向量化写法；需要逐行引用"上一行的结果"这类强依赖关系 → 才考虑循环。

**板书式小结**：pandas 的 Series = 带索引的 numpy 数组；向量化运算用整体替代逐条循环。

## 五、缺失值 / 重复值 / 异常值：别急着套公式

回到开头的悬念。现在正式"体检"这批数据，看看到底藏了哪些问题：

```python
import pandas as pd
d = pd.read_csv("../数据集/cosmetics_sales.csv")

print("销售额缺失:", d["销售额"].isna().sum())
print("会员等级缺失:", d["会员等级"].isna().sum())
print("整行重复:", d.duplicated().sum())
print("订单号重复:", d["订单号"].duplicated().sum())
print("销售数量<=0的条数:", (d["销售数量"] <= 0).sum())
print("销售数量 最小值/最大值:", d["销售数量"].min(), d["销售数量"].max())
print("均值:", d["销售额"].mean().round(1), " 中位数:", d["销售额"].median())
```

实际运行结果（已验证，你的运行结果应该完全一致）：

```
销售额缺失: 120           （占比15%）
会员等级缺失: 144         （占比18%）
整行重复: 0
订单号重复: 0
销售数量<=0的条数: 24
销售数量 最小值/最大值: -7 7
均值: 3689.6  中位数: 194.0
```

这一次性暴露了三类问题，下面逐个拆解——每一类的处理方式都不一样，不能用一套公式套所有情况。

### 1. 缺失值：先别急着填均值

拿到15%缺失的销售额字段，很多人的第一反应是"用均值填充"。但填充之前，先看一眼这个字段的分布——**均值 3689.6，中位数只有 194.0，两者相差近 19 倍**。这个巨大的反差本身就是一个警报信号：**真实数据不是均匀分布的，而是长尾分布**（多数订单金额不高，少数大额订单极高）。

| | 用均值填充 | 用中位数填充 |
|---|---|---|
| 本例计算值 | 3689.6 | 194.0 |
| 是否受少数大额订单影响 | **是**，被拉高近19倍 | 否，不受极端值影响 |
| 填进缺失样本后的效果 | 把普通订单错误地"拔高"成大额订单水平 | 更接近这批数据"典型"的真实水平 |

如果不假思索地用均值 3689.6 去填充那 15% 的缺失值，相当于把"少数大额订单硬塞给了大多数本该是普通订单的缺失记录"，这会**系统性地高估**这批样本的真实水平——后续任何基于这批数据的统计、建模都会跟着失真。

正确的决策顺序，是一棵决策树，不是一个万能公式：

1. **能不能补录**（比如联系原始数据源核实）？能补录就优先补录；
2. 不能补录，这批缺失数据占比大不大、删除影响大不大？**影响小可以直接删除**；
3. 必须填充时，再看字段的分布形态——**均值和中位数差异这么大，就是长尾分布的警报信号**（少数大额订单把均值拉得很高），长尾分布用中位数更稳健，均值会被极端值带偏。

### 2. 类别型缺失：连"均值/中位数"这个选项都不存在

再看会员等级缺失 144 条，占比 18%，比销售额缺失的比例还高。能不能也套用"均值/中位数"的思路？**不能**——会员等级是"普通/白银/黄金"这类类别，根本没有数值意义上的"均值"可言。类别型字段缺失的常见做法是：归入一个明确的新类别（如"未知/未注册"），或结合业务规则判断——比如这批缺失是不是"未注册会员"本来就没有等级，那就不是真正意义上的"缺失"，而是业务规则决定的正常空值。

你可以自己动手验证一下这个"NaN单独成一类"的现象：

```python
print(d["会员等级"].value_counts(dropna=False))
```

> 🔑 **判别口诀**：字段是数值型还是类别型？数值型 → 看分布形态选均值/中位数；类别型 → 根本没有均值/中位数可选，要么归为明确的新类别，要么按业务规则判断是否属于正常空值。

### 3. 重复值：查出来是 0，不代表这一步可以跳过

本例"整行重复"和"订单号重复"都检测为 0 条。这是不是意味着"重复值"这个知识点在这份数据里用不上，可以跳过？**不是**。检测的意义不在于"一定要找到问题"，而在于**系统性地把每一类问题都查一遍**——有问题就处理，没问题也要在质检报告里明确写清楚"已检测、无重复"。如果因为这次没查出问题就跳过这一步，下一批数据如果真的存在重复记录，同样的疏漏会被重复放大，而且没有任何检测记录可以证明这一批数据到底查没查过。

```python
print(d.duplicated().sum())
d = d.drop_duplicates()   # 真的存在重复行时才会删掉；本例是0行，不影响数据
```

### 4. 异常值：不是所有"奇怪的数"都直接删

`销售数量` 最小值是 -7，最大值是 7，其中有 24 条记录销售数量小于等于 0——这明显不符合业务常识（销售数量不可能是负数）。但"异常"不等于"立刻删除"：负数销售数量很可能对应"退货/录入异常"这类有业务含义的记录，直接删除会丢失"退货发生了多少次"这类信息；更合理的做法往往是先判断这 24 条记录的业务含义，再决定是单独标记统计，还是确认为纯录入错误后再删除。

**异常值处理和缺失值处理是同一种思路：先搞清楚"为什么会出现这个异常"，再决定怎么处理，而不是看到数字不对劲就一删了之。**

### 本节总结一句话

**这节课最该记住的一课：看到均值和中位数差异很大，就是一个警报信号，提示这个字段可能是长尾分布，不能无脑套用均值填充的默认做法；而类别型字段的缺失，连"均值/中位数"这个选项都不存在，要先判断它是不是业务规则导致的正常空值。** 重复值和异常值也遵循同一个原则——先搞清楚问题的性质和业务含义，再决定处理方式，而不是用一套固定公式打遍天下。

## 六、分组聚合遇到的怪事，根子在字符串格式

体检做完了，现在学一个新能力：**按类别汇总**。假设想知道每个门店的销售额表现，直接 `groupby` 一下：

```python
agg = d.groupby("门店编码")["销售额"].agg(["mean", "sum", "count"])
print(agg.round(1))

pivot = d.pivot_table(index="门店编码", columns="会员等级", values="销售额", aggfunc="sum")
print(pivot.round(1))
```

实际运行结果（已验证，这是标准化门店编码大小写**之前**的结果）：

```
      mean        sum  count
S001  ...         ...    ...
S002  ...         ...    ...
s001  ...         ...    ...
s002  ...         ...    ...
...（共8行，S001系列被拆成了大小写两套）
```

**本来只有4家门店，`groupby` 之后却出来了8行结果。这是代码写错了吗？**

不是代码的问题，是数据本身的问题。`groupby`、`==` 这类操作是严格按照字符串**完全相等**来分组/匹配的，`S001` 和 `s001` 在程序眼里就是两个完全不同的类别，就像"苹果"和"苹果 "（多一个空格）对程序来说也是两个不同的字符串。问题出在门店编码的大小写没有统一，而不是 `groupby` 本身出了问题。

顺手观察一下透视表里有没有异常值（比如某个门店 × 会员等级组合的销售额汇总出现负数）——先记下这个现象，不急着展开，它和上一节讲的"销售数量异常值"是同一个根源，会在下面"综合实战"里串起来。

这也正是上面留下的疑问的答案的前半句：筛选不全、分组被拆散，都是同一类"隐形坑"造成的，下一节正式把它解决掉。

## 七、字符串与类型转换：把隐形坑彻底解决

现在一次性解决前面留下的两个疑问：一是门店编码大小写不统一导致分组被拆散；二是用 `df["门店编码"] == "S001"` 筛选时查不全。

```python
d2 = d.copy()
d2["门店编码"] = d2["门店编码"].str.upper()   # 统一转大写

print("标准化前唯一值数:", d["门店编码"].nunique())
print("标准化后唯一值数:", d2["门店编码"].nunique())
```

实际运行结果（已验证）：

```
标准化前唯一值数: 8
标准化后唯一值数: 4
```

一行 `.str.upper()`，8 种取值收敛成 4 种，真正对应的 4 家门店。这也解释了前面留的疑问：`== "S001"` 之所以查不全，是因为有一部分记录写的是小写的 `s001`，被完全匹配的筛选条件漏掉了——**代码没有报错，结果却悄悄少了一部分**，这类错误比直接报错更危险，因为它不会主动提醒你去检查。再回头用标准化后的 `门店编码` 重新做一次 `groupby`，就只剩 4 行，和业务常识一致了，透视表里的异常负数汇总问题也会随之消失（根源其实是上一节讲的"销售数量异常值"参与了求和，下一节综合实战会验证这一点）。

> 🔑 **判别口诀**：字符串字段在做分组、筛选、关联这类"按值匹配"的操作之前，先问一句——这个字段的大小写、空格、全角半角有没有统一？没统一，一律先用 `.str.upper()` / `.str.strip()` 这类方法清洗，再做匹配类操作，顺序不能反。

类型问题还有一个常见场景——日期：

```python
print(d2["销售日期"].dtype)              # 转换前：object（字符串）
d2["销售日期"] = pd.to_datetime(d2["销售日期"])
print(d2["销售日期"].dtype)              # 转换后：datetime64
print(d2["销售日期"].dt.month.value_counts().sort_index())   # 按月统计
```

`销售日期` 这一列读进来的时候是字符串类型（`object`），表面看起来是日期，但 pandas 并不知道它是日期——字符串没法直接做"晚于某天""按月汇总"这类操作。`pd.to_datetime` 把它转换成真正的日期类型后，才能用 `.dt.month` 这类日期专属功能。**类型不对，对应的功能就用不了**，这和字符串格式不统一是同一类问题的两种表现：**数据"看起来"是对的，不代表程序"认得出"是对的。**

**板书式小结**：大小写/格式不统一，机器眼里就是"不同的类别"；类型不对，对应的功能就用不了。

## 九、练一练诊断能力：这三段代码错在哪

能写代码只是第一步，能看出别人代码里的问题，是更进一步的能力——这也是实际工作中排查问题最常用到的技能。下面三段代码都是真实常见的错误写法，花1分钟自己先想一想问题出在哪，再往下看解析。

**片段 A**：
```python
df_vip = df[df["会员等级"] == "黄金"]
df_vip["销售额打折"] = df_vip["销售额"] * 0.9   # 报 SettingWithCopyWarning
```

**解析**：在筛选出来的子表上直接赋值新列，没有先 `.copy()`，容易引发未定义行为（pandas不确定你是在操作原表的视图还是一份独立副本）。正确写法是 `df_vip = df[df["会员等级"]=="黄金"].copy()`，先声明这是独立副本，再放心赋值。

**片段 B**：
```python
print(df[df["销售额"] == "NaN"].shape)           # 永远是(0, 7)，没有正确识别缺失值
```

**解析**：用字符串 `"NaN"` 去匹配缺失值是错误的做法——缺失值在 pandas 里不是字符串 `"NaN"`，而是一个特殊的浮点值。应该用 `df["销售额"].isna()` 去判断，而不是用等号去比较一个字符串。

**片段 C**：
```python
df_s001 = df[df["门店编码"] == "s001"]            # 漏掉了大写的S001，结果不完整但不报错
```

**解析**：没有先用 `.str.upper()` 统一大小写就直接按固定字符串筛选，悄悄漏掉了另一部分数据——这正是第七节讲过的那个坑。**片段 C 最值得警惕：它不报错，只是结果悄悄错了。** 代码报错至少你知道要修；结果"看起来正常但其实漏了数据"，往往要等到后续分析结果离谱才会被发现。这也是为什么本课题反复强调"体检三件套"和"先统一格式再筛选"的原因。

## 回到开头

现在回答最开始那道判断题：这批"字段齐全、表格规整"的销售数据，能直接拿去建模吗？

**不能。** 光是前3行里就藏着两个问题：第2行销售额是缺失值（`NaN`），第3行门店编码写成了小写 `s001`。体检一遍整份数据后，问题比这更多——销售额缺失15%、会员等级缺失18%、24条销售数量异常、门店编码大小写混用导致本来4家门店被拆成8种取值。**这些问题单独看都不报错，数据表面上"看起来没问题"，正是最容易被直接喂给模型的危险数据。**

这正是本课题反复出现的同一个道理：**看起来规整的数据，不代表真的干净；看起来好看的指标（比如均值3689.6），也不代表真实——必须动手体检、动手验证，才能把"看起来"和"真的是"区分开。** 这个习惯，在下一课题讲"数据质量六维度"时还会继续用到，是整个四级阶段最基础、也最重要的一条暗线。

## 随堂练习（自测）

**练习 1**：某电商销售额字段存在长尾分布（多数订单金额不高，少数大额订单极高），缺失值该用均值还是中位数填充？

**答案**：中位数。长尾分布下均值会被少数极端大额订单拉高，用均值填充会系统性高估大多数缺失样本的真实水平；中位数不受极端值影响，更能代表"典型"水平。

**练习 2**：缺失值处理的正确决策顺序是什么？

**答案**：①先判断能否补录（如联系原始数据源核实）；②不能补录时，判断这批缺失数据占比大不大、删除影响大不大，影响小可直接删除；③必须填充时，先看字段的分布形态，偏态（长尾）分布用中位数，接近对称分布可用均值。这是一个决策流程，不是"遇到缺失就默认用均值"的单一公式。

**练习 3**：`df.isnull().sum()` 和 `df.duplicated().sum()` 分别统计什么？

**答案**：`df.isnull().sum()` 统计每一列的缺失值数量；`df.duplicated().sum()` 统计整个数据框中重复行的总数量。前者按列统计，后者是对整行记录做重复性判断。

**练习 4**：训练集、验证集、测试集三者的作用分别是什么？为什么不能混用？

**答案**：训练集用于模型学习参数；验证集用于调参和判断何时该早停（避免过拟合）；测试集用于最终评估模型的真实效果。三者混用会导致评估结果失真——比如用训练集数据做最终评估，得到的准确率会虚高，无法反映模型在未见过数据上的真实表现。

**练习 5**：为什么说"动手验证优于凭感觉判断"？结合本课题举一个例子。

**答案**：因为很多直觉判断可能是错的，只有实际跑一遍数据才能确认。例如本课题中，很多人凭感觉认为"缺失值就该用均值填充"，但实际对比均值和中位数的计算结果后，会发现长尾分布下两者差异巨大，均值填充会带来系统性偏差——这个结论只有动手算一遍才能真正确信，仅凭"感觉均值填充很常见"是不够的。

## 小结

| 要点 | 一句话 |
|---|---|
| 范式判断 | 有答案→监督；没答案但有结构→无监督；没答案但有反馈→强化 |
| 训练/验证/测试集 | 三者独立；测试集一旦参与调参就失去评估真实效果的意义 |
| pandas核心能力 | 读写+体检三件套+缺失/重复/异常处理+分组聚合+字符串类型处理 |
