学员小李提交的《化妆品门店销售数据采集与处理流程优化建议书》写道：

> **现状与问题**：销售额字段缺失率15%（120条），且存在严重长尾分布（均值3689.6，中位数194.0，相差近19倍）；SKU003、SKU011、SKU022销售额均值偏离同类SKU正常水平（800-900元）约30-45倍，疑似数量级录入错误；门店编码存在8种大小写混用写法（应归并为4种）；销售数量字段出现24条负值/零值记录。

> **优化建议**：建议统一采集和处理流程规范，加强数据质量管控，提升整体数据可靠性。

这份建议书被项目负责人打了回来，批注只有一句：**"问题你写得比我还清楚，但接下来要做什么，我一个字都看不出来。"**

**先别往下看：这份建议书的"现状与问题"部分写得扎实不扎实？既然写得扎实，为什么还是被打回了？**

## 一、建议书的标准结构

```
现状与问题（量化描述）→ 根因分析 → 优化方案 → 预期收益（可度量）→ 实施计划与风险
```

前三个课题（1-1检测六维度、1-2图像/文本/销售数据检测实操、1-3处理方法优化）练的都是"**现状与问题**"这一段——怎么查出问题、怎么处理问题。本课题要解决的是后面四段：怎么把"查出来、处理好"的东西，写成一份别人看了就能照着推动的正式建议。

**为什么必须是这五段，少一段不行？**

- 少了"根因分析"：别人不知道该往哪个方向使劲，很容易把方案用错方向（这一点在下一节会展开讲）。
- 少了"预期收益"：没人知道方案做完算不算成功，也没法验收。
- 少了"实施计划与风险"：方案停留在纸面，没人知道第一步该干什么。

而且要注意一点：**建议书不是凭空写出来的，它通常建立在业务/数据分析发现的问题基础上**——没有1-1、1-2、1-3扎实的检测和处理工作打底，"现状与问题"这一段根本写不出来。这也是为什么这个课题要放在模块的最后一个。

## 二、一份不合格和一份合格的对比

**不合格**：
> "销售数据存在质量问题，建议加强数据治理。"

问题：问题描述模糊（什么质量问题？多严重？），建议空洞（怎么"加强"？），没有可验证的目标。

**合格**：
> "销售额字段缺失率15%，当前无填充机制；SKU003/011/022存在疑似数量级错误（销售额均值是同类SKU的30-45倍）。建议：①建立销售额缺失自动告警机制，缺失率超过5%时触发人工核查；②对销售额异常高（超过同类SKU均值10倍以上）的记录自动标记待复核。预期将销售额字段的有效性从当前85%提升至98%以上，观察周期1个月。"

区别在于：**问题量化、方案具体、指标可验证**。

### 把差距提炼成一个可以直接套用的公式

```
合格的优化目标 = 当前基线数值 → 具体方案 → 目标数值 → 观察周期
```

拿合格范例对照一下：基线是"有效性85%"，方案是"告警机制+异常标记规则"，目标是"98%以上"，观察周期是"1个月"——**四件一样不少**。而不合格范例的那句话，四件套一件都没有，这才是它被判定为空洞的真正原因，不是因为字数少。

> 💡 建议书还须包含**成本与可行性考量**——不能只谈理想方案而不管实施成本，否则无法真正推动落地。这一点在第四节会展开讲。

### 回到开头的判断

现在回头看小李的建议书："现状与问题"部分数字详实（15%、120条、30-45倍、8种混用、24条负值），这部分没问题。问题出在"优化建议"部分——"统一采集和处理流程规范，加强数据质量管控"，套进四件套检查一下：**当前基线没有、具体方案没有、目标数值没有、观察周期没有，一件都不占**。

**这正是问题的本质**：现状分析做得再详实，只要优化建议部分空洞，整份建议书依然会被打回。这也是为什么本课题不再练"怎么查问题"（前三课已经练够了），而是专门练"查完之后怎么写"。

## 三、根因分析：为什么"找对问题"不等于"找对方向"

先做个预测：课题1-3里，门店编码大小写混用（S001/s001等8种写法）的问题，我们当时是怎么处理的？用 `.str.upper()` 做归一化，8种取值合并成了4种。

**预测一下**：如果这批数据处理完上线了，明天系统又导入一批新的销售记录，门店编码还会不会**再次**出现大小写混用？

先写下你的预测，再往下看。

### 答案：会，而且会一直复发

1-3的归一化操作，解决的是"**已经产生的**脏数据"，但它没有触碰"**为什么会产生**脏数据"这个根源——门店录入编码时用的是自由文本输入框，谁都可以随手打成大写、小写，系统不做任何校验。只要这个录入方式不变，新数据进来，照样会混入新的大小写变体。

> 📌 **机制**：处理环节能清理已经脏了的数据，但清理不掉"为什么会脏"。每做一次归一化，只是把这一批数据擦干净了，下一批还得重新擦一遍。

这就引出了一组对比：

| | 处理环节优化（治标） | 采集环节优化（治本） |
|---|---|---|
| 动作 | 每次拿到数据后做清洗（如 `.str.upper()`） | 从录入端改为下拉选择/系统校验，禁止自由文本输入 |
| 效果 | 已产生的问题被清理，但新数据仍会复发 | 问题从源头被杜绝，后续数据天然规范 |
| 成本 | 看似每次成本很低，但长期重复执行、累积维护成本高 | 有一次性改造成本，但一劳永逸 |

### 这就是"根因分析"存在的意义

根因分析不是把现象再重复一遍（"门店编码有8种写法"这句话谁都会写），它要回答的是：**这个问题到底出在哪个环节**。只有先确定了环节，优化方案才知道该往哪个方向使劲。不做根因分析、拿到问题直接堆处理方案，很容易一直在"治标"上反复用力，却从没碰过源头——这也是为什么同样的根因分析思路，一到写方案就必须先问环节归属，而不是先问"用什么技术"。

> 🔑 **判别口诀**：下一批新数据还会不会复发同样的问题？**会 → 到采集环节找根因。不会 → 处理环节内部解决就够了。**

### 注意：同一个现象，根因可能不同

不要死记"门店编码问题=采集环节问题"这种对应关系。比如"销售额字段缺失15%"，根因可能有两种完全不同的情况：

- 如果是门店收银系统**没有强制要求**录入销售额字段——根因在**采集环节**，方案应该是给收银系统加必填校验；
- 如果是销售额本身都录入了，只是后台在合并多个门店数据源时脚本逻辑有漏洞、把部分字段弄丢了——根因在**处理环节**，方案应该是修复合并脚本的逻辑。

同一个"缺失15%"的现象，背后可能是完全不同的根因，必须具体排查，**不能套公式**，这正是根因分析比现象描述更难、也更有价值的地方。

## 四、成本与可行性：为什么"理想方案"也会被打回

第三节讲到采集环节能治本，那是不是建议书应该直接写："立即把采集系统全面推倒重做，所有字段都加上强校验"？

**先判断一下**：这个方案合理吗？

### 答案：方向对，但这么写同样会被打回

这个方案听起来很彻底，但负责人看完大概率会问：**要花多少成本？由谁来改造——IT部门要排期多久？改造期间门店收银系统还能不能正常使用？**

如果这些问题答不上来，"立即全面重构"和开头那句"加强数据治理"其实是同一种空话，只是听起来更有技术含量而已——**两者的共同缺陷都是：只说了方向，没说清楚怎么走到那个方向、要付出什么代价**。

> 📌 **机制**：理想方案只回答"该怎么做最彻底"；可行方案还要回答"用多大代价、花多久时间、谁来推进"。少了后半句，再正确的方向也无法落地，负责人没法基于一句"推倒重做"做决策。

### 更合格的写法：分阶段、分优先级

> ①**优先**对影响范围最大、改动成本最低的门店编码字段，先在前端加一个下拉选择框（改动小，1-2周可上线）；
> ②销售额/销售数量的自动化异常检测规则，作为**后续阶段**，先在异常率最高的门店试点，验证有效后再全面推广。

这样写，既保住了"治本"的方向，又给出了负责人能接受、能落地的节奏——这就是"成本与可行性考量"在建议书里真正发挥的作用：**不是让方案变得保守，而是让正确的方向变得可执行**。

> 🔑 **判别口诀**：理想方案 ≠ 可行方案。**理想方向 + 分阶段 + 说清楚谁来做/多久/什么风险 = 可行方案。**

## 五、实施计划与风险：写完方案不等于写完建议书

很多人把"实施计划与风险"这一段直接漏掉，或者只写一句"尽快实施"。这一段其实有明确的三个必备要素：

1. **步骤**——先做什么、后做什么（就是第四节的①②两步）；
2. **涉及角色**——谁来改、谁来验收（例如"IT部门负责前端改造，数据组负责验收新采集数据的合规率"）；
3. **潜在风险**——可能遇到什么阻力（例如"采集系统改造涉及IT部门排期，短期内可能增加门店录入操作步骤，一线人员或有抵触，需提前培训说明"）。

**为什么这三样缺一不可？**

少了"步骤"，负责人不知道从哪里开始推进；少了"角色"，方案容易变成"谁都该做、谁都没做"；少了"风险"，一旦推进中遇到预料外的阻力（比如一线门店抵触改用下拉选择框），团队毫无准备，项目很容易半途而废。**这三样信息合在一起，才能让一个"方向正确"的方案真正被推进下去**，这也是为什么"实施计划与风险"和"优化方案"是两个独立的段落，不能合并成一句话带过。

## 六、回到开头：小李的建议书该怎么改

现在把前面几节的内容合起来，重新审视小李那份被打回的建议书。

"现状与问题"部分不用动，数据已经足够详实。问题出在"优化建议"部分，需要按以下方式重写：

1. **区分根因环节**：销售额缺失、SKU数量级错误更可能是**处理/核实环节**问题（需要排查录入流程和核实价格表）；门店编码混用更可能是**采集环节**问题（录入时未做格式校验）。
2. **分优先级给方案**：先做成本低、见效快的（如门店编码改下拉选择），再做需要试点验证的（如异常值自动标记规则）。
3. **每条方案补上四件套**：例如"销售额有效性当前85% → 建立缺失告警+异常标记规则 → 目标98%以上 → 观察1个月"。
4. **补上实施计划与风险**：写清步骤、涉及的IT/数据组角色、以及可能遇到的一线抵触风险。
5. **补上成本与可行性说明**：哪些改动成本低可以立即做，哪些需要排期和预算。

把这五点补齐，"统一采集和处理流程规范，加强数据质量管控"这句空话，就能变成一份负责人能直接拍板推进的正式建议书。

## 随堂练习

**练习 1**：把"建议优化数据采集流程"这句话改写成一个可度量的优化目标。

<details><summary>答案</summary>示例："当前数据采集环节人工录入错误率约8%，建议引入自动化校验规则（如字段格式校验、取值范围校验），预期将录入错误率降至2%以下，观察周期2周。"——关键是给出当前基线数值、具体方案、目标数值和观察周期。</details>

**练习 2**："销售数据存在质量问题，建议加强数据治理"这句话存在哪些具体问题？

<details><summary>答案</summary>三个问题都没有回答：①"存在质量问题"没有说明是什么问题、有多严重（缺乏量化）；②"加强数据治理"没有说明具体怎么做、谁来做（方案空洞）；③没有说明做到什么程度算完成、怎么验证效果（缺乏可验证指标）。这三点缺一不可，是建议书是否合格的核心判断标准。</details>

**练习 3**：建议书中为什么必须包含成本与可行性考量？

<details><summary>答案</summary>因为脱离成本和可行性的"理想方案"即使技术上正确，也可能因为资源不足、周期过长等原因无法落地。建议书的目的是推动实际改进，而不是展示理想状态，必须让读者（通常是决策者）能判断这个方案现实中能不能做、值不值得做。</details>

**练习 4**：优化建议书的"根因分析"环节，和"现状与问题"环节有什么区别？

<details><summary>答案</summary>"现状与问题"描述的是观察到的表面现象（如销售额字段缺失率15%），"根因分析"要回答这个现象背后的深层原因（如为什么会缺失——是采集环节没有强制校验，还是系统对接存在遗漏）。根因分析的质量直接决定了后续优化方案是否对症，跳过根因分析直接给方案容易"治标不治本"。</details>

**练习 5**：一份建议书只写了详实的问题分析，但没有给出具体优化方案，这份建议书合格吗？

<details><summary>答案</summary>不合格。建议书的核心价值在于"建议"，即提出可执行的优化方案，仅有问题分析没有解决方案等于只完成了一半工作。四级的能力要求是"对业务数据处理方法提出优化建议"，缺少建议部分无法体现这项核心技能。</details>
