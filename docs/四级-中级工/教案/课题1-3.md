## 一、教学目标

### 知识目标
1. 能说明常见处理方法的适用边界（删除vs填充、均值vs中位数vs前向填充）。
2. **能说明"方法用错比不处理更糟"的典型情形**。

### 技能目标
1. **能识别现有处理方法的缺陷并提出替代方案，且能说明替代理由**。
2. 能评估优化前后的效果差异。

---

## 二、教学重点与难点

**重点**：数量级错误（录入错误导致的异常值，不同于正常的长尾分布）的识别方法。

**难点**：学员容易把"数量级错误"和"正常的长尾分布高值"混为一谈，用同一种方式处理（如都用中位数替换），但数量级错误应该被识别并修正，而非简单填充掩盖。

---

## 三、学情分析与前置知识

学员已学完课题1-1、1-2，对质量检测方法已有基础，但本课题要求的是"检测出问题后，判断用哪种处理方法"，这是从"发现问题"到"解决问题"的进阶，容易出现"发现了但处理错"的情况。此外，学员此前接触的处理操作多停留在"能跑通就行"，本课题还要求建立"处理方法本身也有优劣之分（效果上/效率上）"的意识，这是部分学员此前未曾注意的维度。

---

## 四、教学方法与手段

1. **认知冲突法**：用数量级差异制造"这不是正常数据"的直观冲击；用循环与向量化的真实耗时反差制造"效率也要讲证据"的冲击。
2. **对比辨析法**：区分"正常长尾高值"和"数量级错误"两类表面相似实则本质不同的情形；区分"处理得对不对"与"处理得快不快、省不省"两个维度。
3. **任务驱动法**：以"产出一份数据处理方法优化报告"作为本课题的终产物。

### 环节二：新授——处理方法的适用边界（10–35′）

**讲授脚本**：

> "课题1-1教大家'检测'出问题，课题1-2练了检测的实际操作。今天要解决下一步——**检测出问题之后，具体该怎么处理？是删，还是填？填的话填哪个数？**
>
> 做这个判断，问自己三个问题。"

**第一问：缺多少，这个字段重不重要？**（决定删除还是填充）

> "如果缺失比例很高——比如超过一半——而且这个字段对后续分析非常关键，再怎么估算都不可信，不如整体删除这些记录或者明确标记出来，不要硬填一个数字冒充真实数据。但如果缺失比例可以接受，比如咱们1-1检测出的销售额缺失15%、会员等级缺失18%，这种程度优先考虑填充，把本来可用的样本保留下来。"

**第二问：分布是什么形状？**（决定均值还是中位数）

> "这是1-1已经验证过的结论：对称分布用均值没问题；长尾/偏态分布——比如咱们的销售额，被少数大额订单拉得很偏——用均值会被极端值带偏，必须改用中位数。还记得那个反差吗？均值3689.6，中位数194.0，相差近19倍。"

**第三问：记录之间有没有顺序关系？**（决定能不能用前向填充）

> "前向填充（ffill）的逻辑是：用前一条记录的值顶替当前缺失值。这个假设只有在记录之间**真的存在时间或空间上的连续性**时才成立——比如同一台设备按时间顺序连续采集的传感器读数，中间短暂断了几次，用前一个读数顶上通常合理。
>
> 但是——**我们这份订单数据，每一条记录是不是互相独立的？**"

**预期学员反应与教师应对**：

| 学员反应 | 教师应对 |
|---|---|
| "不是，订单之间没有关系" | 肯定："对。上一条订单的销售额和下一条毫无关系，这种情况下用前向填充，相当于凭空捏造了一种本不存在的因果关系，是典型的用错场景。" |
| 犹豫或答"好像可以用" | 追问："如果我们按录入顺序，把第5条订单的缺失值，填成第4条订单的销售额——这个数字和第5条订单本身有任何关系吗？" |

**板书核心句**：

> **先问比例和重要性决定删不删；再问分布形状决定均值还是中位数；最后问有没有顺序关系决定能不能用前向填充。**

**学员活动**：记录三类方法的适用场景，判断本课数据集是否适用前向填充并说明理由。

### 环节三：实操一——识别数量级错误SKU（难点突破，35–75′）

**教师指令**：

> "打开 Jupyter，我们按SKU分组算一下销售额均值，看看能不能找到异常。"

**投影代码**（学员照抄运行）：

```python
import pandas as pd
d = pd.read_csv("../数据集/cosmetics_sales.csv")
sku_mean = d.groupby("SKU")["销售额"].mean().sort_values(ascending=False)
print(sku_mean.head(5))
```

**预期输出（已实测验证）**：

```
SKU003    39700.6
SKU022    28900.9
SKU011    27164.2
...
```

**教师讲解**：

> "SKU003均值39700.6、SKU022均值28900.9、SKU011均值27164.2，而正常SKU均值通常在800-900左右——**相差约30-45倍**。这不是正常的销售波动，是数量级录入错误（比如单价多打了两个0）。"

**教师提问**：

> "如果你看到这几个SKU销售额偏高，直接用中位数去'拉平'它们，合理吗？"

**预期学员反应与教师应对**：

| 学员反应 | 教师应对 |
|---|---|
| "合理，用中位数替代是常见做法" | 追问："中位数替代适用于什么场景？是'数据本身没错、只是有点极端'，还是'数据本身就是录入错误'？这两种情况一样吗？" |
| "不合理，应该先核实" | 肯定："对，这是关键区别。中位数替代处理的是'正常但极端'的数据，而数量级错误是'根本就是错的'数据，掩盖不等于修正。" |

**教师总结**：

> "不合理。这是**错误数据**，应该先排查确认是否为数量级录入错误（如价格多了100倍），核实后应**按正确值修正**，而不是用统计手段掩盖。统计手段（中位数替代）适用于正常数据的填充，不适用于已确认的录入错误——**掩盖问题和解决问题是两回事**。
>
> 发现一处错误后，还要多问一句：**是不是还有同类遗漏？** 核实这批错误是否集中出现在某个录入环节或时间段，排查有没有其他未被发现的类似记录，而不是只改掉已发现的这几条就结束。"

**回扣导入**：

> "现在回到开头——小李的那份报告，现在再看，你觉得能通过吗？"

（预期学员此时能明确答出"不能通过"，并说出理由）

> "对。统一用中位数替换，恰恰是把录入错误当成了正常数据来掩盖。这正是一会儿我们要讲的——**方法用错比不处理更糟**。"

### 环节五：新授——方法用错比不处理更糟（85–105′）

**讲授脚本**：

> "很多人觉得'好歹做了处理，总比放着不管强'。我们来看一个具体后果，检验这句话对不对。
>
> 还记得1-1算出的那组数字吗：销售额均值3689.6，中位数194.0。如果销售额缺失的那120条记录，一律用均值3689.6去填充——这批记录大多数真实水平在一两百元左右（参照中位数194.0）——会发生什么？"

**预期学员反应与教师应对**：

| 学员反应 | 教师应对 |
|---|---|
| "填错了，数字不对" | 追问："具体错在哪？这120笔普通订单，填充之后在报表里看起来像什么？" |
| "看起来像是大额订单" | 肯定："对。这120笔本来一两百元的普通订单，被'包装'成了近3700元的大单。如果后续按门店统计业绩、算员工提成，这批被污染的数据会让涉及较多这批记录的门店或SKU业绩虚高。" |

**关键对比提问**：

> "现在对比两种情况：第一种，这120条销售额干脆留空（NaN）；第二种，统一填成3689.6。**哪一种对后续工作的危害更大？**"

（引导讨论后给出结论）

**教师总结话术**：

> "留空的数据，至少任何人在统计前都能一眼看到'这里有120条缺失'，知道这部分结果需要打问号、需要谨慎对待。**而错误的处理方法，把一个'看得见的缺口'变成了一个'看不见的污染'**——填进去的数字'看起来很正常'，混入正常数据后根本无法分辨，比留白更难被发现、更难挽回。这就是'方法用错比不处理更糟'的真正含义：不是说随便处理一下也比什么都不做强，而是**错误的处理可能制造出一个比原问题更隐蔽、更难纠正的新问题**。"

**板书核心句**：

> **错误处理的危险，在于它把可见的问题变成了不可见的污染。**

### 环节七：新授——处理效率优化（130–160′）

**讲授脚本**：

> "前面讲的都是'处理方法选得对不对'。本课题还有同样重要的另一面——处理方法**跑得快不快、占用内存多不多**。数据处理方法优化，优化的不只是结果，也包括过程的效率。"

**方向一：向量化替代循环**

**投影代码**：

```python
import timeit
discount_map = {"黄金": 0.9, "白银": 0.95, "普通": 1.0}

def loop_version(df):
    out = []
    for idx, row in df.iterrows():
        rate = discount_map.get(row["会员等级"], 1.0)
        out.append(row["销售额"] * rate)
    return pd.Series(out, index=df.index)

def vector_version(df):
    rate = df["会员等级"].map(discount_map).fillna(1.0)
    return df["销售额"] * rate

t_loop = timeit.timeit(lambda: loop_version(d), number=20)
t_vec = timeit.timeit(lambda: vector_version(d), number=20)
print(f"循环版本单次均值: {t_loop/20*1000:.3f} ms")
print(f"向量化版本单次均值: {t_vec/20*1000:.3f} ms")
```

**实测结果（Python 3.11.17 + pandas 2.3.3 已验证）**：循环版本单次均值约 **10.4 ms**，向量化版本约 **0.2 ms**，**快约52倍**。

**讲解机制**：

> "为什么差这么多？循环版本每处理一行，都要经过一次Python解释器的调度开销；向量化版本把整列数据一次性交给pandas底层（用C实现）批量运算，解释器开销只发生一次，不是发生800次。**数据量越大，这个差距会被成倍放大。**"

**方向二：分块处理大文件**

> "如果数据文件大到内存放不下——比如上千万条记录——可以用 `pd.read_csv(path, chunksize=10000)` 分块读取，每次只加载一小块进内存处理，再汇总结果。本课800条数据用不上这个技巧，但数据量上一个量级，这是必备手段。"

**方向三：字段类型降存**

**投影代码**：

```python
before = d.memory_usage(deep=True).sum()
d2 = d.copy()
d2["门店编码"] = d2["门店编码"].str.upper().astype("category")
d2["会员等级"] = d2["会员等级"].astype("category")
d2["SKU"] = d2["SKU"].astype("category")
d2["销售数量"] = d2["销售数量"].astype("int8")
after = d2.memory_usage(deep=True).sum()
print(f"优化前: {before}字节, 优化后: {after}字节, 降幅: {(1-after/before)*100:.1f}%")
```

**实测结果（已验证）**：优化前 278756 字节，优化后 119226 字节，**降幅约57.2%**。

**板书核心句**：

> **向量化：批量交给底层算，别一行行自己跑。类型降存：数值范围小就用小类型，文本重复多就用category。**

### 环节八：实操三——性能优化验证（160–195′）

**任务布置**：

> "大家亲手运行一遍环节七的两段代码，验证你机器上的结果和课堂展示是否一致（数值可能有ms级波动，但数量级应该一致）。"

**巡回指导要点**：

- 检查学员是否用 `map` 而非 `apply` 实现向量化——`apply` 本质上仍是逐行调用，速度提升有限，是常见的"伪向量化"误区。追问："`apply` 和 `map` 都能完成同样的事，为什么我们选 `map`？"
- 检查 `int8` 的选择是否稳妥——`int8` 范围是 -128~127，本课数据销售数量范围是 -7~7，够用；但追问："如果以后业务扩大，单笔销售数量可能超过127，还能用 `int8` 吗？" 引导学员意识到"够用就行，但要留出合理余量"，不能只图当前数据集下最小。

**预期学员反应与教师应对**：

| 学员反应 | 教师应对 |
|---|---|
| 用 `apply(lambda row: ...)` 代替 `map` | 指出："这样写比循环快不了多少，因为 `apply` 内部本质还是在逐行调用你的函数。真正的向量化是让pandas的底层运算直接作用在整列上，像 `map` 这种按值映射的写法才是。" |
| 不假思索把所有整数列都降为 `int8` | 追问："这一列的取值范围是多少？`int8` 装得下吗？如果装不下会发生什么？"（溢出或报错）引导养成"先看取值范围，再选类型"的习惯 |

**学员活动**：独立运行代码，记录自己机器上的实测数值，与课堂展示结果对比。

### 环节九：新授与讨论——评估效果与成本权衡（195–215′）

**讲授脚本**：

> "判断一次处理方法优化是否真正有效，不能只看'代码没报错'，要有具体的前后对比。"

**评估框架（板书）**：

```
处理方法对不对 → 对比优化前后的数据分布统计量 / 下游指标
处理效率高不高 → 对比优化前后的运行耗时 / 内存占用，用具体数字说话
```

**成本权衡讨论**：

> "现在问大家一个问题：刚才咱们在800条数据上实测，循环10.4ms、向量化0.2ms。这个差距，在实际工作中你能感觉出来吗？"

（预期：学员意识到几毫秒的差异几乎无感知）

> "既然感觉不出来，那是不是这个优化没必要做？"

**预期学员反应与教师应对**：

| 学员反应 | 教师应对 |
|---|---|
| "没必要，反正感觉不出来" | 追问："如果这批数据以后涨到几十万条，每天要批量跑几十次，还感觉不出来吗？" |
| "看情况，数据量大了就有必要" | 肯定："对。为了引入 `category` 类型，还要考虑'后续出现原来没有的新类别值会报错'这类维护成本——在小数据、低频场景下，这个成本可能比收益还大。**真正值得优化的，是数据量大、运行频率高、已经成为瓶颈的场景**，不是逢优化必做。" |

**板书核心句**：

> **数据量小、偶尔跑一次 → 不必为了优化而优化；数据量大、高频运行 → 效率优化的收益会被放大，值得投入。**

**教师活动**：展示2-3份预先准备的"典型误用"案例卡片，组织分组诊断。

**案例卡片**（教师预先准备）：

```
          处理方法三问：删不删？填什么？补前值行不行？
  删除   ←— 缺失比例过高 且 字段关键、无法估算
  均值   ←— 分布对称
  中位数 ←— 长尾/偏态（本课"销售额"即此例）
  前向填充(ffill) ←— 有时间/顺序关系的连续记录（订单记录不适用！）

┌───────────────── 方法用错的代价 ─────────────────┐
│ 销售额  均值 3689.6   中位数 194.0  （1-1 实测）  │
│ 若用均值误填120条缺失 → 普通订单被"包装"成大单   │
│ 错误处理 = 把"看得见的缺口"变成"看不见的污染"     │
└────────────────────────────────────────────────────┘

数量级错误识别：按SKU分组算均值，偏离30-45倍 → 核实修正，不可统计掩盖
```

字段降存：object→category，int64→int8

         数据量大、高频运行   → 值得优化
