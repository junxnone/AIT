# 教案 · 课题 3-1：智能系统维护与场景部署

| 项目 | 内容 |
|---|---|
| 所属等级 | 四级 / 中级工 |
| 对应国标 | 职业功能3 智能系统运维 · 3.1 智能系统维护与场景部署 |
| 对应实操试题代码 | 四-6（语音识别系统的场景部署方案设计） |
| 学时 | **4 学时**（理论 2 + 实操 2，共 240 min） |
| 授课类型 | 理论与实操一体化 |
| 教学场地 | 计算机机房 |

---

## 一、教学目标

### （一）知识目标
1. 能说明智能系统的基本组成（数据层、模型层、服务层、应用层）与运维关注点，**能说出日常维护记录应包含的三类信息**（功能使用情况、运行是否正常、异常现象描述）。
2. **能说明特定场景部署需考虑的要素**：硬件与算力、网络与时延、数据接口与格式、并发量、安全与权限、回滚方案。

### （二）技能目标
1. **能针对给定场景制定部署方案与检查清单**，且方案须结合该场景的具体特点（而非套用通用模板）。
2. 能识别常见部署问题并给出排查顺序（先查外部环境与接口，再查模型本身）。

---

## 二、教学重点与难点

### 重点
1. 部署检查清单的完整性——六大要素缺一不可。
2. 常见部署问题的排查顺序——先查网络/并发/接口等外部环境因素，不要上来就怀疑模型本身。
3. 日常维护记录须包含的三类信息，保证问题可追溯。

### 难点

| 难点 | 学员典型错误预判 | 突破方式 |
|---|---|---|
| 部署六要素中"非硬件类"要素容易被忽视 | 问"部署一个模型到新场景，你觉得最重要的是什么"，几乎全员只答"硬件算力够不够""模型能不能跑起来"，完全想不到接口格式、并发量评估、回滚方案 | 用真实场景制造认知冲突：某语音识别系统从安静客服场景扩展到嘈杂车载场景，**硬件和模型本身都完全没问题**，上线后却大面积投诉"说了指令没反应"。让学员亲身经历"硬件没问题 ≠ 部署没问题"的反差，再引出六要素清单，并用判别口诀巩固 |

---

## 三、学情分析与前置知识

**前置知识**：课题0-3（AI 原理基础）、课题1-1～2-4（数据质量检测、聚类分析、标注审核等）。

**学情判断**：学员经过前面几个课题的训练，已经习惯了"数据层面"的系统思维——拿到一批数据，会条件反射地去查六维度质量、算 Kappa、做分类诊断。但本课题是从"数据层面"切换到"系统运维层面"的第一课，这个思维惯性反而会造成新的盲区：学员容易把"模型效果好不好""数据准不准"当成部署成不成功的唯一标准，而现实中的部署问题大多出在数据和模型之外——网络、接口、并发、权限、回滚这些工程维度，恰恰是学员此前的训练里没有覆盖过的。教师需要明确点出这次思维切换，而不是让学员继续用旧框架硬套新问题。

---

## 四、教学方法与手段

1. **清单教学法**（核心）：用六要素检查清单结构化讲解，避免要素遗漏。
2. **情境排查演练法**：给出具体故障现象，训练排查顺序的判断力。
3. **任务驱动法**：以"复刻真实实操试题场景，产出一份可交付的部署方案"作为本课题终产物，缩短课堂练习与考核之间的距离。
4. **对比纠错法**：展示典型不合格方案，让学员分组诊断缺陷所在，从"自己会写"走向"能判断别人写得对不对"。

### 环节一：导入——车载场景部署判断题（0–15′）

**教师活动** —— 投影展示（不给结论）：

> "某语音识别系统原本只部署在安静的室内客服场景，识别效果一直很好。现在要把它扩展部署到车载场景——用户在开车时直接喊语音指令，车里有胎噪、风噪、音乐声。项目负责人说：**'模型没改、硬件算力也评估过绰绰有余，这次部署应该很顺利。'**"

**提问话术**：

> "先别急着下结论。花三十秒写下你的判断：如果这次部署真的只是把同一个模型原样搬过去，不做任何其他调整，上线后**最先暴露出来的问题会是什么**？"

**预期学员反应**：多数学员会预测"车内噪声大，识别准确率会下降"——这个判断方向没错，但只看到了"模型效果"这一个维度。

**教师收口**：

> "先记住你的预测。噪声确实会影响识别效果，这节课最后我们会回来验证——但真正让这次部署上线后被用户大面积投诉的，**可能根本不是识别准确率这件事**。"

**设计意图**：不直接否定学员的预测，让"硬件/模型没问题=部署没问题"这个隐含假设先被激活，后面用真实情况反转，冲击力更强。

---

### 环节二：新授——系统组成+运维关注点+维护记录三要素（15–45′）

**讲授脚本**：

> "要维护一个智能系统，先要清楚它由哪几层组成。一般分四层：**数据层**（数据存储与接入）、**模型层**（算法模型）、**服务层**（接口与调度）、**应用层**（最终用户界面）。日常维护要关注的是：运行状态监控、日志检查、数据更新、异常处理与上报、维护记录——这五项里，前四项大家在实习和日常使用系统时多少都接触过，**最容易被轻视、但考试和实际工作中同样看重的是最后一项：维护记录**。"

**追问引入维护记录**：

> "大家想过没有：如果半年后某条数据或某次故障被人翻出来追问'当时到底发生了什么'，我们凭什么能说清楚？"

（停顿，等待反应）

> "靠的就是维护记录。一条规范的记录要包含三类信息：**功能使用情况、运行是否正常、异常现象描述**。"

**逐项展开**：

| 要素 | 含义 | 为什么必须记 |
|---|---|---|
| 功能使用情况 | 当时在使用系统的哪个功能、做什么操作 | 没有这一条，后面排查时根本不知道"故障发生在哪个动作上" |
| 运行是否正常 | 当时系统整体状态（正常/异常/部分异常） | 用来快速定性，判断是个别功能问题还是系统性问题 |
| 异常现象描述 | 具体看到了什么现象（报错信息、卡顿时长、界面表现等） | **这是最容易被写成"结论"而不是"现象"的一项**——比如直接写"系统坏了"，而不写"点击提交后页面卡住约3分钟，刷新后恢复"。只有写清楚客观现象，后续排查的人才能按你写的步骤重新核实问题，而不是凭猜测排查 |

**板书核心句**：

> **运行记录三要素——功能使用情况 / 运行是否正常 / 异常现象描述；记录要写现象，不要只写结论。**

**学员活动**：记录四层架构与五项维护关注点，口头举一个自己最近使用某个系统时可以记录的例子（提问2-3人，重点检查是否写成了"现象"而不是"结论"）。

---

### 环节三：新授+案例讨论——部署六要素（难点突破，45–85′）

**教师活动**——揭晓真相：

> "回到开头的车载场景。实测情况是这样的：车内噪声确实让识别准确率有一定下降，这和大家的预测一致。但真正让这次部署上线后被用户大量投诉的，**不是识别准确率**，而是——用户喊了唤醒词，系统经常要隔好几秒才有反应，有的用户以为系统死机了。"

**关键提问**：

> "硬件算力评估过是够用的，模型也完全没改动，为什么会'卡'？"

**预期学员反应与教师应对**：

| 学员反应 | 教师应对 |
|---|---|
| "是不是车速太快信号跟不上" | 肯定方向："对，车辆移动中网络信号确实不如室内稳定，这是其中一个原因——**网络与时延**没有被重新评估" |
| 答不上来 | 引导："客服场景里，麦克风设备和网络环境是固定的、稳定的。换到车上，什么东西变了？"——引导联想到网络环境、设备采集格式的变化 |
| "是不是车上的麦克风和客服用的不一样" | 肯定并补全："对，车载麦克风的采样率、音频格式很可能和原来客服场景的设备不一样，这是**数据接口与格式**没有适配" |

**教师总结话术**：

> "这就是为什么我要强调'六要素缺一不可'——**硬件算力只是六个要素中的一个**，网络与时延、数据接口与格式这两项，恰恰是最容易被'模型能跑就行'这种想法完全忽视掉的。"

**第二案例（巩固"并发量"这一易忽视要素）**：

> "再看另一个真实场景：某团队把模型部署到新环境后，**硬件和模型本身都没问题**，上线后却频繁出现接口超时。排查后发现，是**新场景的并发请求量远超原设计容量**——这既不是硬件问题也不是模型问题，是**容量评估**这个环节被完全忽视了。"

**板书清单归纳**：

> **部署六要素：硬件与算力 / 网络与时延 / 数据接口与格式 / 并发量评估 / 安全与权限 / 回滚方案。数据接口格式、并发量评估、回滚方案，这三项最容易被"模型能跑就行"的想法掩盖掉。**

**学员活动**：填写六要素检查清单，对照车载场景案例逐项标注"这项在车载场景里具体对应什么"。

### 环节五：实操一——为车载场景制定部署方案（95–130′）

**任务书**（复刻实操试题四-6第1题）：

> 某语音识别系统原部署于安静的室内客服场景，现需扩展部署到嘈杂的车载场景（用户在驾驶中使用语音助手）。请针对这一新场景，**制定完整的部署方案，须覆盖六大部署要素**，且方案要结合车载场景的具体特点，不能是放之四海皆准的通用模板。

**方案必备要素**（教师给模板）：

```
一、场景背景说明（与原客服场景相比，新场景有哪些关键差异）
二、六要素逐项方案
    硬件与算力：……
    网络与时延：……
    数据接口与格式：……
    并发量：……
    安全与权限：……
    回滚方案：……
三、本方案与"通用部署模板"相比，针对车载场景做了哪些具体调整
```

**巡回指导要点**：

- 检查六要素是否全部覆盖（最常见遗漏：安全与权限——学员容易忘记车载场景涉及驾驶安全，需要限定危险操作的语音触发权限）。
- 检查方案是否真的"结合场景"而不是套模板：如果学员写"并发量：评估系统能否承受高并发"这种通用表述，而不是"车载场景通常单设备单用户，并发需求远低于客服中心，重点应放在响应速度而非吞吐量"这种结合场景的具体判断，要当场追问"车载场景的并发量跟客服中心比，是更大还是更小？"引导学员重新思考。

**学员活动**：独立撰写部署方案。

### 环节六：分组互评与典型错误诊断（130–155′）

**教师活动**：投影展示2-3份教师预先准备的"典型不合格方案"，组织学员分组诊断问题所在。

**预期诊断点**：

| 典型错误 | 应诊断出的问题 |
|---|---|
| 方案只写了"硬件算力评估通过，可以部署" | 遗漏网络时延、接口格式、并发量、安全权限、回滚方案五项，只盯着硬件一项 |
| 方案六要素都写了，但每一项都是通用表述（如"保证网络稳定""做好权限管理"） | 没有结合车载场景的具体特点展开，属于典型的"套模板"，拿不到针对性得分 |
| 回滚方案写"出问题就重启系统" | 没有理解回滚方案的本质——应该是"能快速切换回原有的按键交互方式"这类**真正可行的降级手段**，而不是模糊的"重启" |

**学员活动**：分组讨论，每组派代表指出至少1处问题并给出修改建议。

---

### 环节七：新授+实操二——常见问题排查顺序演练（155–180′）

**讲授脚本**：

> "部署方案写得再周全，上线后也可能出问题。这时候排查的**顺序**很关键——顺序错了，会把时间浪费在成本最高、但其实最不可能的那个原因上。"

**排查顺序表（教学演示）**：

| 现象 | 排查顺序 |
|---|---|
| 新环境运行报错 | 先查环境依赖版本是否一致，再查数据格式是否匹配 |
| 接口超时 | 先查网络时延，再查并发量是否超出设计容量 |
| 权限不足 | 查账号权限分配是否与新环境同步 |

**板书核心句**：

> **先查外部环境与接口，最后才怀疑模型本身——模型排查成本最高，留到最后。**

**实操任务**（复刻实操试题四-6第2题）：

> 刚才大家写的车载场景部署方案上线后，发现接口响应经常超时。请说明你的排查思路与顺序。

**预期学员反应与教师应对**：

| 学员反应 | 教师应对 |
|---|---|
| "先换个识别准确率更高的模型试试" | 追问："模型准确率和接口超时是一回事吗？超时说明请求'没有及时得到响应'，这和模型'识别得准不准'是两个问题。先别碰模型，想想还有什么环节会让响应变慢" |
| "先查网络时延，再查并发量" | 肯定："对。车载场景网络本身不如室内客服场景稳定，这是最先要排除的；其次才是看并发量是否超出预期" |

**学员活动**：独立写出排查顺序并说明理由，教师抽2-3人口述。

### 环节八：变式练习——填写维护记录表（180–205′）

**教师指令**：

> "现在把前面学的'维护记录三要素'用起来。给大家一个具体场景：**车载语音助手上线第3天，某用户反馈说了唤醒词系统没反应，运维人员登录后台查看日志，发现当时正值4G/5G网络切换，日志显示请求在网络切换的2秒内发生了超时。** 请把这个场景写成一条规范的维护记录。"

**巡回指导要点**：

- 检查是否写出了具体的"现象"（如"请求超时发生在网络切换的2秒窗口内"），而不是直接写结论（如"网络不好导致故障"）。
- 检查三要素是否齐全：功能使用情况（语音唤醒功能）、运行是否正常（部分异常，非全局故障）、异常现象描述（具体的网络切换时间点与超时表现）。

**对完成较快学员的追问话术**：

> "你这条记录写得很清楚了。再想一个问题：如果你是半年后看到这条记录的人，你能不能靠这条记录**判断出这是不是个例、要不要紧急修复**？记录里还需不需要补一句'该现象是否反复出现'？"

**设计意图**：把环节二讲的三要素落实成一次真实的书面产出，并通过追问把"记录现象"进一步推向"记录要能支撑后续判断"这一更高要求。

## 七、板书设计

**主板书区**

```
                 智能系统维护与场景部署

系统组成：数据层 → 模型层 → 服务层 → 应用层
维护记录三要素：功能使用情况 / 运行是否正常 / 异常现象描述（写现象，不写结论）

┌──────────────── 部署六要素检查清单 ────────────────┐
│ □ 硬件与算力      □ 网络与时延                      │
│ □ 数据接口与格式  □ 并发量评估                      │
│ □ 安全与权限      □ 回滚方案                        │
└──────────────────────────────────────────────────────┘
        ↑
真实案例：车载场景部署——硬件/模型都没动，
却因【网络时延 + 接口格式不匹配】导致指令卡顿数秒
```

**副板书区（常见问题排查顺序）**

```
现象              排查顺序
────────────────────────────────────────────
新环境运行报错 →  先查环境依赖版本 → 再查数据格式
接口超时       →  先查网络时延 → 再查并发量 → 最后才查模型本身
权限不足       →  查账号权限是否与新环境同步

判别口诀：先查"外部环境与接口"，再查"模型本身"——
         模型排查成本最高，永远留到最后一步
```
